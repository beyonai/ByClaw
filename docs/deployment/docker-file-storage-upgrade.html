ByClaw Docker 文件型运行态存储升级手册

本手册面向没有 Kubernetes/K3s 的纯 Docker 环境。目标是把 OpenClaw 容器内的 /by 从 MinIO/rclone FUSE 挂载切换到 NFSv4 真实文件系统。 MinIO 继续保留为对象存储、归档、共享和备份层。

推荐路线：Docker + OpenSandbox + NFSv4 + .env 驱动 deploy.sh init/update。

1. Docker 技术栈与总流程

不使用 Rook-Ceph。Rook 是 Kubernetes Operator，在纯 Docker 环境中不成立。本方案将文件型存储作为 Docker 宿主机的统一挂载点，再由 openSandbox 把用户目录 bind mount 给 OpenClaw 容器。当前主线不部署 CephFS、Rook-Ceph、K3s、SMB。

准备一台文件存储服务器，安装 NFS Server 并导出 /exports/byclaw。
在每台 openSandbox Docker 宿主机把共享目录挂载为 /mnt/byclaw-file。
配置 ByClaw：BYCLAW_SANDBOX_VOLUME_BACKEND=file。
迁移旧 MinIO/rclone 数据到 /mnt/byclaw-file/byclaw-${USER_CODE}/by。
启动沙箱并验证容器内 /by 不再是 FUSE/rclone。

2. 选型建议

方案 适合场景 推荐级别 说明
NFSv4 最快从 0 到 1 测通 首选 Linux 原生，部署简单，适合当前 Docker-only 测试。
OpenMediaVault + NFS 需要 Web 管理面、共享目录、容量和快照管理 推荐 底层仍建议通过 NFSv4 挂到 Docker 宿主机。
SMB3 / CephFS / K3s PVC 历史备选或未来扩展 本轮不落地 当前没有 K8s 环境，且 NFS 已能覆盖本轮 Docker 全流程测试。
MinIO/rclone 旧部署兼容 不推荐新用 对象存储不适合作为 SQLite、WAL、rename、锁等运行态文件系统。

3. 从 0 安装 NFSv4

3.1 文件存储服务器

选择一台独立 Linux 服务器作为文件存储服务器。不要把它和 openSandbox 运行态强绑定在同一个本地目录语义里。

# Ubuntu / Debian
sudo apt-get update
sudo apt-get install -y nfs-kernel-server

sudo mkdir -p /exports/byclaw
sudo chown -R root:root /exports/byclaw
sudo chmod -R 755 /exports/byclaw

编辑 /etc/exports。为了先适配不固定的宿主机或 Docker 网段，测试环境可以全网段开放。

/exports/byclaw  *(rw,sync,no_subtree_check,no_root_squash)
安全边界： * 表示允许任意客户端尝试挂载该 NFS export，适合内网测试或快速验证。 生产环境建议改成 openSandbox Docker 宿主机的固定 IP 或网段，例如 10.0.0.0/24(rw,sync,no_subtree_check,no_root_squash)。 NFS 服务端看到的通常是执行 mount 的宿主机 IP，不是 OpenClaw 容器内部随机 IP。 
sudo exportfs -rav
sudo systemctl enable --now nfs-server
sudo exportfs -v

3.2 OpenSandbox Docker 宿主机

每台会运行 openSandbox Docker 的宿主机都执行同样挂载，路径必须一致。

sudo apt-get update
sudo apt-get install -y nfs-common

sudo mkdir -p /mnt/byclaw-file
sudo mount -t nfs4 STORAGE_SERVER:/exports/byclaw /mnt/byclaw-file \
  -o rw,hard,noatime,nconnect=4,_netdev

3.3 mount 命令解释

这条命令是在 openSandbox Docker 宿主机上执行的，作用是把文件存储服务器导出的 NFS 目录接到本机统一路径。

sudo mount -t nfs4 A_SERVER:/exports/byclaw /mnt/byclaw-file \
  -o rw,hard,noatime,nconnect=4,_netdev
片段 含义
sudo 挂载文件系统需要管理员权限。
mount 把一个文件系统挂载到本机目录树中。
-t nfs4 指定文件系统类型为 NFSv4。NFSv4 的锁语义和一致性通常比 NFSv3 更适合运行态文件目录。
A_SERVER:/exports/byclaw A 服务器，也就是 NFS 服务端导出的共享目录。可以写 IP、域名或主机名。
/mnt/byclaw-file B 服务器，也就是 Docker/openSandbox 宿主机上的本地挂载点。挂载后访问这里，实际读写 A 服务器目录。
rw 读写挂载。OpenClaw 需要在 /by 中创建、修改、删除文件。
hard NFS 服务端短暂不可用时，客户端 I/O 会等待恢复，而不是快速返回错误。运行态数据目录建议使用 hard，避免应用误以为写入成功或直接丢错。
noatime 读取文件时不更新访问时间，减少 metadata 写入压力。
nconnect=4 对同一个 NFS 服务端建立 4 条 TCP 连接，提高并发吞吐。需客户端内核支持，不支持时可去掉。
_netdev 标记这是网络文件系统。写入 /etc/fstab 后，系统会在网络就绪后再尝试挂载。

写入 /etc/fstab，避免重启丢失挂载。

A_SERVER:/exports/byclaw /mnt/byclaw-file nfs4 rw,hard,noatime,nconnect=4,_netdev 0 0

验证挂载和写入。

findmnt /mnt/byclaw-file
touch /mnt/byclaw-file/.probe-$(hostname)
ls -la /mnt/byclaw-file

3.4 OpenClaw 写入同步与性能边界

当 openSandbox 把宿主机 /mnt/byclaw-file/byclaw-${USER_CODE}/by bind 到 OpenClaw 容器 /by 后， 容器内凡是写到 /by 下的文件，都会通过 NFS 同步到 A 服务器的 /exports/byclaw。

容器内操作 是否写到 A 服务器 说明
/by/project/app.js、/by/output/video.mp4 是 属于 bind 到 NFS 的 /by 目录。
npm install 在 /by/project 执行 是 node_modules 会写到 NFS，但大量小文件会比本地盘慢。
python -m venv /by/project/.venv 是 虚拟环境会持久化，但安装依赖会产生大量 metadata 操作。
/tmp、/root/.cache/pip、/root/.npm 否 这些路径在容器本地层，除非额外挂载，不会自动同步到 A 服务器。
pip install 到系统 site-packages 否 写入容器镜像层或运行层，不属于 /by。

性能上，NFS 比 MinIO/rclone 更适合运行态文件系统，但它仍然是网络文件系统。大文件顺序读写、视频输入输出通常可接受；node_modules、pip 依赖、批量小文件、find、rm -rf 这类 metadata 密集场景会明显慢于本地 SSD。

建议的容器内目录策略：
  • /by：用户项目、需要持久化的数据、最终产物。
  • /tmp：ffmpeg 中间文件、临时缓存、可重建 scratch 数据。
  • /root/.cache：pip/npm 缓存，默认不持久化，减少 NFS 小文件压力。
mkdir -p /tmp/byclaw-work /by/output

ffmpeg -i /by/input/source.mp4 \
  -preset veryfast \
  /tmp/byclaw-work/result.mp4

mv /tmp/byclaw-work/result.mp4 /by/output/result.mp4

npm install --cache /tmp/npm-cache
PIP_CACHE_DIR=/tmp/pip-cache pip install -r requirements.txt

4. SSH 自动初始化 NFS

如果部署机可以 SSH 到 NFS Server 和 Docker/openSandbox/BE 宿主机，可以单独执行 deploy.sh nfs-init，只初始化 NFS，不拉镜像、不启动或重建中间件。脚本会安装 NFS Server、写入 /etc/exports、安装客户端、 挂载到 /mnt/byclaw-file、写入 /etc/fstab，并执行 findmnt 和写入探针。 

# .env
BYCLAW_DEPLOY_STORAGE=nfs
BYCLAW_DEPLOY_INIT_NFS=true

# A 服务器：NFS Server
BYCLAW_NFS_SERVER_HOST=10.0.0.10
BYCLAW_NFS_SERVER_PORT=22
BYCLAW_NFS_SERVER_USER=root
BYCLAW_NFS_SERVER_PASSWORD=
BYCLAW_NFS_EXPORT_PATH=/exports/byclaw
BYCLAW_NFS_EXPORT_CLIENTS=*

# B/C 服务器：Docker/openSandbox/BE 宿主机，多个用英文逗号分隔
BYCLAW_NFS_CLIENT_HOSTS=10.0.0.20,10.0.0.21
BYCLAW_NFS_CLIENT_PORT=22
BYCLAW_NFS_CLIENT_USER=root
BYCLAW_NFS_CLIENT_PASSWORD=
BYCLAW_NFS_MOUNT_OPTIONS=rw,hard,noatime,nconnect=4,_netdev

sh deploy.sh nfs-init
说明： sh deploy.sh nfs-init 是显式动作，会直接执行 NFS 初始化，不会触碰 Docker 服务。 BYCLAW_DEPLOY_INIT_NFS=true 只在完整首次部署 sh deploy.sh init 阶段生效。 后续增量更新使用 sh deploy.sh update，不会重复初始化 NFS。密码为空时使用 SSH key； Shell 版本如果配置密码登录，需要部署机安装 sshpass。

5. 配置 ByClaw 与 openSandbox

5.1 .env 推荐配置

推荐只在 .env 中选择部署 profile，具体派生变量由 deploy/storage-profile.sh 在 deploy.sh init/update 阶段统一设置。 

# .env
BYCLAW_DEPLOY_STORAGE=nfs
BYCLAW_DEPLOY_START_MINIO=false
BYCLAW_DEPLOY_INIT_NFS=false

FILE_STORAGE_TYPE=file
FILE_STORAGE_LOCAL_PATH=/mnt/byclaw-file
FILE_STORAGE_MINIO_MOUNT_ENABLED=false

BYCLAW_SANDBOX_VOLUME_BACKEND=file
BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-file
BYCLAW_SANDBOX_FILE_VOLUME_TYPE=nfs
BYCLAW_SANDBOX_FILE_VOLUME_SNAPSHOT_PROVIDER=nas
BYCLAW_SANDBOX_FILE_BROWSER_ENABLED=false

5.2 生成 openSandbox 配置

正常情况下不需要手工进入 deploy/middleware 生成配置，sh deploy.sh init 和 sh deploy.sh update 会按 .env 自动完成。需要单独调试时可执行： 

cd deploy/middleware
sh gen-opensandbox-config.sh
cat opensandbox-server.toml

应看到：

[docker.private_volume]
backend = "file"
file_root = "/mnt/byclaw-file"
file_type = "nfs"
snapshot_provider = "nas"
file_browser_enabled = false

5.3 启动或更新服务

# 首次部署
sh deploy.sh init

# 修改 .env 或镜像后增量更新
sh deploy.sh update
注意： 当前 ByClaw 后端会把 scope、subPath、mountPath 传给 openSandbox。 最终是否把 /mnt/byclaw-file/byclaw-${USER_CODE}/by bind 到容器 /by， 取决于 openSandbox server 镜像是否支持 [docker.private_volume] 配置。

5.4 一键部署脚本切换

一键部署入口通过 .env 选择 MinIO 或 NFS，deploy.sh 只负责 init 和 update 阶段。

# .env
# NFS 全文件型模式：OpenClaw /by 和 BE 文件 CRUD 都走 /mnt/byclaw-file
BYCLAW_DEPLOY_STORAGE=nfs

# legacy MinIO 模式：保持旧 MinIO/rclone 运行态方案
BYCLAW_DEPLOY_STORAGE=minio

# 混合模式：OpenClaw /by 走 NFS，上传/下载 API 继续走 MinIO
BYCLAW_DEPLOY_STORAGE=nfs-hybrid

# 首次部署
sh deploy.sh init

# 仅初始化 NFS，不动中间件和应用
sh deploy.sh nfs-init

# 增量更新
sh deploy.sh update

BYCLAW_DEPLOY_STORAGE=nfs 会自动应用：

FILE_STORAGE_TYPE=file
BYCLAW_SANDBOX_VOLUME_BACKEND=file
BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-file
BYCLAW_SANDBOX_FILE_VOLUME_TYPE=nfs
FILE_STORAGE_MINIO_MOUNT_ENABLED=false

NFS 模式默认跳过 MinIO 中间件；如果仍需要同时启动 MinIO：

# .env
BYCLAW_DEPLOY_STORAGE=nfs
BYCLAW_DEPLOY_START_MINIO=true

5.5 上传接口兼容策略

BYCLAW_SANDBOX_VOLUME_BACKEND=file 只控制 OpenClaw 容器运行态 /by。 现有上传、下载、预览接口通过 FileIngressService 和 ObjectStorageRouter 统一接入， 因此可以单独选择继续走 MinIO，或切到服务器文件型存储。

推荐混合模式

FILE_STORAGE_TYPE=minio
BYCLAW_SANDBOX_VOLUME_BACKEND=file

上传接口继续使用 MinIO；OpenClaw /by 使用 NFS。适合第一阶段升级，风险最低。

全文件型模式

FILE_STORAGE_TYPE=file
FILE_STORAGE_LOCAL_PATH=/mnt/byclaw-file
BYCLAW_SANDBOX_VOLUME_BACKEND=file

上传接口也写入服务器挂载文件系统。后端把 file 作为 local 文件系统实现的配置别名。

切换边界： FILE_STORAGE_TYPE 会同时影响上传和后续下载/预览读取。 切到 file 前，请先把仍需访问的 MinIO 对象迁移到 FILE_STORAGE_LOCAL_PATH 对应目录； 灰度期建议保持 FILE_STORAGE_TYPE=minio，只先切 OpenClaw /by。

5.6 BE 配置与启动参数说明

ByClaw BE 不负责执行 mount -t nfs4。NFS 必须先由操作系统挂载到宿主机 /mnt/byclaw-file，BE 只通过配置判断运行态卷和文件 CRUD 应该走哪一种后端。

参数 推荐值 决定什么
BYCLAW_SANDBOX_VOLUME_BACKEND file OpenClaw 容器 /by 使用文件型运行态卷，不再使用 MinIO/rclone。
BYCLAW_SANDBOX_FILE_VOLUME_ROOT /mnt/byclaw-file openSandbox 解释 PRIVATE volume 的宿主机根路径。这个路径必须已经是 NFS 挂载点。
BYCLAW_SANDBOX_FILE_VOLUME_TYPE nfs 声明文件型卷类型，用于配置收口、诊断日志和 openSandbox TOML，不会自动执行 NFS mount。
FILE_STORAGE_MINIO_MOUNT_ENABLED false 关闭 legacy rclone mount。只有 backend=minio-mount 且这里为 true 才会执行 rclone。
FILE_STORAGE_TYPE file 或 minio 控制 BE 上传接口、UserFS/ResourceFS CRUD、文件列表读写使用哪个存储后端。
FILE_STORAGE_LOCAL_PATH /mnt/byclaw-file FILE_STORAGE_TYPE=file 时，BE 文件 CRUD 写入的服务器文件根目录。

如果使用环境变量启动 BE，完整 NFS 文件型模式示例：

export BYCLAW_SANDBOX_VOLUME_BACKEND=file
export BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-file
export BYCLAW_SANDBOX_FILE_VOLUME_TYPE=nfs
export BYCLAW_SANDBOX_FILE_VOLUME_SNAPSHOT_PROVIDER=nas
export FILE_STORAGE_MINIO_MOUNT_ENABLED=false
export FILE_STORAGE_TYPE=file
export FILE_STORAGE_LOCAL_PATH=/mnt/byclaw-file

java -jar byclaw-be.jar

如果使用命令行参数启动 BE，等价写法：

java -jar byclaw-be.jar \
  --byclaw.sandbox.volume.backend=file \
  --byclaw.sandbox.volume.file-root=/mnt/byclaw-file \
  --byclaw.sandbox.volume.file-type=nfs \
  --byclaw.sandbox.volume.snapshot-provider=nas \
  --file.storage.minio.mount.enabled=false \
  --file.storage.type=file \
  --file.storage.local.path=/mnt/byclaw-file
什么时候才算“使用 NFS”：
  • 宿主机上 findmnt /mnt/byclaw-file 能看到 NFS 挂载。
  • BYCLAW_SANDBOX_VOLUME_BACKEND=file，且 BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-file。
  • openSandbox TOML 中 [docker.private_volume] 的 backend="file"、file_root="/mnt/byclaw-file"。
  • 如果 BE 文件 CRUD 也要读写 NFS，必须再设置 FILE_STORAGE_TYPE=file 和 FILE_STORAGE_LOCAL_PATH=/mnt/byclaw-file。
  • 如果 BE 运行在 Docker 容器中，BE 容器也必须挂载同一个宿主机路径 /mnt/byclaw-file:/mnt/byclaw-file。

standalone Docker Compose 中 BE 服务需要包含这个 volume：

services:
  be:
    volumes:
      - ${BYCLAW_SANDBOX_FILE_VOLUME_ROOT:-/mnt/byclaw-file}:${BYCLAW_SANDBOX_FILE_VOLUME_ROOT:-/mnt/byclaw-file}

5.7 用户 private 目录是否会自动创建

BE 进程启动时不会为所有历史用户批量创建 NFS private 目录。新增或注册用户时， UserBucketProvisioningService 会沿用 MinIO 时代的用户空间初始化链路： FILE_STORAGE_TYPE=minio 时创建用户 bucket， FILE_STORAGE_TYPE=file 或 local 时创建 /mnt/byclaw-file/byclaw-${USER_CODE}/by。

时机 当前行为 建议
BE 进程启动 只做配置校验和日志提示，不批量创建所有历史用户目录。 启动前确认 /mnt/byclaw-file 已挂载且可写；历史用户通过迁移脚本补齐。
新增或注册用户 FILE_STORAGE_TYPE=file/local 时创建 byclaw-${USER_CODE}/by；minio 时创建用户 bucket。 新增用户可以直接获得独立 private 目录。
迁移旧数据 迁移步骤会显式创建 /mnt/byclaw-file/byclaw-${USER_CODE}/by。 这是最稳的灰度迁移方式。
启动 OpenClaw 沙箱 最终 bind 源路径由 openSandbox 服务端按 file_root + subPath 解释。是否自动 mkdir -p 取决于 openSandbox 镜像实现。 为避免镜像差异，建议启动前显式创建目录。
BE UserFS 写文件，且 FILE_STORAGE_TYPE=file LocalStorageService.put 会创建目标文件父目录。 适合 CRUD 写入时自动补齐 .openclaw、.sessions 等子目录。

历史用户迁移或手工补偿时，可以显式准备用户 private 目录：

export USER_CODE=user001
sudo mkdir -p "/mnt/byclaw-file/byclaw-${USER_CODE}/by"
sudo chown -R root:root "/mnt/byclaw-file/byclaw-${USER_CODE}"
sudo chmod -R 755 "/mnt/byclaw-file/byclaw-${USER_CODE}"

5.8 既有文件系统 CRUD 接口兼容性

既有文件系统 CRUD 主要通过 UserFS、ResourceFS、ObjectStorageRouter 进入底层存储。代码已经支持 FILE_STORAGE_TYPE=file，并把它路由到服务器挂载文件系统实现。

接口/能力 FILE_STORAGE_TYPE=minio FILE_STORAGE_TYPE=file
上传/下载/预览接口 继续读写 MinIO。 读写 FILE_STORAGE_LOCAL_PATH 下的文件。
UserFS.write/read/list/delete 读写用户 MinIO bucket。 读写 NFS 目录，例如 /mnt/byclaw-file/byclaw-user001/by/.sessions/...。
ResourceFS.write/read/list/delete 读写 MinIO 公共资源 bucket。 读写本地挂载文件根下的公共资源目录。
OpenClaw 容器生成文件 如果 BYCLAW_SANDBOX_VOLUME_BACKEND=file，仍写入 NFS /by。 同样写入 NFS /by。
BE 文件列表接口，如 qryByClawFileByUserCode 通过 UserFS.list 看 MinIO，不会自动看到 NFS 里的新产物。 通过 UserFS.list 看 NFS，可以看到 OpenClaw 写入 /by 的文件。
配置选择建议：
  • 只想先解决 OpenClaw 运行态稳定性：BYCLAW_SANDBOX_VOLUME_BACKEND=file，FILE_STORAGE_TYPE=minio。
  • 希望 BE 文件 CRUD、文件列表和 OpenClaw /by 看到同一份 NFS 文件：同时设置 BYCLAW_SANDBOX_VOLUME_BACKEND=file 和 FILE_STORAGE_TYPE=file。
  • BE 如果以 Docker 方式运行，需要把 NFS 挂载点也 bind 到 BE 容器，否则用户目录 provisioning 和 CRUD 访问不到宿主机 NFS。
  • 切到 FILE_STORAGE_TYPE=file 前，需要把旧 MinIO 中仍需访问的对象迁移到 FILE_STORAGE_LOCAL_PATH 对应目录。

路径映射示例：

# UserFS 外部路径
/.sessions/10014538/result.txt

# UserFS 内部路径
/by/.sessions/10014538/result.txt

# NFS 物理路径
/mnt/byclaw-file/byclaw-user001/by/.sessions/10014538/result.txt

# A 服务器实际目录
/exports/byclaw/byclaw-user001/by/.sessions/10014538/result.txt

6. 代码接入点

位置 职责 升级后行为
SandboxProperties.VolumeConfig 运行态卷配置模型 读取 backend/fileRoot/fileType/snapshotProvider/fileBrowserEnabled。
SandboxVolumeBackendValidator 启动校验 backend=file 时校验 fileRoot 是绝对路径；当前部署文档按 fileType=nfs 落地。
InitMinioBucketMountRunner MinIO bucket 初始化 backend=file 时仍初始化 MinIO 对象桶，但不把 MinIO 当运行态卷。
MinioBucketMountSupport legacy rclone mount 仅 backend=minio-mount 且 FILE_STORAGE_MINIO_MOUNT_ENABLED=true 时执行。
GenericSandboxSpecProcessor 构造沙箱 volume 保持 subPath=byclaw-${user_code}/by 和 mountPath=/by 不变。
SandboxRuntimeRequestFactory 构造 openSandbox payload 不扩展 hostPath API，仍由 openSandbox 服务端解释 PRIVATE volume 根。
UserBucketProvisioningService 新增/注册用户后的用户空间初始化 minio 创建用户 bucket；file/local 创建 byclaw-${USER_CODE}/by。
FileStorageUserSpaceProvisioner 文件型用户 private 目录创建 在 FILE_STORAGE_LOCAL_PATH 下创建隔离目录，并校验绝对路径和路径穿越。
LocalStorageService 上传接口的本地/挂载文件系统实现 FILE_STORAGE_TYPE=file 时写入 FILE_STORAGE_LOCAL_PATH。
StorageType / FileIngressBackendRegistry 文件型上传后端路由 把部署配置 file 兼容为本地文件系统实现，业务上传接口无需改代码。

关键不变量

  • OpenClaw 容器内路径永远是 /by。
  • 用户目录结构保持 byclaw-${USER_CODE}/by。
  • MinIO 继续通过 SDK/对象接口承载上传、下载、归档、共享。
  • 如果上传接口也要落到文件型存储，切换 FILE_STORAGE_TYPE=file 和 FILE_STORAGE_LOCAL_PATH。
  • 新运行态文件系统不再走 rclone、s3fs、goofys 或 FUSE 对象存储模拟。

7. 从 MinIO/rclone 迁移数据

迁移按用户分批进行。每个用户迁移前先停止该用户 OpenClaw 沙箱，避免旧目录继续写。

7.1 准备变量

export USER_CODE=user001
export BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-file

7.2 创建目标目录

sudo mkdir -p "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by"
sudo chown -R root:root "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}"
sudo chmod -R 755 "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}"

7.3 用 mc mirror 同步

mc alias set oldminio http://MINIO_HOST:MINIO_PORT ACCESS_KEY SECRET_KEY

mc mirror --overwrite \
  "oldminio/byclaw-${USER_CODE}/by" \
  "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by"

7.4 可选 rsync

如果旧 rclone 挂载仍健康，也可以从旧挂载目录同步。

export FILE_STORAGE_MINIO_MOUNT_PATH=/data/8080

rsync -aH --info=progress2 \
  "${FILE_STORAGE_MINIO_MOUNT_PATH}/byclaw-${USER_CODE}/by/" \
  "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by/"

7.5 校验

mc find "oldminio/byclaw-${USER_CODE}/by" --type f | wc -l
find "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by" -type f | wc -l

ls -la "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by/.openclaw" || true
ls -la "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by/.sessions" || true
ls -la "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by/output" || true

9. 回滚方案

灰度期不要删除旧 MinIO 数据。如果新文件型卷异常，可以临时切回 legacy rclone。

BYCLAW_SANDBOX_VOLUME_BACKEND=minio-mount
FILE_STORAGE_MINIO_MOUNT_ENABLED=true
FILE_STORAGE_MINIO_MOUNT_PATH=/data/8080

如果新文件型卷已有增量文件，先反向归档到 MinIO。

mc mirror --overwrite \
  "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${USER_CODE}/by" \
  "oldminio/byclaw-${USER_CODE}/by"

重生成 openSandbox 配置并重启：

cd deploy/middleware
sh gen-opensandbox-config.sh
docker compose up -d opensandbox-server
