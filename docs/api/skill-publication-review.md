# 个人技能上架企业审核

个人技能的“上架到企业”提交独立企业快照，状态为审核中（4）。申请进入资源中心审核中心，申请类型为“技能上架”。仅 adminvip 和平台管理角色可审核，资源管理授权、组织管理和平台运营角色不提供该审核权限。

审核通过后快照上架（2）；驳回后保持不可用（5）。重复提交待审核技能复用已有副本，不重复创建申请；驳回后再次提交按个人技能当前内容创建新快照及审核记录。个人源技能不变，历史记录保留审核人及时间。

企业技能统一使用 `原名_企业`，不再追加 `(企业)`；该后缀不随界面语言变化。展示名、ZIP 文件名（去掉 `.zip`）和包内根 `SKILL.md` 的 `name` 必须一致，例如 `report_企业.zip` 对应 `name: report_企业`。原名和发布人中的非法字符统一替换为下划线，连续分隔符合并为一个下划线，去掉首尾分隔符；合法的 Unicode 字母、数字和单个连字符、下划线保留。例如 `销售 分析（日报）` 发布为 `销售_分析_日报_企业`。归一化后的企业名称已存在时使用 `原名_发布人_企业`，仍重名则追加来源资源 ID 和必要的序号；个人原包、脚本和其他包内文件保持不变。数字员工自身的展示名称规则不受此变更影响。

Harness 的 ByClaw 加载器、原生技能注册与 `skill` 工具、`/技能名` 调用统一支持 Unicode 字母、数字，以及分隔用的 `-`、`_`，因此可以保留中文企业后缀；路径分隔符、空格、括号和标签字符仍不属于技能标识符。若替换后没有任何字母或数字，接口会提示修改名称，不上传文件、不创建企业副本或审核申请。OpenClaw 沿用包名与包内名称一致的安装约定，并按包内名称进行技能过滤。发布服务与 Harness 业务镜像需要一起更新；旧企业副本不会被本次代码修改自动改名或重打包。

数字员工发布时复制的个人技能也使用相同规则；若企业已存在同名技能，副本名称追加申请 ID、来源技能 ID 和必要序号。审核时仍先核对冻结原包的哈希，再仅替换企业副本根 `SKILL.md` 的名称，保存副本自身哈希及 `sourcePackageHash`，重试不能绕过原包或副本完整性检查。员工发布的技能仍是只读快照，不能直接下架或编辑，需通过员工发布流程更新。

直接新建企业技能（ZIP 导入以及员工工作区同步到企业资源中心）只允许 `adminvip` 或平台管理角色；预检与实际导入使用同一规则。个人导入、普通用户提交发布审核、持有管理权限的既有资源更新，以及具备同步主体权限的 Whale 资源同步保留各自规则。商用版前端也按后端返回的企业技能导入能力展示入口。

`POST /byaiService/tool/publishSkillToEnterprise` 接收 `resourceId`，返回企业快照 `resource`、是否复用 `alreadyExists` 和 `personalDependencies`（资源 ID、名称、业务类型）。有效显式关联中的个人数字员工、知识和工具只触发提醒，不阻断提交；企业出向关联保留，沿用既有权限。不会解析技能文件正文中的非结构化资源引用。

上架申请复用 `au_privilege_grant`，以 `grant_type=SKILL_PUBLICATION` 区分使用权限申请，状态沿用 `P`（待审核）、`X`（通过）、`R`（驳回），申请人和审核人沿用现有字段。该类型不产生有效使用或管理授权。

通过、驳回复用现有 `approveUseApply` / `rejectUseApply` 接口，接收 `resourceId`、`applyUserId`，上架申请额外传 `auditType=SKILL_PUBLICATION`。不传类型保持原使用审核行为。服务端重新校验上架审核角色、当前企业及待审核状态，在同一事务内更新资源和申请记录；上架通过不执行使用授权逻辑。

审核中心原聚合查询返回 `auditType=SKILL_PUBLICATION`，申请 ID 沿用 `privilegeGrantId`，与使用权限申请区分。待审核数量沿用同一聚合查询。

本功能复用现有表和字段，不新增表、不需要数据库迁移。
