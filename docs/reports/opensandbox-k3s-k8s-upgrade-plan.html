ByClaw OpenSandbox K3s 分布式升级方案

将沙箱从 Docker 单机迁移到 k3s HA 集群。ByClaw API 不变，OpenSandbox runtime 切换为 kubernetes；存储默认使用 Longhorn 分布式 RWX PVC（不依赖 NFS），彻底弃用 minio-mount/rclone；部署与现有 deploy.sh 同风格的一键脚本。

已落地 deploy/k3s/ · scripts/deploy-k3s.sh · 生成日期 2026-06-11

1. 结论

推荐路径：3 台 server+worker HA k3s → Namespace 三分（by-service / by-middleware / by-sandbox）→ Longhorn 分布式 RWX PVC（deploy/k3s/install-longhorn.sh）→ OpenSandbox runtime.type=kubernetes + gateway Ingress → Prometheus/HPA/KEDA 扩缩容 + Alertmanager webhook 通知。与现状 Docker+MinIO 的全面对比见 第 2 节。
能力状态说明
分布式沙箱 Pod满足OpenSandbox BatchSandbox CRD 调度到多 worker
统一 Ingress满足wildcard host 或 path-prefix，见第 9 节
Longhorn 工作区满足3 副本 RWX PVC + subPath，弃用 NFS/minio-mount
动态配额满足gen-resource-quota.sh 按节点 allocatable 计算
监控扩缩容满足Prometheus + HPA/KEDA + webhook 告警
一键脚本已落地deploy/k3s/deploy.sh init|update|stop

2.2 存储与用户文件流（核心差异）

现状痛点：用户工作区经 minio-mount + rclone 以 FUSE 方式挂进沙箱，对象存储语义与 POSIX 文件操作（rename、锁、小文件）不匹配；BE 经 S3 API 写桶，沙箱经 FUSE 读，链路长、故障点多。
升级思路：用户私有目录统一为共享 POSIX 卷上的 byclaw-{user}/by/；BE 与沙箱看同一份数据，MinIO 从沙箱工作区链路退出（系统级附件可另议）。
维度Docker + MinIO（BYCLAW_DEPLOY_STORAGE=minio）K3s + Longhorn（BYCLAW_DEPLOY_STORAGE=longhorn）
存储 profiledeploy/storage-profile.sh → FILE_STORAGE_TYPE=minioenv.k3s → FILE_STORAGE_TYPE=file
沙箱卷后端BYCLAW_SANDBOX_VOLUME_BACKEND=minio-mountBYCLAW_SANDBOX_VOLUME_BACKEND=file
MinIO 角色用户桶 byclaw-{user} 存对象；启动时 InitMinioBucketMountRunner 初始化沙箱工作区不依赖 MinIO；可选保留给图标/会话等非 /by 附件
沙箱 /by 实现OpenSandbox [docker.private_volume] → 宿主机执行 rclone mount :s3:{bucket}BatchSandbox PVC + subPath: byclaw-{user}/by → 容器 /by

6. 存储：Longhorn 分布式 PVC，弃用 NFS / minio-mount / rclone

原则：沙箱工作区使用 Longhorn ReadWriteMany PVC（storageClassName: longhorn）；FILE_STORAGE_MINIO_MOUNT_ENABLED=false；不再部署外部 NFS。pip/FFmpeg 临时目录仍用 emptyDir。
图 4：存储分层
场景存储原因
OpenClaw /by 工作区Longhorn PVC RWX3 副本跨节点调度、FileBrowser 上传下载
pip install 依赖emptyDir scratch大量小文件不走 RWX 层，完成后同步到 /by
FFmpeg 转码emptyDir scratch顺序大文件写本地 NVMe，完成后 mv 到 PVC
中间件数据盘Longhorn RWOopenGauss 等 StatefulSet 使用 longhorn RWO

BE 侧 volume payload 只传 subPath/scope/mountPath（SandboxRuntimeRequestFactory），K8s 模板用 PVC 承接，无需改 Java 代码。

6.1 Longhorn 分布式存储方案（默认）

定位：在 3 台 k3s 节点 /data/longhorn NVMe 上部署 Longhorn，沙箱工作区 PVC 使用集群内 3 副本块存储 + RWX share-manager。一键脚本：deploy/k3s/install-longhorn.sh，deploy/k3s/deploy.sh init 默认自动执行（BYCLAW_K3S_INSTALL_LONGHORN=true）。

6.1.1 为什么 ByClaw 适合 Longhorn

负载特征NFS 痛点Longhorn 做法
OpenClaw /by 工作区（跨节点）NFS Server 单点；故障影响全集群挂载卷副本分布在 node-1/2/3，任一节点故障仍可调度（需≥2 副本）
pip 依赖（大量小文件）NFS 元数据操作延迟高工作区仍用 RWX PVC；pip 缓存目录挂 emptyDir 本地 NVMe，装完 rsync 回工作区
FFmpeg 大文件转码并发写锁竞争转码输出写 emptyDir scratch，完成后移动至 Longhorn PVC
FileBrowser 上传下载需 RWX + POSIX renameLonghorn RWX 经 NFS-ganesha share-manager 暴露，语义满足 FileBrowser
3×984G 数据盘外部 NAS 需另购直接消费节点 /data，Longhorn 默认路径 /var/lib/longhorn 建议改到 /data/longhorn

6.1.3 部署与配置要点

# 2. 将默认数据路径改到 /data（避免根分区 40G 爆满）
# Longhorn UI → Settings → Default Data Path = /data/longhorn

# 3. 创建 RWX StorageClass（Longhorn UI 或 CRD 启用 accessMode RWX）
# env.k3s 中：

# 4. 更新 BatchSandbox 模板 claimName，scratch 仍用 emptyDir
# deploy/k3s/manifests/sandbox/batchsandbox-template.yaml

# 5. 从 NFS 迁移数据（维护窗口）
kubectl -n by-sandbox run rsync-migrate --rm -it --image=alpine \
  --overrides='...' -- sh -c \
  "apk add rsync && rsync -av /nfs-src/ /lh-dst/"
配置项推荐值（3 节点）说明
Number of Replicas3与节点数一致，允许挂掉 1 台仍可读
Data Localitybest-effort尽量在 Pod 所在节点放一份副本，降低网络 IO
Storage Reserved≥ 250GiB/节点为 containerd、kubelet、镜像缓存预留，与文档 11 节一致

6.1.4 与 ByClaw 现有代码的衔接（BE 私有目录 ↔ Longhorn）

BE 为每个用户维护私有工作区，路径约定与 Longhorn PVC subPath 天然对齐，无需改 Java 业务代码；只需让 BE Pod 与沙箱 Pod 共享同一 PVC 目录树。

Longhorn PVC 根 (byclaw-workspace，挂载于 BE /mnt/byclaw-workspace)
└── byclaw-{userCode}/by/          ← 沙箱 subPath 挂载到容器 /by
    └── .openclaw/openclaw.json    ← BE UserFS 在创建沙箱前写入
层是否改动说明
UserBucketNameResolver否桶名 byclaw-{userCode}，与 spec subPath 前缀一致
ByclawUserFS + LocalStorageService否逻辑根 /by → 物理路径 {FILE_STORAGE_LOCAL_PATH}/byclaw-{user}/by/...，写时 createDirectories 自动建目录
SandboxWorkspaceBootstrapInitializer否创建沙箱前经 UserFS 写 /.openclaw/openclaw.json 等到同一目录树
GenericSandboxSpecProcessor否渲染 subPath: byclaw-${user_code}/by、mountPath: /by、scope: PRIVATE
SandboxRuntimeRequestFactory否发给 OpenSandbox 的 payload 仅含 subPath/scope/mountPath（K8s runtime 用 PVC+subPath，忽略 host.path）
sandbox_service_spec volumes否迁移 SQL 已保留 subPath: byclaw-${user_code}/by
byclaw-be Deployment是（挂载）必须挂 byclaw-workspace PVC 到 /mnt/byclaw-workspace，否则 bootstrap/UserFS 与沙箱文件不一致
BYCLAW_SANDBOX_FILE_VOLUME_TYPE是（配置）填 bind（Pod 内 POSIX 路径），不是 longhorn——后者会被 SandboxVolumeBackendValidator 拒绝启动
OpenSandbox BatchSandbox 模板是（仅 PVC）claimName: byclaw-workspace，subPath: {{ workspace_subpath }} 由 API 注入
deploy/k3s/env.k3s是FILE_STORAGE_TYPE=file、FILE_STORAGE_LOCAL_PATH=/mnt/byclaw-workspace、BYCLAW_SANDBOX_VOLUME_BACKEND=file

6.1.5 分布式下 FILE_STORAGE_LOCAL_PATH 的处理逻辑

核心结论：FILE_STORAGE_LOCAL_PATH 在 BE 代码里表示当前 JVM 进程能直接读写的 POSIX 根目录，不是「某台物理机的本地盘」。分布式能力由 K8s 将同一块 Longhorn RWX PVC 挂进每个 BE / 沙箱 Pod 的同一路径 保证；BE Java 侧零 Longhorn 感知、零分布式存储客户端，只做 Path.of(basePath).resolve(...) 拼接。
两套配置、两个消费者

配置链（byclaw-be/config/application.properties）：

file.storage.type=${FILE_STORAGE_TYPE:minio}
file.storage.local.path=${FILE_STORAGE_LOCAL_PATH:${BYCLAW_SANDBOX_FILE_VOLUME_ROOT:/tmp/byclaw-storage}}
byclaw.sandbox.volume.file-root=${BYCLAW_SANDBOX_FILE_VOLUME_ROOT:}
配置项消费者K3s 分布式下的含义
FILE_STORAGE_LOCAL_PATHLocalStorageService、FileStorageUserSpaceProvisionerBE 所有文件 I/O 的物理根（Pod 内挂载点）
BYCLAW_SANDBOX_FILE_VOLUME_ROOTSandboxVolumeBackendValidator、spec hostPath 模板渲染启动校验 + Docker 时代 OpenSandbox 用；K8s runtime 忽略 host.path
BYCLAW_SANDBOX_FILE_VOLUME_TYPE仅启动校验 / 日志描述挂载类型（bind|nfs|smb|cephfs），不参与路径计算；Longhorn 场景填 bind
FILE_STORAGE_TYPE存储路由、用户空间初始化必须设为 file，否则 BE 仍走 MinIO/SFTP，不会调用 LocalStorageService

K3s 推荐三处对齐为同一路径：

FILE_STORAGE_TYPE=file
FILE_STORAGE_LOCAL_PATH=/mnt/byclaw-workspace
BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-workspace
BYCLAW_SANDBOX_FILE_VOLUME_TYPE=bind
BYCLAW_SANDBOX_VOLUME_BACKEND=file
BE 路径拼接算法（LocalStorageService.resolve）

BE 无 NFS/Longhorn 客户端，仅用 Java NIO Files.*：

物理路径 = FILE_STORAGE_LOCAL_PATH / byclaw-{userCode} / by / {相对路径}
场景逻辑路径（UserFS）物理路径示例（user=alice）
沙箱 bootstrap/.openclaw/openclaw.json/mnt/byclaw-workspace/byclaw-alice/by/.openclaw/openclaw.json
用户文件 API/by/docs/a.pdf/mnt/byclaw-workspace/byclaw-alice/by/docs/a.pdf
用户注册建目录—FileStorageUserSpaceProvisioner → mkdir .../byclaw-alice/by

Docker 单机 vs K3s 分布式对比
维度Docker 部署K3s + Longhorn

部署约束（运维侧，无需改 Java）
约束原因
BE Deployment 必须挂 byclaw-workspace PVC不挂则 BE 写容器 ephemeral 盘，沙箱读 Longhorn → 数据分裂
三处路径一致：FILE_STORAGE_LOCAL_PATH = BYCLAW_SANDBOX_FILE_VOLUME_ROOT = Pod volumeMount.mountPath保证 bootstrap、UserFS、校验器指向同一根
PVC 必须 ReadWriteManyBE 多副本 + 沙箱跨节点调度需多 Pod 同时挂载
FILE_STORAGE_TYPE=file激活 LocalStorageService 与用户目录 ensureUserSpace
系统附件（图标、会话临时文件等）与用户工作区分离；StorageCategory 桶映射可仍走 MinIO，与 /by 工作区无关
易错点：勿将 BYCLAW_SANDBOX_FILE_VOLUME_TYPE 设为 longhorn——Longhorn 是 StorageClass 名，对 BE 而言只是 Pod 内的 POSIX 挂载，应填 bind。勿把 FILE_STORAGE_LOCAL_PATH 理解成「绑定某 worker 节点本地目录」；在 K3s 下它始终是Pod 挂载命名空间内的共享卷根路径。

7. 动态 ResourceQuota（不写死）

deploy/k3s/gen-resource-quota.sh 读取 kubectl get nodes -o json 汇总 allocatable，按环境变量比例分配：

QUOTA_SYSTEM_RESERVE_PERCENT=15   # 系统预留
QUOTA_SANDBOX_PERCENT=70          # by-sandbox
QUOTA_MIDDLEWARE_PERCENT=10       # by-middleware
QUOTA_SERVICE_PERCENT=5           # by-service

./deploy/k3s/gen-resource-quota.sh deploy/k3s/env.k3s --dry-run
./deploy/k3s/gen-resource-quota.sh deploy/k3s/env.k3s --apply

输出 manifests/generated-resource-quota.yaml，含 sandbox 的 ResourceQuota + LimitRange（默认 request 1C/2Gi，limit 2C/4Gi）。三台 72C/276Gi 示例：sandbox 约 50C/193Gi requests。
