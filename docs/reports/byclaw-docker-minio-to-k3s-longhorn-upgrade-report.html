ByClaw 从单机 Docker + MinIO 升级到 K3s + Longhorn 架构改造汇报

本方案将 ByClaw 从“单机 Docker Compose + MinIO/rclone 沙箱挂载”升级为“三节点 K3s + Longhorn 分布式 PVC + OpenSandbox Kubernetes Runtime”。升级后，业务入口统一由主节点公网 IP 或域名的 80 端口承载，BE 通过 OpenSandbox API 创建沙箱，沙箱 Pod 使用 Longhorn 共享卷挂载用户工作区 /by，部署流程由 scripts/deploy-k3s.sh <env> init|update 统一编排。

报告范围：部署架构、存储架构、沙箱运行时、业务入口、一键部署、YAML 说明、FAQ。生成日期：2026-06-12。

目标架构：K3s + Longhorn OpenSandbox Kubernetes Runtime FE/BE/QA/Data 单 Pod 起步 生产建议 Longhorn 副本数 2 或 3

0. 汇报结论

升级前 Docker Compose 单机部署，OpenSandbox 挂 Docker Socket 创建本机容器，沙箱工作区依赖 MinIO + rclone/FUSE。
升级后 K3s 统一编排 FE、BE、中间件、OpenSandbox 与沙箱 Pod；Longhorn 提供共享工作区 PVC；Traefik/FE nginx 统一入口。
保留边界 ByClaw BE 调 OpenSandbox API 的业务模型不变，OpenClaw 仍使用 /by/.openclaw 作为用户状态目录。
3台 K3s 节点起步
4核心 Namespace：service、middleware、sandbox、monitoring
1共享工作区 PVC：byclaw-workspace
80主节点公网 IP 或域名统一访问端口

1. 为什么要升级

1.1 单机 Docker + MinIO 的主要瓶颈

问题旧架构表现对业务的影响
沙箱容量受限沙箱由单机 Docker 守护进程创建，CPU/内存/磁盘集中在一台机器并发用户增多后，沙箱启动慢、互相抢资源、故障半径大
存储链路复杂BE 写 MinIO，沙箱通过 rclone/FUSE 挂对象桶到 /by小文件、rename、锁、目录遍历性能不稳定，排障链路长
运行时耦合宿主机OpenSandbox 需要挂载 /var/run/docker.sock安全边界弱，容器逃逸风险和宿主机依赖更高
发布不可控服务、端口、卷、配置由 compose 和宿主机目录拼接更新后容易残留旧容器、旧配置、旧端口
可观测性不足主要依赖 docker logs 和宿主机脚本Pod 状态、事件、卷挂载失败、镜像拉取失败没有统一视图

1.2 升级目标

  • 把沙箱从单机 Docker 容器改为 K8s Pod，由调度器按节点资源自动分配。
  • 把用户工作区从 MinIO/rclone/FUSE 改为 Longhorn RWX PVC 的原生文件系统挂载。
  • 把 FE、BE、QA、Data、中间件、OpenSandbox 纳入同一套 YAML 渲染和一键部署流程。
  • 把外部访问统一到主节点公网 IP + 80 端口，同时保留域名和 wildcard sandbox 域名的扩展口子。
  • 提升部署可恢复性：可重复执行 update，自动清理坏 Pod，打印等待进度和失败原因。

5. Longhorn 如何解决存储卷的高性能、分布式和数据不丢

5.1 存储目标

升级后的核心目标是让 BE 和沙箱看见同一份用户工作区数据：BE 写入 /mnt/byclaw-workspace/byclaw-{user}/by，沙箱 Pod 挂载为 /by。Longhorn 提供的是 K8s 原生 PVC 能力，而不是对象存储模拟文件系统。

图 8：Longhorn 分布式卷读写路径
能力Longhorn 方案对 ByClaw 的价值
高性能用户工作区走块存储 + 文件系统挂载，去掉 MinIO S3 API 与 rclone/FUSE 中间层提升目录遍历、小文件读写、rename、日志写入等 POSIX 场景稳定性
分布式卷副本分布在多节点 /data/longhorn，Pod 可在任意满足调度条件的节点挂载沙箱不再被固定宿主机限制，支持水平扩容
数据不丢副本数生产建议 2 或 3；单节点故障时仍有其他副本可恢复用户 /by 工作区不会因为单节点盘故障立即丢失
RWX 共享ReadWriteMany PVC 支持 BE 与沙箱同时访问工作区BE 初始化配置后，沙箱启动即可看到 /.openclaw/openclaw.json
运维可观测CSI、PVC、PV、Volume、Replica、Events 均可查询卷挂载失败可定位到 CSINode、longhorn-csi-plugin、share-manager 或副本状态
副本数说明：当前联调环境可能为了快速验证设置 LONGHORN_REPLICA_COUNT=1。生产环境建议至少 2，三节点资源允许时建议 3。副本数越高，容灾越强，但写入放大会增加网络和磁盘负载。

5.2 与 MinIO/rclone 的差异

项目MinIO/rcloneLonghorn PVC
文件语义对象存储模拟目录，FUSE 层转译原生文件系统路径
故障点BE、MinIO、rclone、FUSE、OpenSandbox 卷驱动BE、K8s CSI、Longhorn 卷
写入路径BE PutObject，沙箱通过 FUSE 读BE 和沙箱都读写同一 PVC 子目录
扩容方式扩容 MinIO 或迁移桶扩容 PVC/Longhorn 卷并添加节点磁盘

6. 业务系统出口 Ingress 详细介绍

当前目标是“不依赖域名也能访问”：主节点公网 IP + 80 端口进入 Traefik，再转到 byclaw-fe。FE nginx 负责静态页面、后端 API、WebSocket、文件预览下载，以及沙箱 URI 模式代理。

图 9：公网入口与内部路由

6.1 Ingress YAML

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: byclaw
  namespace: by-service
  annotations:
    traefik.ingress.kubernetes.io/router.entrypoints: web
spec:
  ingressClassName: traefik
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: byclaw-fe
                port:
                  number: 80

6.2 FE nginx 对沙箱 URI 模式的代理

location ~ ^/v1/sandboxes/([^/]+)/([0-9]+)(/.*)?$ {
    rewrite ^/v1/sandboxes/([^/]+)/([0-9]+)(/.*)?$ /v1/sandboxes/$1/proxy/$2$3 break;
    proxy_pass http://opensandbox-server.by-sandbox.svc.cluster.local:9005;

    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
}

说明：当没有 wildcard 域名时，OpenSandbox endpoint 可统一返回 http://<master-ip>/v1/sandboxes/<id>/8080 这一类 URI，由 FE nginx rewrite 到 OpenSandbox 的 /proxy/{port}。

7.1 部署前检查

检查项要求说明
服务器3 台 Linux 节点1 台 server，2 台 agent 起步；也可三台都作为 server+worker，但需评估 etcd HA

7.3 首次部署

# 本地执行，脚本会上传 deploy/k3s 和 deploy/config 到远端
sh scripts/deploy-k3s.sh byclaw init

完整流程如下：

  1. 读取 envs/byclaw/env.k3s，确认 server/agent、镜像、Longhorn、DB/Redis、OpenSandbox 参数。
  2. 安装 K3s：server 使用 --cluster-init，agent 通过 K3S_JOIN_URL 加入。
  3. 同步 registry 配置，保证 containerd 能拉取业务镜像和 OpenSandbox 镜像。
  4. 安装 Longhorn，修正 K3S_KUBELET_ROOT 下 CSI 注册路径。
  5. 安装 OpenSandbox Controller Helm chart。
  6. 渲染 YAML 到 deploy/k3s/generated。
  7. 按顺序 apply：namespace → storage → middleware → schema SQL → sandbox → service → ingress → monitoring。
  8. 等待 by-middleware 和 by-service 中目标工作负载 Ready，打印 Pod 进度和失败事件。

7.4 更新部署

# 修改 env.k3s、镜像 tag 或 deploy/config 后执行
sh scripts/deploy-k3s.sh byclaw update

update 会同步 registry 配置、确保 Traefik 80 入口、重新渲染并 apply YAML、清理旧的异常 Pod，并按配置决定是否 rollout restart 业务工作负载。

9.4.1 为什么必须做规格分层

OpenClaw 沙箱不是单一负载。一个只做聊天和少量文件读写的会话，和一个启动 Chrome/VNC、跑网页自动化、处理大文件的会话，资源曲线完全不同。如果所有沙箱都按最高规格 2C / 4GiB 申请，集群调度会提前被 CPU request 填满，导致大量资源被“预留但未实际使用”；如果全部按最低规格申请，又会让浏览器型和重任务型沙箱更容易 OOM 或被 CPU throttle。因此要把沙箱分层，让资源申请和真实任务形态匹配。

不分层的问题表现后果
全部按最高规格每个沙箱都申请 2C / 4GiB现有 3 节点只能调度二十多个沙箱，资源利用率低。
全部按最低规格每个沙箱只申请 0.25C / 765MiB普通聊天可以跑，但浏览器、VNC、大文件任务容易被压垮。
没有任务准入用户任意启动高消耗能力少量重任务会影响大量普通会话，节点负载不可预测。
没有节点池隔离所有沙箱混跑在 general 节点Chrome、FFmpeg 等任务会挤占 BE、FE、普通沙箱资源。

9.4.4 容量换算公式

容量测算建议按 request 计算稳定调度上限，再用实际 p95 使用率校正：

可用于沙箱的 CPU = 集群 allocatable CPU - 平台基础 request - 安全余量
可用于沙箱的内存 = 集群 allocatable memory - 平台基础 request - 安全余量

CPU 维度可承载沙箱数 = 可用于沙箱的 CPU / 单沙箱 CPU request
内存维度可承载沙箱数 = 可用于沙箱的内存 / 单沙箱 memory request

最终建议并发沙箱数 = min(CPU 维度, 内存维度) * 稳定系数
稳定系数建议取 0.75 - 0.85

以当前三节点为例，集群 allocatable 约 68C / 267GiB。扣除平台基础、Longhorn、中间件、业务服务和安全余量后，按约 45C 作为稳定沙箱 CPU 水位估算：

规格CPU 口径估算并发解释
最小型45C / 0.25C约 160-180CPU 可覆盖，内存也基本够，但要监控 p95 内存。
经济型45C / 0.5C约 85-100适合当前集群作为默认容量口径。
标准型45C / 1C约 45-55适合更稳妥的生产体验。
上限型45C / 2C约 22-28浏览器/重任务专用，不适合作为全量默认。

9.4.5 落地到 OpenSandbox 模板的方式

当前 BatchSandbox 模板支持通过变量渲染资源规格：

resources:
  requests:
    cpu: "{{ cpu_request | default('1') }}"
    memory: "{{ memory_request | default('2Gi') }}"
  limits:
    cpu: "{{ cpu_limit | default('2') }}"
    memory: "{{ memory_limit | default('4Gi') }}"

建议后续在 BE 创建沙箱时，根据用户套餐、任务类型、是否启用浏览器、是否长任务，写入对应的 cpu_request、memory_request、cpu_limit、memory_limit 和目标节点池。这样普通用户默认走经济型，高消耗任务才申请上限型。

9.4.6 推荐默认值

当前阶段建议：100 用户以内，默认用经济型 0.5C / 1GiB；对体验敏感或工具调用复杂的用户使用标准型 1C / 2GiB；只有浏览器/VNC/重任务申请上限型 2C / 4GiB。最小型 0.25C / 765MiB 可以用于高密度轻量会话，但必须配合监控验证 OOM 和响应延迟。

10. FAQ

Q1：为什么不继续使用 MinIO 做沙箱工作区？

MinIO 是对象存储，适合附件、归档、静态资源，不适合高频 POSIX 文件系统场景。OpenClaw 在 /by 下会写配置、日志、workspace、插件缓存，rclone/FUSE 会引入语义和性能不确定性。Longhorn PVC 更贴近应用真实文件系统需求。

Q2：openclaw_sandbox.sql 里的 hostPath 是否控制 K8s 挂载？

当前 BE 会解析该字段，但最终发给 OpenSandbox 的 volume payload 不包含 Kubernetes hostPath/PVC 语义。实际 K8s 挂载由 BatchSandbox 模板中的 PVC + subPathExpr 决定。因此该字段应理解为兼容旧规格和目录语义，不应当把它当作真实 K8s hostPath 控制面。

Q3：业务服务为什么当前每个只启 1 个 Pod？

当前目标是先完成稳定迁移和状态链路验证。FE/BE/QA/Data 都按 1 个副本部署，降低数据库连接、会话、文件写入并发语义的迁移风险。后续确认无状态边界后，可逐步提高副本数。

Q4：沙箱 Pod 是随机分配到三台 K3s 节点吗？

不是纯随机，而是由 Kubernetes scheduler 按资源、节点状态、nodeSelector、污点容忍等条件调度。当前模板有 nodeSelector: byclaw.io/node-pool=sandbox-general，所以只会调度到带该标签的节点。

Q5：没有域名时怎么访问沙箱服务？

使用 URI 模式：OpenSandbox endpoint 返回主节点公网 IP + /v1/sandboxes/{id}/{port}，FE nginx 将该路径 rewrite 到 OpenSandbox /proxy/{port}。有域名后，可切到 wildcard 模式：{sandboxId}-{port}.sandbox.example.com。

Q6：Longhorn 副本数设置为 1 会不会丢数据？

副本数 1 只能用于联调或资源不足场景，不具备节点级容灾。生产建议 2 或 3。三副本可以承受单节点故障，代价是写放大和网络复制成本更高。

Q7：执行 update 会清理之前错误的 Pod 吗？

会。当前脚本会清理 ErrImagePull、ImagePullBackOff、CrashLoopBackOff、CreateContainerConfigError 等异常 Pod，并重新 apply 最新 YAML。

Q8：数据库 SQL 初始化在哪里执行？

deploy/k3s/deploy.sh 的 ensure_opengauss_schema 会在中间件 Ready 后检查 byai.byai_system_config 是否存在，不存在则依次执行 deploy/middleware/initdb/01_init.sql 到 04_dml.sql。
