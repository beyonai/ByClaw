OpenClaw 沙箱规格分层与动态扩缩容方案

本文面向 ByClaw 从单机 Docker + MinIO 升级到 k3s + Longhorn + OpenSandbox 之后的沙箱资源治理。目标是：默认给用户低成本的 openclaw-xs，再根据真实使用情况自动升级、降级、预热与释放，同时避免有状态沙箱被普通 HPA 误扩容。

生成日期：2026-06-12 · 范围：OpenClaw 沙箱 Pod、OpenSandbox 控制面、ByClaw BE 调度策略、Prometheus/Grafana 监控指标

默认 XS 最高 2C/4Gi Longhorn 工作区 有状态 Pod 不直接 HPA

0. 结论

结论：默认给所有用户分配 openclaw-xs 是合理的；可以根据用户实际 CPU、内存、会话活跃度、任务类型进行动态规格调整。但不建议把单个 OpenClaw 沙箱 Pod 当普通 Deployment 做 HPA 横向扩容。推荐采用“按用户创建/释放 + 规格分层 + 热切换升级 + 空闲释放 + 下次启动降级”的组合策略。
问题建议答案原因
默认是否都给 openclaw-xs 是，作为默认起步规格 降低常态资源占用，让集群容量跟真实活跃度匹配。
能否按用户使用情况实时扩容 可以，但要分实现层级 最稳的是“新建更大规格沙箱并切流”；原地 resize 依赖 Kubernetes/OpenSandbox 能力。
能否从 XS 自动升到 S/M/L 可以 Prometheus 识别用户沙箱连续资源压力，BE 更新用户规格策略并触发升级。
能否自动降回 XS 可以，但不建议运行中频繁降级 内存下降可能带来风险。建议低负载持续一段时间后，下次启动降级或空闲后释放。
是否使用 HPA 扩单个沙箱 不建议 OpenClaw 沙箱包含浏览器、工作目录、gateway token 和会话状态，复制多个 Pod 会造成状态不一致。
0.25C/768Mi建议最小请求
2C/4Gi单沙箱最高上限
1 Pod/用户活跃沙箱基本模型
30 min建议默认空闲释放窗口

1. 当前实现基础

当前 BE 已经具备通过 sandbox_service_spec 驱动 OpenSandbox 创建沙箱的基础能力。关键链路如下：

模块现状对规格分层的意义
SandboxService 负责按用户、资源、serviceKey 启动或复用沙箱。 可以在这里接入用户默认规格、升级策略、释放策略。
launchSandboxWithServiceKey 支持显式传入 serviceKey。 可以用 openclaw-xs/s/m/l 实现规格分层。
SandboxServiceSpec 已有 resourceLimits 字段。 可以直接下发 CPU/内存 limits；还需要补 resourceRequests。
GenericSandboxSpecProcessor 从 DB spec 生成 CreateSandboxRequest。 适合扩展 requests、nodePool、priorityClass 等调度字段。
OpenSandboxRuntimeProvider 调用 OpenSandbox API 创建沙箱。 后续需要增加 resize / replace / migrate 接口封装。
Prometheus/Grafana 已部署并采集 Pod、节点、Namespace 资源指标。 可作为用户规格调整的事实来源。

2. 沙箱规格分层

沙箱规格分层的核心原则是：requests 用于调度和容量核算，limits 用于限制单用户峰值。用户提到的边界“最小 0.25C/765MB，最高允许 2C/4Gi”应固化为平台策略。

2.1 推荐规格表

serviceKey定位requestslimits适用用户/场景调度池
openclaw-xs 默认起步规格 250m / 768Mi 1C / 2Gi 普通聊天、轻量 Agent、首次登录、低活跃用户 sandbox-general
openclaw-s 标准规格 500m / 1Gi 1.5C / 3Gi 普通持续使用、轻量浏览器、文件浏览 sandbox-general
openclaw-m 增强规格 1C / 2Gi 2C / 4Gi 浏览器/VNC、数据处理、长任务、多工具调用 sandbox-browser 或 sandbox-heavy
openclaw-l 重任务规格 1.5C / 3Gi 2C / 4Gi 高价值用户、管理员、批处理任务、长时运行任务 sandbox-heavy
注意：openclaw-l 的 limits 仍然不超过 2C/4Gi，只是提高 requests，让调度器为它预留更稳定的资源。这样可以防止重任务被挤在资源很紧的节点上。

2.2 限额边界

边界建议值说明
单沙箱最小 requests250m / 768Mi低于该值 Chrome、Node、OpenClaw gateway 更容易抖动。
单沙箱最大 limits2C / 4Gi避免单用户拖垮节点。
单用户同时沙箱数1 默认，管理员可放宽OpenClaw 当前更适合一人一活跃工作区。
Namespace 总沙箱数按节点 allocatable 动态计算继续使用现有 gen-resource-quota.sh 思路。
空闲释放30min 默认可对 XS/S 设置 30 分钟，M/L 设置 15 到 30 分钟。

3. 默认 XS 与动态升降级

3.1 默认 XS 后，能否按用户使用情况实时动态扩缩容？

可以做，但要分三类能力：第一类是“下次启动动态选规格”，当前最稳；第二类是“热切换升级”，当前可实现且风险可控；第三类是“运行中原地 resize”，需要 Kubernetes 版本、OpenSandbox API 和 Pod 权限都满足。
能力层级是否推荐是否中断当前会话实现难度说明
下次启动动态选规格 第一阶段推荐 不中断当前会话 低 当前 Pod 继续跑；BE 根据近期指标更新用户 preferred tier；下次创建沙箱时使用 S/M/L。
热切换升级 第二阶段推荐 轻微影响，文件不丢 中 创建更大规格新 Pod，挂载同一 Longhorn 用户目录，ready 后切 endpoint/token，再释放旧 Pod。
运行中原地 resize 增强能力 理论上不中断 中高 Kubernetes 官方已提供运行中调整容器 CPU/内存的能力，但需要集群版本、OpenSandbox 支持 resize 或 BE 具备 Kubernetes resize 权限。
HPA 复制沙箱 Pod 不推荐 状态不一致 中 复制多个 OpenClaw Pod 会造成浏览器会话、工作目录写入、gateway token、长连接路由混乱。

3.2 推荐动态策略

建议把动态调整拆成升级快、降级慢：

动作触发条件处理方式冷却窗口
XS → S CPU 使用率连续 5 分钟 > 75%，或内存 working set > 70%，或启动 Chrome 后明显接近上限 优先热切换升级；不具备热切换时记录为下次启动 S 15 分钟
S → M CPU throttle 明显、内存 > 80%，或浏览器/VNC/文件处理任务启动 创建 M 规格新沙箱并切流 30 分钟
M → L 高价值用户、管理员任务、批处理任务、长时运行任务 需用户等级或任务类型授权，避免自动把所有压力都推到 L 60 分钟
L/M/S → XS 连续 24 小时或 7 次会话低负载 不建议运行中降级；更新 preferred tier，下次启动降级 24 小时
空闲释放 无心跳、无请求、无任务运行超过 TTL 释放沙箱 Pod，保留 Longhorn 用户目录 30 分钟默认

4. 扩缩容体系

ByClaw 的扩缩容应分为三层：沙箱实例层、控制面层、节点池层。

层级对象扩容方式缩容方式是否适合 HPA
沙箱实例层 每个用户的 OpenClaw Pod 按需创建、热切换升级、原地 resize 空闲 TTL 释放、下次启动降级 不适合直接 HPA
控制面层 opensandbox-server、controller、BE、FE HPA / KEDA HPA / KEDA 适合
节点池层 sandbox-general、sandbox-heavy 加节点、云厂商 Cluster Autoscaler 释放空闲节点 节点级扩缩

4.1 沙箱层不是横向副本，而是活跃用户数

OpenClaw 沙箱不是无状态 Web 服务。每个沙箱包含用户工作目录、浏览器、VNC、gateway token、Agent 运行态。它的扩缩容模型应是：

活跃用户数 ≈ 活跃沙箱 Pod 数
空闲用户数 → 释放 Pod，只保留 Longhorn 用户目录
重负载用户 → 升级到更大规格 Pod
低负载用户 → 下次启动回到 XS/S

4.2 控制面 HPA

控制面组件可以 HPA，因为它们是服务型组件：

组件minmax触发说明
opensandbox-server26 或 12CPU 70%、请求 QPS、创建队列长度沙箱创建和代理入口。
byclaw-be28 或 16CPU、HTTP QPS、WebSocket 数业务 API、沙箱调度策略、会话协调。
byclaw-fe13CPU 或请求量nginx 静态服务，通常压力不大。
kube-state-metrics11不扩监控基础组件。

4.3 KEDA 的位置

KEDA 适合基于 Prometheus 指标扩控制面，或扩“待创建沙箱 worker 队列”。它不应直接复制用户沙箱 Pod。官方 KEDA Prometheus scaler 可以把 Prometheus 查询结果作为扩缩容指标。

5. 指标与判定规则

规格调整需要从 Prometheus 拉取“用户沙箱维度”的指标。Pod 必须带上稳定标签：

byclaw.io/workload=sandbox
byclaw.io/user-code=${user_code}
byclaw.io/service-key=openclaw-xs
byclaw.io/tier=xs
byclaw.io/sandbox-id=${sandbox_id}
指标PromQL 示例用途
CPU 使用 sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="by-sandbox", container!="", pod=~".*openclaw.*"}[5m])) 判断是否长期接近 requests 或 limits。
内存 working set sum by (pod) (container_memory_working_set_bytes{namespace="by-sandbox", container!=""}) 判断是否逼近 2Gi/3Gi/4Gi。
CPU throttle rate(container_cpu_cfs_throttled_seconds_total{namespace="by-sandbox"}[5m]) 判断 limits 是否造成明显限速。
重启次数 increase(kube_pod_container_status_restarts_total{namespace="by-sandbox"}[1h]) 识别 OOM 或崩溃。
就绪状态 kube_pod_status_ready{namespace="by-sandbox", condition="false"} 识别升级/切换过程失败。

5.1 调整判定规则

if tier == xs and (cpu_p95_5m > 0.75C or mem_p95_5m > 1.4Gi):
    targetTier = s

if tier == s and (cpu_throttle_5m > threshold or mem_p95_5m > 2.4Gi):
    targetTier = m

if tier == m and userLevel in ["vip", "admin"] and longTaskRunning:
    targetTier = l

if tier in [s, m, l] and low_usage_days >= 1:
    preferredTier = max(xs, tier - 1)   # 下次启动生效

if idle_minutes >= idleTimeout:
    releaseSandbox()
防抖规则：升级至少 15 到 30 分钟冷却；降级至少 24 小时观察；同一用户每天最多自动升级 2 次，避免因短峰值频繁重建。

6. 落地改造

6.1 数据模型

表/配置新增字段说明
sandbox_service_spec.spec_json resourceRequests、nodePool、priorityClassName 按规格分层描述 Pod 调度诉求。
用户偏好表或系统参数 preferred_service_key、last_resize_at、resize_reason 记录用户当前推荐规格。
沙箱记录表 tier、resource_request_cpu、resource_request_memory 方便审计每次启动的规格。
Redis byclaw:sandbox:tier:{userCode} 快速读取用户当前推荐规格。

6.2 后端改造点

类/模块改造优先级
SandboxServiceSpec 增加 resourceRequests、nodePool、resizePolicy。 P0
CreateSandboxRequest 增加 resourceRequests。 P0
GenericSandboxSpecProcessor 把 spec 中 requests/limits 放入 OpenSandbox 创建请求。 P0

SandboxLaunchContextFactory 接入用户默认规格和任务类型选择。 P1

6.3 OpenSandbox 侧能力

OpenSandbox 需要支持或透传以下字段：

{
  "resourceRequests": {
    "cpu": "500m",
    "memory": "1Gi"
  },
  "resourceLimits": {
    "cpu": "2",
    "memory": "4Gi"
  },
  "nodeSelector": {
    "byclaw.io/node-pool": "sandbox-general"
  },
  "metadata": {
    "userCode": "u001",
    "serviceKey": "openclaw-s",
    "tier": "s"
  }
}
如果 OpenSandbox 暂时不支持 requests：仍可先用 limits + 多 serviceKey 落地；但容量规划和调度准确性会打折，建议尽快补 requests。

7.4 原地 resize 方向示例

Kubernetes 官方提供了运行中调整容器 CPU/内存的能力；若当前 k3s 版本和 OpenSandbox 均支持，可以由 OpenSandbox 代理执行 resize。示例形态如下，具体命令需以集群版本和 RBAC 为准：

# 方向示例：对目标 Pod 的 resize 子资源调整资源
kubectl patch pod ${POD_NAME} \
  -n by-sandbox \
  --subresource=resize \
  --type=merge \
  -p '{
    "spec": {
      "containers": [{
        "name": "main",
        "resources": {
          "requests": {"cpu": "500m", "memory": "1Gi"},
          "limits": {"cpu": "1500m", "memory": "3Gi"}
        }
      }]
    }
  }'
不把原地 resize 作为第一阶段依赖：内存缩小、节点容量不足、运行时不支持、OpenSandbox 无 resize API 都可能导致调整失败。第一阶段应以“热切换升级 + 下次启动降级”为主。

8. 容量规划

容量以 requests 为准进行核算。假设系统和 Longhorn 预留后，每个 worker 可用于沙箱的资源约为总资源的 70% 到 80%。

节点规格节点数量按 XS 估算按 S 估算按 M 估算建议用途
4C / 16Gi 3 约 45 到 60 个活跃沙箱 约 25 到 35 个活跃沙箱 约 10 到 15 个活跃沙箱 小规模试点，100 注册用户以内
8C / 32Gi 3 约 100 到 140 个活跃沙箱 约 60 到 80 个活跃沙箱 约 25 到 35 个活跃沙箱 100 到 500 注册用户
16C / 64Gi 5 约 350 到 450 个活跃沙箱 约 220 到 300 个活跃沙箱 约 90 到 120 个活跃沙箱 1000 注册用户，20% 活跃率
16C / 64Gi 20 约 1400 到 1800 个活跃沙箱 约 900 到 1200 个活跃沙箱 约 360 到 480 个活跃沙箱 10000 注册用户，10% 活跃率需混合 XS/S
估算公式：可用沙箱数 = min(可用 CPU / 单沙箱 CPU request, 可用内存 / 单沙箱内存 request)。实际还要扣除 Longhorn 副本、Prometheus、OpenSandbox 控制面、BE、Redis、OpenGauss 等系统开销。

10. FAQ

Q1：默认 XS 会不会体验差？

不会作为最终规格，而是起步规格。XS 有 250m/768Mi requests 和 1C/2Gi limits，可覆盖轻量会话。用户一旦触发浏览器、VNC、数据处理、长任务，就升级到 S/M。

Q2：为什么不直接给所有人 S 或 M？

这样会让集群容量被空闲用户占满。按 XS 起步，再根据真实负载升级，可以显著提高同等机器能承载的活跃用户数。

Q3：运行中从 XS 升到 M，用户文件会丢吗？

不会丢文件。用户目录在 Longhorn PVC 的 byclaw-${user_code}/by 下，新旧 Pod 挂载同一用户目录。但正在运行的浏览器内存态、shell 进程、WebSocket 长连接不能完全无损迁移，所以热切换需要前端提示和后端切 endpoint。

Q4：为什么降级不建议实时做？

CPU 降级通常问题较小，但内存下降可能触发 OOM 或运行时不稳定。降级收益不值得冒会话中断风险，建议记录低负载状态，下次启动或空闲释放后再降级。

Q5：VPA 能不能直接做？

VPA 适合给资源建议或管理控制器型工作负载。OpenClaw 是每用户有状态沙箱，更适合由 BE/OpenSandbox 的专用 Resizer 控制。后续可以参考 VPA 推荐值，但不要让 VPA 直接频繁驱逐用户沙箱。
