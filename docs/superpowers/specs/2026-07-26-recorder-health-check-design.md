# Recorder 健康检查交互设计

## 目标

健康检查完成前不展示 LLM 可用性结论。检查完成后同时展示四项必需依赖和默认 LLM 的状态，让用户理解 LLM 缺失不阻断本地规则评分与本地脚本生成。

## 状态与操作

1. 初始状态显示五项“未检查”：Local Service、byCLI Daemon、Chrome 扩展、High-Level 模块、默认 LLM。
2. 用户点击“运行健康检查”后，保留在当前页面并更新全部五项状态。
3. 前四项为必需项。任一项为 `down` 或 `disconnected` 时，页面显示失败说明，不显示“下一步”，用户只能重新运行检查。
4. 默认 LLM 作为非必需项。可用时显示“可用”；不可用时显示“不可用”，并提示后续仍会使用本地规则评分和本地脚本生成。
5. 四项必需依赖全部可用时，按钮行显示“运行健康检查”和“下一步”。LLM 是否可用均不影响“下一步”。
6. 点击“下一步”后，状态机进入 `health_checked` 并展示绑定会话步骤。

## 视觉原则

保留现有 Ant Design 和品牌紫色。检查项使用一致的语义状态色和可读文本，不通过仅依赖颜色表达。动作按钮保持同一行、明确主次层级。LLM 缺失提示为非阻断信息，不使用错误态造成流程失败的暗示。

## 实现边界

仅修改录制工作台前端的健康检查组件、会话状态模型与相关单元测试。既有后端健康检查契约与本地规则评分、脚本生成能力不变。

## 测试

- 初始状态不提前提示 LLM 缺失；
- 健康检查后五项状态均可见；
- LLM 缺失时有说明且“下一步”仍可用；
- 任一必需项失败时“下一步”不可用且可重新检查；
- 点击“下一步”后进入绑定会话。
