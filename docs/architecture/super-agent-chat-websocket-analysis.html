现状判断 `superAgentChat` 是 HTTP POST + SSE 输出流，会占用 Servlet 请求直到流结束。长任务、网络抖动、代理超时或前端 20 分钟超时都可能导致前端收不到最终事件。
WebSocket 适配度 WebSocket 是合适的升级方向，项目已有 Netty WebSocket、Channel 管理、多端广播、`NettyArrayOutputStream` 等基础，可以渐进复用。
关键前提 WebSocket 不是天然“永不丢消息”。要彻底解决，需要事件持久化、断点续传、幂等请求和最终状态查询。

一、superAgentChat 当前问题

代码事实

  • `ChatChannelController.postChat` 设置 `text/event-stream`，然后直接使用 `HttpServletResponse.getOutputStream()`。
  • `RouteService.route` 在请求线程中消费 `ctx.gatewayEventQueue`，每条 Gateway 事件再写回 SSE。
  • Gateway 事件队列 `poll(5, TimeUnit.MINUTES)`，连续 5 分钟没有事件就抛出 `Gateway 响应超时`。
  • 前端 `SendHelper` 对聊天请求设置 `REQ_TIMEOUT = 1200000`，即 20 分钟硬超时。
  • `SessionStreamManager.stopSessionListener` 会清理 `OutputStreamManager` 中的上下文；之后 Redis 监听器无法再把事件投递给原请求。

风险表现

  • 长时间无 token / 无阶段事件时，后端先因 5 分钟静默超时中断。
  • 任务总时长超过 20 分钟时，前端主动 abort。
  • Nginx、Ingress、LB、浏览器、移动网络都可能提前断开 SSE。
  • 断开后任务可能仍在 Gateway/Worker 侧运行，但当前前端连接已经无法收到后续 `answerDelta` 或 `appStreamResponse`。
  • 最终消息是否完整入库取决于后续事件是否还能被监听、消费和持久化，存在边界风险。
结论：当前问题不是“Servlet 必然丢消息”这么简单，而是“聊天任务生命周期绑定到一次 HTTP/SSE 连接”。连接断开时，前端可见流和后端任务流缺少可靠的补偿协议。

四、WebSocket 是否合适

合适，尤其适合 ByClaw 这类“长任务、多阶段、需要多端同步、可能需要用户中途输入/审批/继续执行”的聊天场景。相较于当前 HTTP/SSE，WebSocket 可以减少一次请求长时间占用 Servlet 线程的问题，并把消息收发抽象成持续连接上的帧协议。

维度 HTTP POST + SSE 当前方案 WebSocket 升级后 注意事项
连接模型 一次聊天绑定一次 HTTP 请求。 一个用户维护长连接，多次聊天请求走消息帧。 需要心跳、重连、鉴权刷新。
长任务支持 容易受 Servlet、代理、浏览器超时影响。 更适合长任务和双向交互。 LB/网关仍可能断开，必须支持恢复。
多端同步 当前已有广播到 WS 设备的辅助逻辑。 天然可以把同一用户多设备纳入统一事件通道。 需要 session/channel 映射和发送端排除。
消息可靠性 断开后缺少补发机制。 可以做 ack、offset、重放。 可靠性来自协议设计，不来自 WebSocket 本身。
改造成本 保留现状成本低，但边界问题会反复出现。 中等偏高；后端已有 Netty 基础可复用。 建议双栈灰度，避免一次性切断 SSE。
推荐判断：如果目标是 PC、Web、App、小程序统一实时接入，WebSocket 是合适的主方案。短期可以保留 `superAgentChat` 兜底，但目标态应把聊天发送、实时同步、断点恢复、取消和 ACK 都收敛到统一 WebSocket 协议。

五、多端兼容判断

多端统一走 WebSocket 是可行的，但不能让每个端各自理解一套聊天细节。正确做法是服务端提供统一 WebSocket Chat Gateway，PC、Web、App、小程序都接入同一套消息协议：发送消息用 `CHAT_START`，接收流式事件用 `CHAT_EVENT`，断线或后来进入会话用 `CHAT_RESUME` 补齐缺失事件。

端类型 接入方式 同步策略 关键要求
PC / Web 页面启动后建立用户级 WebSocket，按 `deviceId` 注册 Channel。 当前端发送 `CHAT_START` 后，本端收到 `CHAT_ACCEPTED`，其他在线端收到同一 `traceId` 的 `SESSION_EVENT` 和后续 `CHAT_EVENT`。 刷新页面后用本地保存的 `lastEventId` 发起 `CHAT_RESUME`。
App App 前台保持 WebSocket；弱网重连后重新注册 `deviceId`。 上线时发送 `SYNC_SESSION` 或 `CHAT_RESUME`，服务端按会话维度补发缺失事件或返回最终态快照。 需要心跳、指数退避重连、token 过期续签和离线期间事件补齐。
小程序 使用平台 WebSocket 能力连接同一 Chat Gateway。 进入会话页时用 `sessionId + lastEventId` 同步；后台断开后前台恢复继续补发。 需要控制连接数量，统一域名白名单，避免多个页面重复建连。
同一用户多设备 一个用户可对应多个活跃 Channel：`userId -> deviceId -> channel`。 发送端收到完整事件，其他端也收到同一事件；服务端通过 `sourceDeviceId` 避免 UI 重复插入用户消息。 所有端必须保存 `clientMessageId`、`traceId`、`lastEventId`，用于幂等和恢复。
多端统一 WebSocket 的核心不是“每个端各写一套 socket 逻辑”，而是沉淀统一客户端 SDK：连接、鉴权、心跳、重连、ACK、幂等、断点恢复都由 SDK 负责，业务 UI 只消费统一的聊天事件。

PC 发起聊天后其他端如何同步

  1. PC 端生成 `clientMessageId` 和 `idempotencyKey`，通过 WebSocket 发送 `CHAT_START`。
  2. 服务端创建或复用聊天任务，生成 `traceId`、`queryMessageId`、`messageId`，写入 Chat Task Store 和 Event Store。
  3. 服务端向 PC 回复 `CHAT_ACCEPTED`，同时向该用户其他在线 Channel 广播 `SESSION_EVENT:userMessage`，其他端在 UI 中插入“来自 PC 的用户消息”。
  4. Gateway/Worker 产生 `answerDelta`、`reasoningLogDelta`、`appStreamResponse` 等事件后，服务端先写 Event Store，再通过 Delivery Router 广播给所有在线端。
  5. 每个端消费事件后更新本地 `lastEventId` 并发送 `CHAT_EVENT_ACK`；如果某端离线，重新连接后用 `CHAT_RESUME` 补发 `lastEventId` 之后的事件。

七、推荐升级方案

  1. 先做止血层：保留 SSE，补 heartbeat 和可配置超时。 这是过渡期动作，降低当前 `superAgentChat` 的消息丢失概率；目标态聊天主链路统一迁移到 WebSocket。
  2. 建立统一事件模型。 所有 `initialization`、`answerDelta`、`reasoningLogDelta`、`answerEnd`、`appStreamResponse`、`error` 都包装成统一结构：`eventId`、`sessionId`、`traceId`、`messageId`、`eventType`、`payload`、`sourceDeviceId`、`createdAt`。
  3. 落地 Event Store。 事件必须先写入 Event Store，再广播到各端。在线端实时消费，离线端或重连端按 `lastEventId` 补发，最终态用 `traceId` 查询。
  4. 新增统一 WebSocket Chat Gateway。 在现有 Netty `WebSocketHandler` 基础上扩展 `CHAT_START`、`CHAT_ACCEPTED`、`CHAT_EVENT`、`CHAT_EVENT_ACK`、`CHAT_RESUME`、`CHAT_CANCEL`、`SYNC_SESSION`、`HEARTBEAT`。
  5. 服务端解耦连接与任务。 `CHAT_START` 创建任务并立即返回 `CHAT_ACCEPTED`；Gateway/Worker 后续事件进入 Event Store，再由 Delivery Router 推送到所有在线 Channel。任一端连接断开都不停止任务。
  6. 多端统一 SDK。 PC、Web、App、小程序使用同一套协议封装：生成 `clientMessageId`、维护 `deviceId`、保存 `lastEventId`、自动重连、自动 `CHAT_RESUME`、按事件更新 UI。
  7. 幂等和并发控制。 以 `userId + sessionId + clientMessageId` 作为发送幂等键，同一键重复发送只返回已存在的 `traceId`，不会重复创建任务；同一会话是否允许并行发送由会话策略控制。

八、统一消息协议建议

方向 类型 字段 说明
Client → Server `CHAT_START` `clientMessageId`, `idempotencyKey`, `deviceId`, `sessionId`, `chatContent`, `accessTerminal`, `metadata` 开始一次聊天；服务端按 `userId + sessionId + clientMessageId` 幂等去重。
Server → Client `CHAT_ACCEPTED` `clientMessageId`, `traceId`, `queryMessageId`, `messageId`, `deduplicated` 表示任务已创建；如果是重复请求，`deduplicated=true` 并返回原任务标识。
Server → Client `CHAT_EVENT` `eventId`, `traceId`, `eventType`, `payload`, `sourceDeviceId`, `createdAt` 统一承载 `answerDelta`、`reasoningLogDelta`、`appStreamResponse` 等现有事件。
Client → Server `CHAT_EVENT_ACK` `traceId`, `lastEventId` 可选，用于服务端统计和裁剪缓存。
Client → Server `CHAT_RESUME` `traceId`, `sessionId`, `lastEventId`, `deviceId` 断线重连、页面刷新、其他端进入会话后补发缺失事件。
Client → Server `SYNC_SESSION` `sessionId`, `lastEventId`, `deviceId` 新设备进入会话时同步会话内仍在运行或最近完成的消息事件。
Client → Server `CHAT_CANCEL` `traceId`, `deviceId`, `reason` 用户主动取消；服务端应向 Gateway/Worker 传播取消。
双向 `HEARTBEAT` `ts` 保持连接活性，检测半开连接。

发送幂等性处理

多端都能发送消息后，必须防止弱网重试、页面双击、App 重连重放、小程序重复触发造成重复任务。推荐以 `clientMessageId` 作为端侧生成的稳定消息 ID，服务端用 `userId + sessionId + clientMessageId` 建唯一索引。

十、验证清单

功能验证

  • 普通短会话：事件顺序与现有 SSE 一致。
  • 超过 20 分钟长会话：不中断或断后可恢复。
  • 5 分钟无业务事件：heartbeat 生效，不误判失败。
  • 刷新页面后：按 `traceId + lastEventId` 补齐缺失事件。
  • 同一用户多设备：发送端不重复，其他设备可同步。
  • PC 发起聊天后，Web、App、小程序在线端能实时看到用户消息和模型增量回复。
  • App/小程序后来进入同一会话：能通过 `SYNC_SESSION` 或 `CHAT_RESUME` 补齐缺失事件。
  • 任一端弱网重试同一 `clientMessageId`：只产生一个任务、一条用户消息、一组回复事件。

工程验证

  • WebSocket 鉴权、token 过期、重连退避。
  • 任务取消能传递到 Gateway/Worker。
  • Event Store TTL、容量、清理策略明确。
  • 监控：连接数、重连次数、补发次数、事件延迟、任务最终态缺失数。
  • 压测：长连接数量、单用户多会话、慢客户端背压。
  • 多端 SDK：PC/Web/App/小程序的 `deviceId`、ACK、重连、补发和幂等行为一致。

十一、基于当前代码的 WebSocket 升级步骤

这一节按当前项目已有代码落地，不另起一套聊天系统。核心思路是：复用 `AssistantChatService`、`ScriptService`、`RouteService` 的聊天编排能力，扩展现有 Netty WebSocket 层，把 `superAgentChat` 的“一次 HTTP 请求承载一次长流”改成“WebSocket 命令启动任务，事件落库后广播到所有端”。

11.1 盘点可复用代码

现有代码 当前职责 升级后用法
`ChatChannelController.postChat` HTTP SSE 入口，设置响应头并传入 `ServletOutputStream`。 保留为过渡兜底；新链路不再依赖它维持长会话。
`WebSocketHandler` 已有 Netty WebSocket 文本帧入口，按 `MessageType` 分发。 扩展识别 `CHAT_START`、`CHAT_RESUME`、`CHAT_EVENT_ACK`、`SYNC_SESSION`、`CHAT_CANCEL`。
`ChatService.llmChat` 当前 WebSocket 聊天入口，使用 `NettyArrayOutputStream` 调 `AssistantChatService.chat`。 改造成命令入口：先做幂等和任务登记，再异步启动聊天任务。
`NettyArrayOutputStream` 把 `OutputStream.write` 直接写成 WebSocket 帧。 短期可用；目标态建议替换为事件收集器，避免直接写当前连接导致断线丢事件。
`RouteService.route` 监听 Redis Stream 队列，在请求线程写 SSE。 保留 Gateway/Worker 对接逻辑，但把“写流”改为“写 Event Store + Delivery Router 广播”。
`MultiDeviceBroadcastService` / `ChannelManager` 已有同一用户多 WebSocket Channel 广播能力。 作为多端同步基础，增强 `deviceId`、`sourceDeviceId`、ACK、在线状态管理。

11.2 第一步：定义统一 WS 消息模型

在 `MessageType` 或独立枚举中新增聊天命令类型，避免继续复用语义过宽的 `LLM_MESSAGE`。建议新增：

  • `CHAT_START`：任一端发送用户消息。
  • `CHAT_ACCEPTED`：服务端确认任务已创建或命中幂等记录。
  • `CHAT_EVENT`：服务端推送统一事件，承载现有 `answerDelta`、`reasoningLogDelta`、`appStreamResponse`。
  • `CHAT_EVENT_ACK`：端侧确认已消费到哪个 `eventId`。
  • `CHAT_RESUME`：按 `traceId + lastEventId` 补发缺失事件。
  • `SYNC_SESSION`：新端进入会话页后按 `sessionId + lastEventId` 同步会话事件。
  • `CHAT_CANCEL`：取消指定 `traceId` 的运行任务。

同时扩展 `ChatMessage` 或新增 `WsChatCommand`，字段包含 `deviceId`、`clientMessageId`、`idempotencyKey`、`sessionId`、`traceId`、`lastEventId`、`payload`。

11.3 第二步：改造连接注册和多端 Channel 管理

当前 `ChannelManager` 已按用户管理多个 Channel。升级时把映射增强为 `userId -> deviceId -> channel`，握手或首个认证帧中必须带 `deviceId`、端类型和版本号。

  1. 在 WebSocket 握手鉴权成功后，把 `LoginInfo` 写入 Channel 属性，继续沿用当前做法。
  2. 新增 `deviceId` Channel 属性，PC、Web、App、小程序都由 SDK 生成并持久化。
  3. 同一 `deviceId` 新连接上线时，关闭或覆盖旧 Channel，避免一个设备重复收消息。
  4. 广播时携带 `sourceDeviceId`，发送端和其他端都收到统一事件，但 UI 可根据该字段避免重复插入本地乐观消息。

11.4 第三步：增加发送幂等表或缓存

在服务端建立幂等记录，唯一键建议为 `userId + sessionId + clientMessageId`。字段至少包括 `traceId`、`queryMessageId`、`messageId`、`taskId`、`status`、`createdAt`。

  1. 收到 `CHAT_START` 后先查幂等记录。
  2. 如果存在，直接返回 `CHAT_ACCEPTED(deduplicated=true)`，并按 `traceId + lastEventId` 补发已有事件。
  3. 如果不存在，先插入幂等记录和用户消息事件，再启动后续聊天任务。
  4. 数据库唯一索引兜底并发：两个端同时提交同一 `clientMessageId`，只有一个插入成功，另一个读取已存在记录。

11.5 第四步：建设 Event Store

当前风险的根因是事件直接写当前连接。目标态必须改成事件先持久化，再推送。Event Store 可以先用 Redis Stream 加 TTL 落地，稳定后再把关键事件入库。

  1. 定义事件结构：`eventId`、`userId`、`sessionId`、`traceId`、`messageId`、`eventType`、`payload`、`sourceDeviceId`、`createdAt`。
  2. `eventId` 必须单调递增，至少在同一 `traceId` 内有序。
  3. 所有事件写入成功后再调用 Delivery Router 广播。
  4. `CHAT_RESUME` 从 Event Store 查询 `eventId > lastEventId` 的事件并按顺序补发。
  5. 如果事件已过期，返回最终消息快照和 `snapshot=true`，避免端侧永远卡在流式状态。

11.6 第五步：改造 RouteService 写流路径

`RouteService.route` 当前在循环里消费 `ctx.gatewayEventQueue`，然后调用 `pythonSseService.getContentFromPythonStreamV3(..., ctx.res, ...)` 写回 `OutputStream`。升级时需要拆出“解析事件”和“投递事件”两个动作。

  1. 保留 Gateway SDK 发送和 Redis Stream 监听逻辑。
  2. 把每条 Redis 事件转换成统一 `ChatEvent`。
  3. 调用 `chatEventStore.append(event)` 写入 Event Store。
  4. 调用 `deliveryRouter.broadcast(userId, sessionId, event)` 推送给所有在线端。
  5. 收到 `appStreamResponse` 或 `error` 后更新任务状态，并释放运行态标记。
这一改造是解决当前问题的关键点：即使某个端的 WebSocket 断开，Gateway/Worker 后续事件仍会进入 Event Store，端重连后可以补发，不再依赖旧连接还活着。

11.7 第六步：Gateway SDK Redis Stream 接入 WebSocket

当前 `RouteService.route` 已经通过 Gateway SDK 发送消息，并由 `SessionStreamManager` 启动 Redis Stream 监听器；`RedisStreamMessageListener` 收到消息后把 JSON 投入 `ctx.gatewayEventQueue`。升级 WebSocket 时，不需要推翻 Gateway SDK 和 Redis Stream，只需要把“请求线程消费队列写 SSE”替换成“Stream 消费器写 Event Store，然后 Delivery Router 广播 WebSocket”。

  1. `CHAT_START` 命中幂等后，由服务端调用现有 Gateway SDK 发送消息，保持 `sessionId`、`traceId`、`messageId` 与当前链路一致。
  2. Gateway/Worker 继续把 `answerDelta`、`reasoningLogDelta`、`appStreamResponse`、`error` 写入 `byai_gateway:session:{sessionId}:data_stream`。
  3. 把 `SessionStreamManager` 的监听职责从“投递到当前请求上下文”升级为“投递到稳定的 Stream Consumer”。Consumer 不依赖 `ServletOutputStream` 或某个 WebSocket Channel。
  4. Consumer 解析 Redis 消息，校验 `trace_id`，转换为统一 `ChatEvent`，生成服务端 `eventId`。
  5. 先调用 `chatEventStore.append(chatEvent)`，成功后再执行 Redis Stream ACK；如果 Event Store 写失败，不 ACK，让消息留在 pending 或重新消费。
  6. Event Store 写成功后调用 `deliveryRouter.broadcast(chatEvent)`，把同一 `eventId` 推送给 PC、Web、App、小程序所有在线端。
  7. 端侧收到 `CHAT_EVENT` 后更新 UI，保存 `lastEventId`，再发送 `CHAT_EVENT_ACK`。ACK 只表示端已消费，不决定服务端是否保留事件。

11.8 第七步：保证消息不丢的处理规则

WebSocket 连接本身仍可能断开，因此“不丢消息”的边界必须放在 Redis Stream、Event Store 和补发协议上，而不是放在单条 WebSocket 连接上。

  • Redis Stream ACK 时机：必须在 Event Store 写成功之后，不能在 WebSocket 推送成功之后才 ACK，否则慢端会拖垮消费。
  • Event Store 唯一约束：`traceId + gatewayMessageId/eventType/sequence` 或服务端生成的 `eventId` 要能防止 Consumer 重放导致重复事件。
  • WebSocket 发送失败：只记录该 `deviceId` 未 ACK，不回滚 Event Store；端重连后按 `lastEventId` 补齐。
  • 最终态兜底：如果增量事件过期，端通过 `traceId` 拉取最终 `appStreamResponse` 或消息快照。

11.9 第八步：消息幂等性和防抖处理

多端 WebSocket 后，重复消息主要来自四类场景：用户双击发送、弱网重试、WebSocket 重连后 SDK 重放、多个端误用同一草稿提交。处理方式要分前端防抖和服务端幂等两层。

问题 前端/端侧处理 服务端处理
按钮双击 / 快速回车 发送按钮进入 pending；300-500ms 防抖；同一输入框提交复用同一个 `clientMessageId`。 唯一键 `userId + sessionId + clientMessageId`，重复请求返回原 `traceId`。
弱网超时重试 重试时不能重新生成 `clientMessageId`，只重发同一个 `CHAT_START`。 如果任务已创建，返回 `CHAT_ACCEPTED(deduplicated=true)` 并补发已有事件。
WebSocket 重连重放 SDK 维护 pending 队列；已收到 `CHAT_ACCEPTED` 的消息只发 `CHAT_RESUME`，不再发 `CHAT_START`。 根据幂等记录和任务状态判断是返回原任务，还是拒绝非法重复。
多端同时发送 不同端独立生成不同 `clientMessageId`；UI 标明发送端。 是否允许同一 session 并行运行由会话策略决定；不允许时返回 `SESSION_BUSY` 或排队。
防抖只能改善用户体验，不能作为可靠防重手段。真正防止重复任务必须靠服务端幂等键和数据库唯一约束。

11.10 第九步：新增 Delivery Router

Delivery Router 封装多端广播逻辑，不让业务服务直接操作 Netty Channel。它可以复用 `MultiDeviceBroadcastService`，但需要补齐事件格式和 ACK 记录。

  1. 查询 `ChannelManager.getChannels(userId)` 获取该用户所有在线端。
  2. 把 `ChatEvent` 包装为 `CHAT_EVENT` 帧。
  3. 推送给所有在线 Channel，包括发送端。发送端根据 `clientMessageId` 合并本地乐观消息。
  4. 记录每个 `deviceId` 的最后 ACK eventId，用于监控和补发优化。

11.11 第十步：前端和多端 SDK 改造

前端当前 `SendHelper` 使用 `fetchEventSource('/byaiService/chat/superAgentChat')`。目标态新增统一 WS SDK，PC、Web、App、小程序都按同一协议实现。

  1. 封装 `connect()`：负责 token、deviceId、心跳、重连退避。
  2. 封装 `sendChat()`：生成 `clientMessageId`，发送 `CHAT_START`，返回本地可追踪的 pending message。
  3. 封装 `onChatEvent()`：把 `CHAT_EVENT` 转换成现有 UI 可消费的 message patch，尽量复用 `answerDeltaHandler`、`reasoningLogHandler`。
  4. 封装 `resume()`：重连后对运行中的 `traceId` 发送 `CHAT_RESUME`。
  5. 封装 `syncSession()`：进入会话页时按 `sessionId + lastEventId` 发送 `SYNC_SESSION`。

11.12 第十一步：保留 superAgentChat 过渡和灰度

不建议一次性删除 `superAgentChat`。迁移期可以让 PC/Web 指定用户或指定 agent 先走 WebSocket，其余继续走 SSE。稳定后 App、小程序接入同一 WS Gateway，最后把 `superAgentChat` 降级为兼容接口或内部 fallback。

  1. 增加开关：按租户、用户、agent、端类型控制是否启用 WS。
  2. 新旧链路事件格式保持一致，便于对比回放。
  3. 同一会话不要同时启用 SSE 和 WS 两条主发送链路，避免重复任务。
  4. 灰度期间重点看：重复消息数、补发成功率、最终态缺失数、平均重连次数、连接数峰值。

11.13 第十二步：上线验收顺序

  1. 后端单测：幂等键重复提交只创建一个任务。
  2. 后端集成测试：模拟 Redis Stream 事件，确认 Event Store 先落库再广播。
  3. 前端联调：PC 发起聊天，Web/App/小程序在线端实时收到同一事件序列。
  4. 断线测试：任一端断开 30 秒后重连，`CHAT_RESUME` 能补齐缺失 `eventId`。
  5. 弱网测试：同一 `clientMessageId` 重发 3 次，服务端返回同一 `traceId`。
  6. 长任务测试：超过 20 分钟仍能收到最终 `appStreamResponse`，中途刷新能恢复。

十二、最终建议

推荐采用“短期 SSE 止血 + 中期统一 WebSocket Chat Gateway + 多端 SDK 接入 + 事件可靠投递”的路线。WebSocket 是合适的升级方向，尤其能更好地支撑长任务、多端同步和交互式 Agent 工作流；但要避免只改连接协议而不做事件持久化、断点恢复和发送幂等。

目标形态应该是：PC、Web、App、小程序都通过 WebSocket 接入；聊天任务独立运行；事件先可靠保存再广播；在线端实时收到同一 `eventId`；离线或重连端按 `lastEventId` 补发；重复发送按 `clientMessageId` 幂等复用原任务。这样才能同时解决长会话丢消息、多端同步和重复提交问题。
