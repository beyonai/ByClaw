# 技能组创建、展示、安装与权限架构

本文描述技能组从创建、上传和选择组内技能、处理封面，到针对数字员工安装、申请权限、展示状态和按来源卸载的实现口径。

## 1. 核心语义

技能组是一个可复用的技能集合，但不是运行时的嵌套容器。系统采用“安装快照”语义：

- 技能组本身保存当前成员配置。
- 安装时，将当前可安装成员展开为“数字员工 → 普通技能”的直接关系。
- 安装后再增删技能组成员，不自动同步到已安装该组的数字员工。
- 直接技能关系记录手工来源、技能组来源和安装人，卸载时仅移除指定来源。
- 查看详情只计算状态，不因权限变化隐式增删数字员工技能关系。

## 2. 组件边界

| 层 | 组件 | 职责 |
|---|---|---|
| 前端 | `SkillGroupCreateModal` | 创建/编辑技能组，按“内置技能、个人技能”Tab 展示候选项，支持上传个人技能、合并选中项和处理封面 |
| 前端 | `ResourceImport` | 复用个人技能导入流程，以 `ownerType = personal` 导入技能并返回结构化导入结果 |

## 3. 数据模型

当前实现不新增表结构，复用资源和资源关系表。

| 数据 | 存储方式 | 关键值 |
|---|---|---|
| 技能组 | `ss_resource` | `resource_biz_type = SKILL_GROUP`，`resource_type = COMBIN` |
| 组内技能 | `ss_resource_rel_detail` | `rel_type_name = SKILL_GROUP_MEMBER`，`resource_id` 为组 ID，`rel_resource_id` 为技能 ID |
| 数字员工技能 | `ss_resource_rel_detail` | 数字员工到普通技能的直接关系；`rel_resource_info` 保存来源元数据 |

来源元数据当前使用版本 2：

```json
{
  "version": 2,
  "manual": false,
  "sourceGroupIds": [7001],
  "legacySourceGroupIds": [],
  "groupInstallers": {
    "7001": [10001]
  }
}
```

- `manual`：是否存在手工安装来源。
- `legacySourceGroupIds`：兼容旧数据中无法定位安装人的技能组来源。
- `groupInstallers`：技能组 ID 到安装用户 ID 集合的映射。
- `sourceGroupIds`：兼容字段，等于旧来源与 `groupInstallers` 键的并集。
- 来源 JSON 非法时按保守策略处理，不在卸载流程中误删关系。

## 4. 创建与成员候选

### 4.1 创建和管理

- 企业技能组创建/删除当前受 AdminVip 用户编码控制；后端以 `USERCODE_CONFIG` 为配置来源，并保留 `adminvip` 默认值。
- 编辑技能组和维护成员要求当前用户具备该技能组的管理权限。
- 详情返回 `creatorName`，前端展示技能组创建人。

### 4.2 候选项规则

候选列表由后端完成租户、状态和创建人过滤，前端只负责分类展示：

1. 内置技能：当前企业内、已上架、`owner_type = enterprise` 且 `skill_type = inner`。
2. 个人技能：当前企业内、已上架、由技能组原创建人创建的 `enterprise` 或 `personal` 技能。

创建新技能组时使用当前用户作为创建人；编辑已有技能组时固定使用该技能组的原创建人，不随当前编辑人改变。后端在新增成员时再次执行同一校验，避免绕过候选接口直接提交非法成员。

创建弹窗的下拉内容使用小尺寸 Tabs 区分“内置技能”和“个人技能”，两个 Tab 均显示数量并使用固定高度滚动区域。上传入口复用 `ResourceImport`，并固定以 `activeTab = personal` 导入，因此新技能归属“个人技能”。

上传与成员选择采用延迟提交语义：

1. 导入弹窗只把后端明确标记为成功的技能 ID 返回父弹窗；预检结果、失败项和空 ID 不参与合并。
2. 父弹窗关闭导入弹窗并重新查询成员候选；刷新成功后合并当前已选技能与新导入技能，去重后切换到“个人技能”Tab。
3. 候选刷新失败时保留技能的导入结果，但不把无法确认的 ID 自动写入当前选择，并提示用户重试。
4. 上传技能本身在导入完成时已经创建，但技能组成员关系只在父弹窗确认提交时通过创建/成员维护接口写入；取消父弹窗不会把该技能加入技能组。
5. 父弹窗关闭、重新打开或切换编辑对象时递增请求代次，过期的刷新和详情请求不得覆盖当前表单状态；导入弹窗采用条件挂载，关闭后重置内部状态。

### 4.3 封面处理与瀑布流

封面上传由前端在提交文件服务前完成规格化：

- 图片自然宽度与自然高度严格相等时，视为 1:1；直接复用原始 `File`，不裁切、不转码，也不改变文件名、类型和修改时间。
- 其他比例继续生成 900×1200 的 3:4 PNG。画布先绘制模糊、降亮度的铺满背景，再将完整原图按 `contain` 居中叠加，避免主体拉伸或裁掉。
- 图片无法解码、Canvas 不可用或无法生成 Blob 时终止本次封面选择，并显示处理失败提示。
- 预览和最终上传使用同一个处理结果，避免预览比例与服务端保存文件不一致。

列表卡片不固定封面容器为 3:4，而是使用图片自身高度。1:1 原图、历史或新生成的 3:4 封面会形成不同卡片高度，并由现有分栏算法组成瀑布流。封面缺失或加载失败时使用 1086×1086 的 1:1 默认封面；详情抽屉继续使用 `object-fit: contain` 完整展示封面。

## 5. 可见性与权限边界

### 5.1 技能组

- 列表和详情限制在当前租户。
- 非 `personal` 技能组对同租户用户可见；`personal` 技能组列表/详情默认仅创建人可见。
- 安装/卸载非 `personal` 技能组时，不额外要求技能组本身的使用授权。
- 安装/卸载 `personal` 技能组时，要求用户具备该组的管理权限或使用权限。
- 无论技能组是否可见，安装目标数字员工都必须属于同租户、处于上架状态，且当前用户具备管理权限。

### 5.2 组内技能

- 系统内置技能在技能组场景中视为天然可使用，不发起使用申请。
- 个人/企业自建技能按实时授权结果判断。
- 有效的显式 `ALLOW_MANAGE` 授权可作为使用权限；授权维护流程也会在没有同维度使用黑名单时补充 `FORCE_USE`。
- 平台管理员、组织管理员等角色带来的管理兜底不自动等同于技能使用权限。
- 同维度已有使用黑名单时，管理授权维护流程不会自动补充 `FORCE_USE`；管理和使用两类红黑名单仍分别计算。

## 6. 成员状态模型

详情和安装预检使用同一套状态计算。只有传入 `digitalEmployeeId` 时，才能判断该数字员工是否已经安装技能。

| 后端状态 | 前端文案 | 判定条件 |
|---|---|---|
| `INSTALLED` | 已安装 | 当前具备使用权限，且数字员工已有该技能直接关系 |
| `INSTALLABLE` | 可安装 | 当前具备使用权限，但数字员工尚未关联该技能 |
| `APPLY_REQUIRED` | 需申请 | 当前无使用权限，允许发起使用申请，且没有待审核申请 |
| `APPLY_PENDING` | 申请中 | 当前无使用权限，已有待审核使用申请 |
| `APPLY_UNAVAILABLE` | 无法申请 | 当前无使用权限，且资源配置或黑名单等条件不允许申请 |

状态以当前权限为准。若技能已经关联到数字员工，但之后使用权限被撤销，详情不会继续显示“已安装”，而会根据实时条件显示“可安装”“需申请”“申请中”或“无法申请”；底层关系和技能组来源不会被自动清理。

## 7. 安装流程

```text
打开技能组详情
    │
    ├─ 未指定数字员工 ──> 安装按钮禁用，成员只展示权限状态
    │
    └─ 指定且可管理的数字员工
          │
          ├─ POST /skillGroup/detail ──> 返回实时成员状态和 installedByGroup
          │
          └─ 点击安装
                │
                ├─ POST /skillGroup/install/preflight
                │      └─ 统计可立即安装、需申请、申请中、无法申请
                │
                ├─ 全部可直接处理 ──> POST /skillGroup/install/execute
                │
                └─ 存在权限阻碍 ──> 展示分类确认弹窗
                       └─ 用户确认后统一执行安装和申请
```

确认弹窗展示汇总数字，并按状态列出具体技能：

- 可立即安装：`INSTALLED + INSTALLABLE`，其中已安装项保持现状。
- 需要申请：`APPLY_REQUIRED`。
- 申请中：`APPLY_PENDING`，本次不重复申请。
- 无法申请：`APPLY_UNAVAILABLE`，本次不安装。

执行阶段安装 `INSTALLABLE` 技能，保留 `INSTALLED` 技能，并逐个为 `APPLY_REQUIRED` 技能提交使用申请。接口返回最终成员状态，前端立即更新；再次进入详情时后端重新计算。

当所有当前成员均为 `INSTALLED`，且来源元数据确认该数字员工存在本技能组来源时，`installedByGroup = true`。此时安装按钮置灰并显示“已安装”。仅仅手工安装了相同技能，不会被误判为已安装该技能组。

## 8. 卸载、删除和撤权

### 8.1 来源感知卸载

卸载预检读取数字员工现有技能关系，不依赖技能组当前成员，因此成员变更不会造成旧快照无法卸载。

- `PRESERVE_SHARED`：仅移除当前技能组来源；仍有手工或其他技能组来源时保留直接关系。
- `REMOVE_ALL`：删除受影响的直接技能关系，可能影响其他来源，因此要求带预检生成的 `previewToken` 二次确认。
- 来源元数据非法时跳过该关系，优先避免误删。
- 技能组仍被数字员工来源引用时，不允许直接删除技能组。

### 8.2 权限撤销

权限撤销采用“状态实时收敛、关系不自动清理”的兼容方案：

- 不在授权变更事务中批量扫描组织或岗位成员。
- 不自动删除 `sourceGroupIds`、`groupInstallers` 或数字员工技能关系。
- 详情、预检和安装时重新计算权限，阻止无权限技能继续以“已安装”状态出现或被新装入快照。

该方案保持原有授权变更事务边界，避免组织人数较多时产生大事务和集中锁竞争。后续如需物理清理，应采用独立、可重试、分批执行的对账任务，而不是放入授权变更事务。

## 9. 并发与事务

- 安装、卸载和删除共享技能组行锁，避免删除与快照操作并发。
- 数字员工行锁串行化同一数字员工的直接技能关系变更。
- 安装时按技能 ID 升序锁定活跃技能，减少不同请求的锁顺序差异。
- 关系表历史部署没有专用的数字员工-技能唯一约束，插入逻辑在持有数字员工锁的前提下执行幂等检查。
- 权限申请和快照安装由后端事务编排；发生异常时按当前接口事务整体回滚。

## 10. 主要接口

| 接口 | 用途 |
|---|---|
| `POST /skillGroup/create` | 创建技能组 |
| `POST /skillGroup/update` | 更新技能组信息 |
| `POST /skillGroup/page` | 分页查询技能组 |
| `POST /skillGroup/detail` | 查询详情、成员实时状态和安装来源状态 |
| `POST /skillGroup/member/candidates` | 查询内置技能和原创建人的技能 |
| `POST /skillGroup/member/add` | 添加组内技能 |
| `POST /skillGroup/member/remove` | 移除组内技能 |
| `POST /skillGroup/install/preflight` | 安装前状态汇总 |
| `POST /skillGroup/install` | 兼容入口；无权限阻碍时直接安装，否则返回待确认结果 |
| `POST /skillGroup/install/execute` | 统一执行安装和申请 |
| `POST /skillGroup/uninstall/preflight` | 卸载来源预检 |
| `POST /skillGroup/uninstall` | 按模式卸载技能组来源 |
| `POST /skillGroup/delete` | 删除无安装来源引用的技能组 |
