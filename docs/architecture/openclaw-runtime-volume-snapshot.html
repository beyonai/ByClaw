OpenClaw 运行态数据卷与快照恢复方案

目标是彻底避免把 S3/MinIO 的 rclone 网盘挂载用作运行时文件系统，从而规避随机读写、文件锁、WAL、fsync、mmap、rename 原子性和多实例写入一致性问题；同时保留系统级数据卷快照与恢复能力。

基于当前代码实现梳理：Spec.json、GenericSandboxSpecProcessor、SandboxRuntimeRequestFactory、MinioBucketMountSupport、MinioStorageService。

结论

首选兼容方案是保持 OpenClaw 容器内仍然只有一个 /by 运行态数据卷，但把 /by 的底层从对象型 S3/rclone mount 替换成文件型 NAS/NFS/SMB 存储。这样不改变 OpenClaw 现有路径习惯，也可以彻底避开 S3 对象存储模拟文件系统带来的兼容性问题。 

/by  OpenClaw 运行态主卷：NAS/NFS/SMB 文件型存储，承载 state、DB、workspace、用户可见文件

最关键的 Spec 改造不是修改容器内路径，而是修改 /by 的卷来源：不再让 hostPath=${FILE_STORAGE_MINIO_MOUNT_PATH} 指向 rclone 挂载目录，而是让 /by 来自 Docker NFS/SMB volume、宿主机 NAS 挂载目录或 K3s NFS/SMB PVC。

架构图：保留容器内 /by，替换底层卷来源

当前实现对比

Spec.json 的现状

当前 Spec.json 的 OpenClaw 容器只定义了一个业务数据卷：

{
  "env": {
    "OPENCLAW_STATE_DIR": "/by/.openclaw",
    "DWS_CONFIG_DIR": "/by/.openclaw/.dws",
    "NODE_OPTIONS": "... --diagnostic-dir=/by/node-diagnostics ..."
  },
  "volumes": [
    {
      "key": "base",
      "scope": "PRIVATE",
      "subPath": "byclaw-${user_code}/by",
      "hostPath": "${FILE_STORAGE_MINIO_MOUNT_PATH}",
      "readOnly": false,
      "mountPath": "/by"
    }
  ]
}

这意味着用户文件、OpenClaw state、DWS 配置、Node 诊断文件都落在 /by 下。如果宿主机的 ${FILE_STORAGE_MINIO_MOUNT_PATH} 是 rclone 挂载出来的 S3/MinIO bucket，那么运行态随机写也会落到对象存储网盘语义上。

后端如何把 Spec 变成容器请求

GenericSandboxSpecProcessor.buildVolumes 会渲染 hostPath、subPath、mountPath，并构造 sandbox volume。当前字段已经足以保持单卷 /by 模型，只需要把 hostPath 从 S3/rclone 挂载根目录切换为 NAS/NFS/SMB 文件型存储根目录。 

hostPath = renderPathTemplate(v.getHostPath(), ...)
mountPath = renderPathTemplate(v.getMountPath(), ...)
subPath = renderPathTemplate(v.getSubPath(), ...)

Volume.builder()
  .host(new HostVolume(hostPath))
  .mountPath(mountPath)
  .scope(v.getScope().name())
  .readOnly(...)
  .subPath(subPath)

SandboxRuntimeRequestFactory.buildVolumesPayload 会把 volume 的 mountPath、name、readOnly、subPath、scope 传给运行时。也就是说，Spec 层已经有“多卷”的模型，只是当前 OpenClaw 配置没有把热状态卷拆出来。

MinIO/rclone 挂载现状

MinioStorageService.mount 会创建 bucket 并调用 MinioBucketMountSupport.mountSingleBucketOnAllTargets。后者在宿主机执行 rclone mount： 

rclone mount ':s3:<bucket>' <mountDirectory> \
  --s3-provider Minio \
  --s3-endpoint '<endpoint>' \
  --vfs-cache-mode minimal \
  --allow-non-empty \
  --poll-interval 2s \
  --dir-cache-time 2s \
  --attr-timeout 2s \
  --daemon

--vfs-cache-mode minimal 对普通文件读取和下载场景可用，但不足以承载 SQLite/PGLite、ffmpeg 临时输出、包管理器缓存、git 工作区等随机读写场景。即使改成 full，也只能缓解体验，不能把对象存储变成强 POSIX 文件系统。

能否完全替代 MinIO 数据卷

可以完全替代 MinIO/rclone 数据卷挂载方案，也就是 OpenClaw 容器仍然挂载 /by，但 /by 不再来自 ${FILE_STORAGE_MINIO_MOUNT_PATH} 这类 S3 网盘目录，而是来自开源文件型存储服务提供的 NAS/NFS/SMB。

不建议一并替代 MinIO 对象存储能力。当前代码中 ByclawFS、UserFS、ResourceFS、ArchiveFS 的抽象仍然适合通过 ObjectStorage 写入 MinIO/S3：它们表达的是上传、下载、列目录、删除、归档这类对象存储语义，而不是容器运行时磁盘语义。

能力 当前实现 是否应替代 目标实现
OpenClaw 运行态文件系统 /by 由 rclone mount 提供，OPENCLAW_STATE_DIR=/by/.openclaw 必须替代 /by 使用 Docker NFS/SMB volume、宿主机 NAS 挂载目录或 K3s 文件型 PVC
临时计算工作区 用户和工具可能直接使用 /by 必须替代 优先使用 /by/tmp 或可选额外临时卷；单卷模式下仍在 PVC 上
用户文件对象存储 MinIO bucket 中以 /by 为 objectKey 前缀 不建议替代 继续用 MinIO/S3 SDK 读写；需要本地文件路径时下载或同步到 PVC 的 /by
公共资源 bucket ResourceFS.init() 初始化 bucket，历史 spec 可挂到 /by/.openclaw/byresources 替代挂载，不替代对象存储 资源仍在 MinIO/S3，通过后端 API 或启动同步进入 /by/.openclaw/resources
系统级快照恢复 S3/rclone mount 不具备真实文件系统快照语义 必须替代 Docker 用 NAS/NFS/SMB 服务端快照或备份；K3s 用 NFS/SMB PVC + 备份任务

替代后的边界

替代前：
  MinIO/S3 bucket
    -> rclone mount 到宿主机
    -> sandbox volume 挂到容器 /by
    -> OpenClaw state、DB、ffmpeg、用户文件全部混在 /by

替代后：
  /by    = NAS/NFS/SMB 文件型 PVC，OpenClaw 运行态和用户文件
  MinIO  = 对象存储，用户文件、最终产物、备份、资源包
  S3 SDK = OpenClaw 或后端在 /by 与 MinIO 之间搬运需要归档/共享的文件

因此，架构上的“完全替代”应该理解为：完全移除 OpenClaw 容器对 S3/rclone mount 数据卷的依赖。MinIO 仍然可以保留为对象存储服务和备份目标。

风险矩阵

数据类型 当前落点 风险 推荐落点
OpenClaw state / agent home / gbrain state /by/.openclaw 高：可能包含 DB、索引、锁、状态文件 /by/.openclaw，但 /by 必须是 NAS/NFS/SMB 文件型存储
SQLite / PGLite / DuckDB / 向量索引 如果在 /by 下则危险 高：WAL、fsync、随机写、mmap、锁语义不可靠 /by/.openclaw 或 /by/db，前提是 /by 为文件型存储；高写入 DB 可后续拆到专用数据库或块存储
ffmpeg 转码输入、输出、临时分片 用户容易直接使用 /by 中高：seek、临时文件、输出回写慢且容易失败 单卷模式使用 /by/tmp 中转；高吞吐场景可额外挂 /work
node_modules / venv / pip npm cache / git 工作区 如果 HOME 或工作区在 /by 下则危险 中高：大量小文件、rename、锁、权限、性能问题 单卷模式使用 /by/.cache、/by/.openclaw/tools
用户上传文件、最终产物、导出包、日志归档 /by 低：对象存储适合整文件读写 S3/MinIO，优先 SDK，必要时只作为冷数据挂载

Docker 部署方案

定位

Docker 没有 Kubernetes PVC 抽象。当前升级目标应从“对象型存储 S3/rclone”切换为“文件型存储 NAS/NFS/SMB”。容器内仍然只挂一个 /by，但这个 /by 必须来自 NFS/SMB/NAS 这类原生文件系统，而不是 S3/rclone mount。块存储仍可作为高写入增强选项，但不是本次平移的主路线。

/by

Docker NFS/SMB volume 或 NAS 挂载目录。承载 OpenClaw 运行态和用户文件。

/by/tmp

单卷模式下的临时计算目录。高吞吐场景可额外挂本地 /work。

MinIO/S3

对象存储与备份目标，不再作为 OpenClaw 容器数据卷。

Docker Compose 示例

services:
  openclaw:
    image: 10.10.165.101:8080/byclaw/byclaw-openclaw:develop
    environment:
      OPENCLAW_STATE_DIR: /by/.openclaw
      OPENCLAW_HOME: /by/.openclaw/home
      DWS_CONFIG_DIR: /by/.openclaw/.dws
      TMPDIR: /by/tmp
    volumes:
      - openclaw_by_${USER_CODE}:/by

volumes:
  openclaw_by_${USER_CODE}:
    driver: local
    driver_opts:
      type: nfs
      o: addr=10.10.10.20,nfsvers=4.1,rw,hard,noatime
      device: ":/exports/byclaw/byclaw-${USER_CODE}/by"

Docker 版 Spec.json 建议

建议保持 Spec 单卷模型，只替换 hostPath 的含义：它应该指向宿主机上的 NAS/NFS/SMB 文件型存储挂载根目录，而不是 ${FILE_STORAGE_MINIO_MOUNT_PATH} 这种对象型存储 rclone 根目录。 

{
  "env": {
    "OPENCLAW_STATE_DIR": "/by/.openclaw",
    "OPENCLAW_HOME": "/by/.openclaw/home",
    "DWS_CONFIG_DIR": "/by/.openclaw/.dws",
    "TMPDIR": "/by/tmp"
  },
  "volumes": [
    {
      "key": "base",
      "scope": "PRIVATE",
      "hostPath": "${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}",
      "subPath": "byclaw-${user_code}/by",
      "mountPath": "/by",
      "readOnly": false
    }
  ],
  "bootstrap": {
    "copyTemplate": {
      "copyIfMissing": true,
      "targetVolumeKey": "base"
    }
  }
}

这里 bootstrap.copyTemplate.targetVolumeKey 可以继续使用 base，因为 base 已经不是 S3/rclone mount，而是 NAS/NFS/SMB 文件型存储。

Docker 备份与快照恢复

文件型存储 备份/快照方式 恢复方式
企业 NAS 使用 NAS 原生快照、克隆、回滚能力 从 NAS 快照恢复用户目录后重启容器
NFS 导出目录 由 NFS 服务端底层 ZFS/Btrfs/LVM/NAS 快照承载 恢复服务端目录；客户端 Docker volume 无需感知
SMB/CIFS 共享 由 Windows 文件服务器、NAS 或后端卷提供快照 从共享目录快照恢复，再重新启动 OpenClaw
无原生快照的普通文件服务器 定时 rsync / restic / borg 到备份仓库 从备份集恢复到用户目录

Docker 多机分布式不建议再使用 rclone/S3 mount。若以文件型存储为升级目标，推荐直接使用企业 NAS/NFS/SMB 作为共享文件系统后端；它能解决 S3 对象存储语义问题。若后续出现高写入 DB 压力，再把这类强写入状态迁到块存储或 K3s PVC。

文件型网盘 PVC 方案

需要明确区分两类“网盘”：文件型网盘 和 对象型网盘。文件型网盘例如 NAS、NFS、SMB，本质上就是文件系统服务，可以直接作为 Docker volume 或 K3s PVC 的后端；对象型网盘例如 S3、OSS、COS、MinIO，本质上是对象存储，只有通过 FUSE 或 CSI 模拟文件系统，仍然会存在原子性、锁、权限、目录性能、随机写等兼容性问题。

因此，如果你们有 NAS/NFS/SMB 这类文件型存储，把 /by 改为文件型网盘 PVC，是最接近“平移原有 /by 数据卷体验”的方案，并且能彻底避开 S3 对象存储语义带来的兼容性问题。

开源文件型存储服务技术选型

选型 定位 Docker 原地升级 K3s/PVC 管理界面 推荐结论
CephFS + Rook-Ceph 开源分布式 POSIX 文件系统。CephFS 官方定位为 POSIX-compliant file system；Rook-Ceph 支持 CephFS RWX PVC。 可通过 CephFS kernel mount 或 NFS-Ganesha 暴露给 Docker 宿主机。 直接用 rook-cephfs StorageClass 创建 RWX PVC。 Ceph Dashboard 可看 CephFS、NFS、池和使用情况；文件树仍建议配 File Browser。 生产分布式首选，但运维复杂度最高。
OpenMediaVault + NFS/SMB 基于 Debian 的开源 NAS 方案，提供 SMB/CIFS、NFS、FTP 等文件服务。 Docker 用 NFS/SMB volume 挂载 OMV 共享目录到 /by。 K3s 用 NFS CSI 或 SMB CSI 连接 OMV 共享目录。 OMV 自带 Web 管理界面，管理共享目录、权限、服务、磁盘。 中小规模、快速落地首选，比 Ceph 简单。
Samba / NFS server 最小化开源文件服务。Samba 提供 SMB 文件服务；Linux NFS server 提供 NFSv4。 Docker local volume 使用 NFS/SMB driver_opts，或宿主机预挂载后 bind mount。 K3s 使用 NFS CSI / SMB CSI。 无完整 NAS 控制台，需要配合 Cockpit、File Browser 或自建管理页。 适合轻量部署，管理面需要补齐。
Longhorn RWX 开源 K8s 存储。RWX volume 通过 Longhorn share-manager Pod 暴露 NFSv4.1。 不适合 Docker 原地方案。 K3s 中可直接创建 RWX PVC。 Longhorn UI 管 volume、replica、snapshot、backup；文件树仍用 File Browser。 K3s 简化选项，本质是 Longhorn 卷 + NFS 导出。
SeaweedFS 开源分布式存储，提供 filer、S3、FUSE 等能力。 可通过 FUSE/挂载方式接入。 需评估 CSI/FUSE 路径。 有自带服务组件和生态工具。 不作为本方案首选，因为目标是摆脱 FUSE/对象存储模拟文件系统风险。

本项目建议按规模选择：如果要快速从 MinIO/rclone 平移，先用 OpenMediaVault + NFSv4 或 Samba/NFS server；如果要建设长期分布式生产存储，选择 Rook-Ceph + CephFS；如果已经在 K3s 里使用 Longhorn，且希望最少组件完成 RWX 文件卷，可以评估 Longhorn RWX。

文件型网盘与对象型网盘对比

类型 例子 能否直接承载 /by 原因 推荐定位
文件型网盘 NAS、NFSv4、SMB/CIFS、企业文件存储 可以 原生文件系统语义，支持目录、权限、rename、随机读写、锁等 POSIX/类 POSIX 能力。 可直接作为 /by PVC 或 Docker volume 后端。
对象型网盘 S3、OSS、COS、MinIO bucket 不建议 对象存储是 GET/PUT/LIST 语义，需要 s3fs、goofys、rclone 或 CSI 模拟文件系统。 用于对象归档、共享、备份目标，不作为运行态文件系统。
块存储增强选项 Longhorn、Ceph RBD、云盘、SAN 可以 提供块设备，在其上格式化 ext4/xfs，文件系统语义完整。 高写入 DB、WAL、核心状态增强选项，不是本次文件型存储平移主线。

基于 NFS 的 K3s PVC

K3s 中可以使用 NFS CSI driver 或 nfs-subdir-external-provisioner 把 NAS/NFS 目录动态切成 PVC。OpenClaw 容器仍然只挂载一个 /by。 

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: byclaw-nfs
provisioner: nfs.csi.k8s.io
parameters:
  server: 10.10.10.20
  share: /exports/byclaw
reclaimPolicy: Retain
volumeBindingMode: Immediate
mountOptions:
  - nfsvers=4.1
  - hard
  - noatime
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: openclaw-by-user-001
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: byclaw-nfs
  resources:
    requests:
      storage: 20Gi

对单用户单 OpenClaw 实例，ReadWriteOnce 或 ReadWriteMany 都可工作；如果要让 File Browser、迁移 Job、备份 Job 同时挂载同一个用户卷，NFS/SMB 的 ReadWriteMany 会比块存储 RWO 更方便。

基于 SMB/CIFS 的 K3s PVC

如果现有企业网盘是 Windows 文件共享或 SMB NAS，可使用 SMB CSI driver。注意把账号密码放入 Secret，不要写进 Spec。 

apiVersion: v1
kind: Secret
metadata:
  name: smbcreds
type: Opaque
stringData:
  username: byclaw
  password: change-me
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: byclaw-smb
provisioner: smb.csi.k8s.io
parameters:
  source: //10.10.10.30/byclaw
  csi.storage.k8s.io/node-stage-secret-name: smbcreds
  csi.storage.k8s.io/node-stage-secret-namespace: default
reclaimPolicy: Retain
volumeBindingMode: Immediate
mountOptions:
  - dir_mode=0770
  - file_mode=0660
  - cache=strict
  - noperm

基于 NFS/SMB 的 Docker volume

Docker 原地升级也可以直接把 /by 绑定到 NFS/SMB volume。这样不需要 K3s，也能把 rclone/S3 根目录替换为文件型网盘。 

services:
  openclaw:
    image: 10.10.165.101:8080/byclaw/byclaw-openclaw:develop
    environment:
      OPENCLAW_STATE_DIR: /by/.openclaw
      DWS_CONFIG_DIR: /by/.openclaw/.dws
      TMPDIR: /by/tmp
    volumes:
      - openclaw_by_user001:/by

volumes:
  openclaw_by_user001:
    driver: local
    driver_opts:
      type: nfs
      o: addr=10.10.10.20,nfsvers=4.1,rw,hard,noatime
      device: ":/exports/byclaw/byclaw-user001/by"

文件型网盘能解决什么

问题 S3/rclone NAS/NFS/SMB
随机读写 模拟，风险高 原生文件系统能力
rename / 临时文件 可能退化为复制/删除 文件系统原语
目录性能 LIST 对象，目录是模拟概念 真实目录结构
权限 由 FUSE 层模拟 由 NAS/NFS/SMB 提供
File Browser 浏览 可浏览，但底层语义仍是对象存储 直接浏览真实文件系统

仍需注意的边界

文件型网盘可以彻底解决 S3 对象存储语义导致的文件系统兼容性问题，但它不是万能的本地 NVMe。高并发 DB、重度 SQLite/PGLite、频繁 fsync 的场景仍要关注 NAS 性能、锁实现、网络延迟和故障恢复策略。若运行态 DB 写入压力很高，分布式块存储或本地块存储仍然比 NFS/SMB 更稳。

推荐分层：普通 OpenClaw 工作区、用户文件、File Browser 浏览用 NAS/NFS/SMB PVC；对强一致、高写入 DB 或核心状态，优先 Longhorn/Ceph RBD 这类块存储 PVC。

Docker 原地升级专项方案

本节针对当前 openSandbox + Docker 架构给出可执行升级方案。目标是在不切换 K3s 的情况下，保持 Spec.json 单卷 /by 模型，把 /by 背后的对象型 S3/rclone 网盘替换成文件型 NAS/NFS/SMB 存储，从而彻底解决对象存储语义导致的文件系统兼容性问题。

这里的“文件型存储”不是部署服务器自己的本地目录，而是一套独立部署的开源文件存储服务。OpenMediaVault、Samba/NFS server、Rook-Ceph/CephFS 运行在存储服务器或存储集群上；ByClaw 和 openSandbox 所在服务器通过网络挂载它提供的 NFS、SMB 或 CephFS。

1. 远端文件存储服务拓扑

所有 openSandbox Docker 节点都要把远端共享目录挂到一致的本地路径，例如 /mnt/byclaw-file。OpenClaw 容器仍只看到 /by，但 /by 的真实来源已经从 rclone/S3 变成远端文件系统。 

[文件存储服务器或存储集群]
  OpenMediaVault / Samba+NFS / CephFS
  export: /exports/byclaw
        |
        | NFSv4 / SMB3 / CephFS
        |
[openSandbox Docker Host A]  mount -> /mnt/byclaw-file
[openSandbox Docker Host B]  mount -> /mnt/byclaw-file
        |
        | ${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${user_code}/by
        |
[OpenClaw container] /by

ByClaw BE 可以不直接挂载这套文件系统；它主要通过 OpenSandboxClient.createSandbox() 请求 openSandbox 创建沙箱。真正必须挂载远端文件存储的是运行 OpenClaw 容器的 openSandbox Docker 节点。如果后端还要做模板复制、迁移或管理端文件预览，也可以额外挂载受控目录，但这不是容器运行态持久化的必要条件。

2. 技术选型、系统架构、流程

能力 推荐选型 说明
运行态卷 远端 NFS/SMB/CephFS 共享目录 + openSandbox 节点统一挂载根 最少改造。openSandbox 把 PRIVATE volume 映射到 BYCLAW_SANDBOX_FILE_VOLUME_ROOT。
底层文件型存储 短期优先 OpenMediaVault + NFSv4/SMB；长期分布式优先 Rook-Ceph + CephFS 文件存储服务不与部署服务器同机。快照、配额、共享目录和权限在存储服务端统一管理。
Docker 管理面 Portainer 管理容器、镜像、volume、绑定关系。可作为现有 Docker 运维 UI。
文件浏览面 File Browser 替代 MinIO Console 的文件树浏览体验，挂载用户 /by 数据卷。
对象存储 保留 MinIO/S3 不再作为 /by 文件系统来源，只做归档、共享、备份目标。

Docker 原地升级后的系统流程：

ByClaw BE
  -> OpenSandboxClient.createSandbox()

  -> 解析 volume: scope=PRIVATE, subPath=byclaw-${user_code}/by, mountPath=/by

  -> OpenClaw 在 /by 上运行，/by 背后是 NAS/NFS/SMB，不再是 rclone/S3

需要在 openSandbox 服务端新增或调整配置，不建议继续复用 FILE_STORAGE_MINIO_MOUNT_PATH：

BYCLAW_SANDBOX_FILE_VOLUME_TYPE=nfs|smb|bind

3. 项目代码改造点（CodeGraph 结论）

CodeGraph 对当前链路的结论是：ByClaw 后端会解析 Spec.json，但在 openSandbox 路线下最终只把卷的 mountPath、name、readOnly、subPath、scope 发给 openSandbox，不会把 hostPath 传过去。因此，单独把 Spec.json 里的 hostPath 改成新环境变量，不足以保证运行态离开 rclone/S3；必须同步改 openSandbox 服务端的 PRIVATE 卷后端。

位置 当前行为 升级要求
Spec.json base 卷挂到 /by，旧 hostPath 来自 ${FILE_STORAGE_MINIO_MOUNT_PATH}。 继续保持单卷 /by，但文档和默认配置改为 ${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}。这个变量指向 openSandbox 节点上的远端文件存储挂载根。
GenericSandboxSpecProcessor.buildVolumes 会渲染 hostPath、subPath、mountPath 并构造 volume。 保留兼容。它能表达新 Spec，但不是 openSandbox 真正 bind mount 的最终执行者。
SandboxRuntimeRequestFactory.buildVolumesPayload 发送给 openSandbox 的 payload 不包含 hostPath。 推荐不扩大 payload 合约，而是在 openSandbox 服务端配置 BYCLAW_SANDBOX_FILE_VOLUME_ROOT。如果要由 ByClaw 控制 hostPath，则需要同步改 ByClaw 和 openSandbox API，改造面更大。
OpenSandboxRuntimeProvider 调用 OpenSandboxClient.createSandbox()，把容器创建委托给远端 openSandbox。 保持 provider 不变；升级重点放在 openSandbox Docker runtime 如何解释 PRIVATE volume。
MinioBucketMountSupport.buildMountCommand 构造 rclone mount ':s3:<bucket>' 命令，旧路线把对象存储模拟成文件系统。 从 OpenClaw 运行态链路移除。MinIO 可以继续作为对象归档和备份目标，但不能再作为 /by 的文件系统来源。
InitMinioBucketMountRunner.run file.storage.type=minio 时初始化公共 bucket；当前代码只调用 resourceFS.init()。 保留对象存储初始化也可以，但要和运行态卷解耦。不要再把这个 runner 的 mount 配置当成 OpenClaw /by 的供应方式。
ByclawUserFS / ByClawUserWorkspacePaths 项目内大量路径约定仍以 /by 作为用户工作区和 OpenClaw state 根。 不需要迁移容器内路径。只替换 /by 的底层存储，能最大限度减少业务代码改动。

Docker 原地升级的项目改造顺序应是：先给 openSandbox 增加文件型卷根配置；再把默认 Spec、数据库初始化 SQL、部署变量中出现的 FILE_STORAGE_MINIO_MOUNT_PATH 替换为运行态专用的 BYCLAW_SANDBOX_FILE_VOLUME_ROOT；最后把 MinIO/rclone mount 从 OpenClaw 运行态部署手册和启动脚本中下线。

4. 迁移方案

迁移原则：保持容器内 /by 路径和 byclaw-${user_code}/by 子目录结构不变，只替换底层存储。

# 1. 停止或冻结目标用户的 OpenClaw 容器，避免迁移期间继续写旧 rclone 目录
opensandbox stop openclaw-${USER_CODE}

# 2. 在远端文件存储服务上准备共享目录
ssh storage-server "mkdir -p /exports/byclaw/byclaw-${USER_CODE}/by"
ssh storage-server "chown -R 0:0 /exports/byclaw/byclaw-${USER_CODE}"

# 3. 在每台 openSandbox Docker 节点挂载远端文件存储到同一路径
mount -t nfs4 storage-server:/exports/byclaw /mnt/byclaw-file

# 4. 从旧 MinIO/S3 迁移数据到新文件型存储
mc alias set oldminio http://MINIO:9000 ACCESS_KEY SECRET_KEY
mc mirror --overwrite oldminio/byclaw-${USER_CODE}/by \
  /mnt/byclaw-file/byclaw-${USER_CODE}/by

# 5. 切换 openSandbox 卷根目录配置
BYCLAW_SANDBOX_FILE_VOLUME_ROOT=/mnt/byclaw-file

# 6. 重启 OpenClaw，容器内仍然看到 /by
opensandbox start openclaw-${USER_CODE}

# 7. 灰度确认无误后，旧 rclone mount 只读保留一段时间，再下线

批量迁移时建议按用户维度分批：先迁移测试用户，再迁移低活跃用户，最后迁移高活跃用户。每个用户迁移完成后记录旧对象版本、迁移时间、目标卷路径、校验结果。

5. 验证方案

验证项 方法 通过标准
远端挂载一致性 在每台 openSandbox Docker 节点执行 findmnt /mnt/byclaw-file 和 touch /mnt/byclaw-file/.probe。 所有节点看到同一个远端文件存储，路径一致，读写权限一致。
卷来源验证 进入 OpenClaw 容器执行 df -T /by、mount | grep /by /by 不显示 fuse.rclone、s3fs、goofys 等对象存储挂载；应显示 nfs、cifs/smb3、cephfs 或文件型存储服务对应类型。
随机写验证 在 /by/.openclaw 下跑 SQLite WAL 写入、创建/rename/删除大量小文件。 无锁错误、无 I/O error，性能稳定。
ffmpeg 验证 在 /by/tmp 中转码大文件，输出到 /by/output。 seek、临时文件、最终输出均正常。

6. 新方案下分布式支持方案

Docker 原地升级的分布式能力取决于远端文件存储服务，而不是 Docker 自身。建议按成熟度分三档：

等级 方案 适用性 限制
L1 远端单节点文件服务 OpenMediaVault 或 Samba/NFS server 独立部署，openSandbox 节点通过 NFS/SMB 挂载 最简单，适合先替代 MinIO/rclone 数据卷。 文件服务节点需要 RAID、快照和备份；它不是部署服务器本机目录。
L2 多节点文件服务 企业 NAS / NFSv4 / SMB / HA NFS 共享到多台 openSandbox Docker 宿主机 推荐的 Docker 分布式升级路线。多节点都能看到同一个文件型存储根。 需要保证同一用户同一时刻只有一个 OpenClaw 写入，避免应用级并发写冲突。
L3 分布式文件系统 Rook-Ceph + CephFS，或 K3s + NFS/SMB/CephFS CSI PVC 长期推荐的文件型存储云原生路线。PVC、调度、文件浏览、备份流程统一。 需要从 Docker runtime 演进到 Kubernetes runtime。

如果坚持 Docker 多机，推荐 NFS/SMB/NAS 这类文件型存储承载 /by，不要再使用 rclone/S3 mount。NFS/SMB 能解决对象存储文件语义不兼容问题；若后续发现 SQLite/PGLite 等高频写状态压力较大，再把这部分状态单独迁到块存储或外部数据库。

7. 类 MinIO 控制面板的替代方案

NAS/NFS/SMB 文件型存储不是对象存储，所以不会天然提供 MinIO Console 那种 bucket/object 页面。需要组合替代：

需求 Docker 方案 说明
看卷、容器、挂载关系 Portainer 查看 Docker volumes、容器挂载、运行状态；适合运维面。
看 /by 文件树 File Browser 挂载用户卷到 File Browser，提供类似 MinIO Console 的文件浏览、下载、上传能力。
看快照和恢复点 OpenMediaVault UI、Ceph Dashboard、Cockpit/Samba 管理页，或自建运维页面 Docker 本身没有统一快照 UI；文件型存储的共享、快照、备份由开源文件存储服务侧提供。
看对象归档 保留 MinIO Console 只查看归档、备份、共享文件，不代表 OpenClaw 运行态文件系统。

项目内替代落地建议：先部署开源文件型存储服务控制面板，例如 OpenMediaVault UI 或 Ceph Dashboard；再部署一个受控的 File Browser 作为“用户卷文件查看器”，只挂载当前用户的 /by，默认只读；管理端继续用 Portainer 看 Docker volume；快照恢复能力先通过脚本封装，再逐步接入 ByClaw 管理后台。

Docker 原地升级与 K3s 切换对比

当前 openSandbox + Docker 基线

当前 ByClaw 后端使用 OpenSandboxRuntimeProvider 调用 openSandbox API 创建沙箱。GenericSandboxSpecProcessor 会根据 Spec.json 生成 volume，但 SandboxRuntimeRequestFactory.buildVolumesPayload 传给 openSandbox 的 volume payload 只包含 mountPath、name、readOnly、subPath、scope，不包含 hostPath。

因此，在当前 openSandbox + Docker 架构下，能否彻底解决问题，不取决于 ByClaw 后端 Java 代码里写了什么 hostPath，而取决于 openSandbox 服务端如何解释 scope=PRIVATE、subPath=byclaw-${user_code}/by 和 mountPath=/by。

路线 改造范围 是否能彻底解决 S3 文件系统问题 系统级快照恢复 适合阶段
Docker 原地升级 保留 openSandbox + Docker；把 openSandbox 的 PRIVATE 卷后端从 rclone/S3 mount 改为 NAS/NFS/SMB 文件型存储根目录 可以。前提是 /by 的真实来源不再经过 S3/rclone/s3fs 由 NAS/NFS/SMB 服务端或其底层存储提供快照/备份 当前架构快速止血、改动最小
K3s 切换 openSandbox 改成 K3s runtime，或新增 Kubernetes sandbox runtime；每个用户/沙箱创建 PVC 并挂到 /by 可以。前提是 PVC 来自 NFS/SMB/CephFS 等文件型存储，而不是 S3 CSI/FUSE Kubernetes PVC + 文件存储快照/备份；强写入增强场景另行评估块存储 分布式生产、统一运维、长期演进
只改 Spec.json，不改 openSandbox 卷后端 仅把环境变量或 hostPath 名称改掉 不可以。当前 openSandbox payload 不传 hostPath，服务端仍可能用旧 rclone/S3 根目录 仍然没有真实文件型存储快照/备份 不推荐
部署图：Docker 原地升级 vs K3s PVC 化

Docker 原地升级需要改什么

Docker 路线可以彻底解决，而且是最贴近当前 openSandbox 架构的路线。关键不是把 /by 拆成多个目录，而是把 openSandbox 的卷供应逻辑改成： 

收到 volume:
  scope=PRIVATE
  subPath=byclaw-${user_code}/by
  mountPath=/by

旧实现：
  /by <- ${FILE_STORAGE_MINIO_MOUNT_PATH}/byclaw-${user_code}/by
        其中 ${FILE_STORAGE_MINIO_MOUNT_PATH} 是 rclone/S3 mount

新实现：
  /by <- ${BYCLAW_SANDBOX_FILE_VOLUME_ROOT}/byclaw-${user_code}/by
        其中 ${BYCLAW_SANDBOX_FILE_VOLUME_ROOT} 是 NAS/NFS/SMB 文件型存储挂载点

这条路可以继续使用当前 Spec.json 的单卷模型。为了避免误配置，建议新增专门的 openSandbox 配置项，例如 BYCLAW_SANDBOX_FILE_VOLUME_ROOT，不要复用 FILE_STORAGE_MINIO_MOUNT_PATH。

K3s 切换需要改什么

K3s 路线更完整，但需要运行时能力升级。当前 ByClaw 的 openSandbox client 只是把 volume 抽象交给远端 openSandbox；如果远端 openSandbox 仍是 Docker runtime，它不会自动拥有 Kubernetes PVC 能力。因此需要二选一：

  • 改造 openSandbox 服务端，让它在 K3s 中创建 Pod、PVC、Service，并把用户 PVC 挂载到容器 /by。
  • 在 ByClaw 增加新的 Kubernetes sandbox runtime provider，绕过 Docker openSandbox，直接用 Kubernetes API 创建 OpenClaw Pod/PVC。

K3s 方案的优势是：PVC、调度、服务发现、生命周期管理都标准化；当 StorageClass 使用 NFS/SMB CSI 时，/by 背后就是文件型存储。代价是从 Docker 编排切换到 Kubernetes 编排，需要处理镜像拉取、Service 暴露、endpoint 解析、沙箱复用、超时续期、删除回收等运行时逻辑。

是否都能彻底解决

两条路线都能彻底解决，但必须满足同一个硬条件：OpenClaw 容器内的 /by 不能来自对象存储挂载，必须来自 NAS/NFS/SMB 这类文件型存储服务。

Docker 原地升级的彻底性取决于 openSandbox 服务端卷后端是否已经切到文件型存储；K3s 切换的彻底性取决于 PVC 的 StorageClass 是否是 NFS/SMB/CephFS 这类文件型存储，而不是 S3 CSI 或 FUSE 类驱动。

K3s 部署方案

定位

K3s 版推荐使用 Kubernetes PVC。当前升级目标是文件型存储，因此 StorageClass 优先选择 NFS CSI 或 SMB CSI，让 /by 直接来自 NAS/NFS/SMB。Longhorn/Ceph RBD 这类块存储保留为高写入 DB 或核心状态增强选项；S3/MinIO 只作为对象存储和备份目标。

K3s 里的 PVC 同样不要求文件存储服务和 K3s 节点同机。推荐把 OpenMediaVault、Samba/NFS server 或 CephFS 作为独立存储服务部署在存储服务器/存储集群上，再由 NFS CSI、SMB CSI 或 CephFS CSI 把远端共享目录供应成 PVC。这样 Pod 只消费标准 PVC，不直接碰 S3/FUSE。

NFS / SMB PVC

/by 的真实文件型存储，支持目录、权限、rename、随机读写。

可选 emptyDir / local SSD

高吞吐 ffmpeg 或编译场景可额外挂 /work。最小改造不需要。

S3 / MinIO

归档、共享、备份目标，不作为热文件系统。

PVC 与 Pod 示例

示例中的 byclaw-nfs StorageClass 应指向远端文件存储服务的导出目录，而不是 K3s 节点本地目录。多节点 K3s 下，调度到任意节点的 OpenClaw Pod 都应通过 CSI 挂到同一个远端文件系统。 

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: openclaw-by-user-001
spec:
  accessModes:
    - ReadWriteMany
  storageClassName: byclaw-nfs
  resources:
    requests:
      storage: 20Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: openclaw-user-001
spec:
  replicas: 1
  selector:
    matchLabels:
      app: openclaw-user-001
  template:
    metadata:
      labels:
        app: openclaw-user-001
    spec:
      containers:
        - name: openclaw
          image: 10.10.165.101:8080/byclaw/byclaw-openclaw:develop
          env:
            - name: OPENCLAW_STATE_DIR
              value: /by/.openclaw
            - name: OPENCLAW_HOME
              value: /by/.openclaw/home
            - name: DWS_CONFIG_DIR
              value: /by/.openclaw/.dws
            - name: TMPDIR
              value: /by/tmp
          volumeMounts:
            - name: by
              mountPath: /by
      volumes:
        - name: by
          persistentVolumeClaim:
            claimName: openclaw-by-user-001

文件型 PVC 的备份与恢复

NFS/SMB 文件型 PVC 的快照能力通常不由 Kubernetes VolumeSnapshot 直接提供，而是由 NAS、文件服务器或其底层 ZFS/Btrfs/LVM 实现。K3s 侧建议用 CronJob 做目录级备份，或调用 NAS API 触发快照。 

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-openclaw-by-user-001
spec:
  schedule: "0 */6 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: alpine:3.20
              command: ["sh", "-lc", "tar -C /by -czf /backup/openclaw-by-user-001-$(date +%Y%m%d%H%M).tgz ."]
              volumeMounts:
                - name: by
                  mountPath: /by
                  readOnly: true
                - name: backup
                  mountPath: /backup
          volumes:
            - name: by
              persistentVolumeClaim:
                claimName: openclaw-by-user-001
            - name: backup
              persistentVolumeClaim:
                claimName: byclaw-backup-store

K3s 版 Spec 接入建议

如果现有 sandbox runtime 已支持 Kubernetes PVC 类型，可以保持 Spec 单卷 /by，由运行时把 scope=PRIVATE 的 base 卷映射到用户级 PVC。如果暂时只支持 hostPath/subPath，可以由 sandbox runtime 在 K3s 节点上把 PVC 挂载路径暴露为 hostPath，但推荐直接扩展运行时支持 PVC。 

{
  "env": {
    "OPENCLAW_STATE_DIR": "/by/.openclaw",
    "OPENCLAW_HOME": "/by/.openclaw/home",
    "DWS_CONFIG_DIR": "/by/.openclaw/.dws",
    "TMPDIR": "/by/tmp"
  },
  "volumes": [
    {
      "key": "base",
      "scope": "PRIVATE",
      "mountPath": "/by",
      "readOnly": false
    }
  ]
}

对象存储与备份 MinIO/S3 保留为归档、跨服务共享、卷备份目标 MinIO/S3 作为业务对象存储和备份归档目标 不再作为 /by 文件系统来源
数据迁移 mc mirror 或 rclone sync 从 MinIO bucket 同步到新 /by 卷 迁移 Job 挂载 PVC，同时使用 mc mirror 从 MinIO 拉取对象 保持原有 byclaw-${user_code}/by 目录结构平移

为什么仍需要 File Browser

NAS 控制台、Portainer、Kubernetes Dashboard 或 Rancher 管的是共享目录、卷、PVC、容器和容量，不一定提供面向 OpenClaw 用户的文件树视图。要像 MinIO Console 一样展示 /by/.openclaw、/by/output 这种文件内容，仍需要 File Browser 这类文件管理 Web UI。

要平移 MinIO Console 的“看文件”体验，需要额外部署 File Browser 这类文件管理 Web UI。File Browser 官方定位就是自托管的文件和目录管理 Web 应用，支持多用户、权限、角色和 home 目录。Docker 侧也可以用 Portainer 查看和浏览 volume；Portainer 文档说明它可以查看 Docker volumes，并在 Swarm/Agent 场景浏览已有 volumes。

K3s 管理面

Kubernetes / Rancher / Dashboard:
  - 查看 PVC、Pod、挂载关系
  - 查看 StorageClass、容量请求、事件

NAS 控制台:
  - 查看 NFS/SMB 共享目录
  - 查看容量、配额、快照、备份
  - 从文件系统快照恢复用户目录

File Browser:
  - 挂载 openclaw-by-user-001 PVC 到 /srv
  - Web 页面浏览 /srv/.openclaw、/srv/workspace、/srv/output
  - 建议默认只读；需要修复文件时临时开启写权限

Docker 管理面

Portainer:
  - 查看 openclaw_by_${USER_CODE} volume
  - 查看容器与 volume 绑定关系
  - 管理容器、镜像、网络、volume

NAS / 文件服务器控制台:
  - NFS/SMB 共享目录
  - 用户目录配额
  - 快照 / 克隆 / 回滚 / 备份

File Browser:
  - 挂载同一个 /by 数据卷
  - 提供类似 MinIO Console 的文件树浏览体验

MinIO 到 PVC 的迁移

迁移原则是保持容器内 /by 看到的目录结构不变。当前 Spec 使用 subPath=byclaw-${user_code}/by，因此新的 NAS/NFS/SMB 文件型存储根目录也建议保留这个结构，降低后端路径和用户文件查询逻辑的变更成本。

迁移流程图：从 MinIO/rclone 平移到 /by 文件型存储
# 1. 准备新 NAS/NFS/SMB 文件型存储目录
mkdir -p /mnt/byclaw-nas/byclaw-${USER_CODE}/by

# 2. 从 MinIO/S3 迁移对象到文件型存储目录
# mc mirror 支持在 filesystem、MinIO、S3-compatible hosts 之间同步。
mc alias set oldminio http://MINIO:9000 ACCESS_KEY SECRET_KEY
mc mirror --overwrite oldminio/byclaw-${USER_CODE}/by /mnt/byclaw-nas/byclaw-${USER_CODE}/by

# 3. 启动 OpenClaw 时仍挂载同一个容器路径
/mnt/byclaw-nas + subPath byclaw-${USER_CODE}/by -> /by

# 4. 灰度校验后冻结旧 rclone mount，只保留 MinIO/S3 作为对象存储和备份层

访问控制建议

  • NAS 控制台、Portainer、Kubernetes Dashboard/Rancher、File Browser 都必须放在内网或管理网，接入统一身份认证。
  • File Browser 默认只读挂载用户文件型 PVC；写操作通过工单或短时授权开启。
  • K3s 使用 NFS/SMB RWX PVC 时，File Browser 可以并行只读查看；写权限仍需严格控制，避免破坏 OpenClaw 运行态。
  • MinIO Console 保留给对象存储管理员，不再作为 OpenClaw 运行态文件查看入口。

数据流改造

ffmpeg

# 不推荐
ffmpeg -i /by/input/video.mp4 ... /by/output/out.mp4

# 推荐：/by 已经是 NAS/NFS/SMB 文件型存储时，可以直接在 /by/tmp 中转
mkdir -p /by/tmp/session-001
cp /by/input/video.mp4 /by/tmp/session-001/input.mp4
ffmpeg -i /by/tmp/session-001/input.mp4 ... /by/tmp/session-001/out.mp4
mv /by/tmp/session-001/out.mp4 /by/output/out.mp4

数据库

# 不推荐
/by/.openclaw/app.sqlite
/by/.openclaw/pglite

# 推荐：/by 为 NAS/NFS/SMB 文件型存储时
/by/.openclaw/app.sqlite
/by/.openclaw/pglite

# 备份到冷存储
sqlite3 /by/.openclaw/app.sqlite ".backup '/by/backups/app.sqlite'"

对象存储访问

长期方向建议把 /by 变成 NAS/NFS/SMB 文件型运行态卷；上传、下载、列目录、签名 URL 继续通过 MinIO/S3 API 表达对象存储语义。需要归档或跨服务共享的文件，从 /by 同步到对象存储。

一致性与快照策略

一致性级别 适用场景 动作
Crash-consistent 普通文件、缓存、可重建索引 直接卷快照，恢复后按崩溃恢复处理
Filesystem-consistent 本地文件系统状态需要更稳时 快照前停写或 fsfreeze，快照后解冻
Application-consistent SQLite/PGLite/Postgres/MySQL 等 DB 先 checkpoint/flush/数据库备份，再卷快照

对 OpenClaw 推荐默认使用 NAS 服务端快照或目录级备份，并为明确的 DB 文件增加 pre-backup hook：暂停 agent 写入、执行 checkpoint 或数据库备份、再触发文件型存储快照/备份。

落地路线

  1. 保持 OpenClaw spec 单卷模型：base 继续挂载到 /by。
  2. 把 base.hostPath 的来源从 ${FILE_STORAGE_MINIO_MOUNT_PATH} 改成 openSandbox 节点上的远端文件存储挂载根、Docker NFS/SMB volume 根目录或 K3s NFS/SMB/CephFS PVC。
  3. OPENCLAW_STATE_DIR、DWS_CONFIG_DIR、OpenClaw HOME 可以继续位于 /by/.openclaw，因为 /by 已经不是 S3/rclone mount。
  4. 让 ffmpeg、解压、编译、包管理器缓存默认使用 /by/tmp、/by/.cache 或 /by/.openclaw/tools。
  5. Docker 原地升级优先使用 NAS/NFS/SMB 文件型存储；分布式生产使用 K3s + NFS/SMB CSI PVC。高写入 DB 可按需独立迁到块存储。
  6. 把 S3/rclone mount 从“运行时磁盘”移除；需要对象存储能力时走 MinIO/S3 SDK 或后台同步。

最终判断

彻底避免 S3/rclone 文件系统兼容性问题的办法，不是调大 rclone cache，而是让运行态不落在 S3 mount 上。

Docker 版用 NAS/NFS/SMB 文件型存储承载 /by，由 NAS 或文件服务器做快照/备份；K3s 版用 NFS/SMB CSI PVC 承载 /by，由文件型存储或备份 Job 做恢复点。S3 仍然重要，但它的位置应该是对象存储和备份归档层，而不是 OpenClaw 的运行时文件系统层。
