# Tenant execution policy foundation

The commercial integration stores immutable full policy snapshots in `byai.tenant_execution_policy`. `tenant_policy_cursor` uses conditional updates to advance the desired revision and runtime generation; `tenant_policy_consumer` scopes acknowledgments to enterprise, policy revision, consumer and generation. Mutations require an actual database transaction. No network call occurs in these transactions.

`TenantExecutionPolicyService.prepare(long, JsonNode)` must run in the provisioning reservation transaction after both `COMMERCIAL_MANAGED=true` and `PACKAGE_CONTENT_SNAPSHOT` configuration rows exist. Initial `revision` must be the decimal string `"1"` and `accessMode` must be `PREPARED`. All six limit fields are required. Member/group/group-member/agent/parallel-task limits are integer counts (maximum signed 32-bit); memberLimit must be at least one. `storageBytes` is a non-negative decimal string within signed 64-bit range. Unknown fields and limits are rejected. Initial PREPARED policies can have null effective times; ENABLED requires both times.

`update(long, long expectedRevision, JsonNode)` requires a full snapshot with string revision equal to expectedRevision + 1. Cursor compare-and-swap and immutable snapshot insertion share the transaction. Stale updates cannot overwrite the current policy. A memberLimit change locks the existing package snapshot through a conditional database write/version increment, preserves its resource profile and other fields, and updates its memberLimit in the same transaction. Reducing a limit does not delete members. The internal add-member API coordinates its local admission with that same snapshot row. No member quota function or trigger is installed; complete organization-member and group-member admission will be implemented separately in application code.

`setGeneration(long, String)` advances the current decimal generation monotonically. `acknowledge(long, long policyRevision, String generation, String consumerKey)` accepts only the implemented `main-service` consumer and rejects stale revisions/generations. It fences against a concurrent cursor update. Node ACKs are rejected because a durable quota consumer does not yet exist. An acknowledgment never claims all consumers have applied a policy, and no fully-applied event is emitted.

## Admission and compatibility

`byclaw.tenant-policy.enabled` defaults to false. Unmanaged legacy tenants first check the existing `tenant_config` table and do not query new policy tables when enforcement is disabled. Commercially managed tenants always require their authoritative policy, including when global enforcement is disabled. Missing policy, PREPARED, READ_ONLY, SUSPENDED, future effectiveFrom and expired effectiveUntil deny ordinary execution. Database read errors propagate as failures rather than granting execution.

Deployment administrators may configure an explicit comma-separated positive enterprise ID list in `byclaw.tenant-policy.exempt-enterprise-ids` for verified LEGACY/EXEMPT compatibility. These are deployment decisions, not access modes accepted by the commercial HTTP policy API. There is no inferred exemption by enterprise name or missing commercial record. A main-service exemption does not activate commercially managed Node writes.

The Java admission aspect checks each `AssistantChatService.chat` call, including the explicit LoginInfo argument used by Netty, and user-context SandboxService launch, restart and renewal entry points. It does not gate history queries. The caller must install the correct tenant context for background work; unscoped context is denied when global enforcement is enabled. Global enforcement must remain disabled until the legacy classification and all background entry contexts have been verified.

Tenant Node receives immutable `COMMERCIAL_MANAGED=true` in its container environment for new commercial tenants. The lifecycle system environment projection preserves this flag. Node rechecks the Redis commercial marker before each new command application and every non-schema HTTP mutation. The immutable managed flag keeps the access-state check active even if the Redis marker disappears. Node reads the existing shared entitlement projection and permits ENABLED within its effective interval; a missing projection, disabled mode, invalid interval or expiry denies new mutations. No quota-capability flag or consumer ACK is required. A failed marker read also denies writes. Schema initialization and read-only history remain available. Existing unmanaged Nodes retain compatibility. Committed command receipt replay returns the recorded result without applying another mutation.

## Capabilities and incomplete scope

The safe policy projection includes enterpriseId, desiredRevision and generation as decimal strings, accessMode, UTC effective timestamps, fullyApplied, and a capability map. It includes no database credentials, provider tokens or arbitrary policy payload. `fullyApplied` is always false in this implementation.

The policy snapshot bridge and local quota checks do not establish complete quota enforcement across every writer. Capability flags and `fullyApplied=false` remain truthful. As explicitly requested on 2026-10-29, a valid ENABLED snapshot is now accepted and ordinary execution passes after mode/time checks. `PUT /internal/v1/tenants/{id}/execution-policy` returns a SUCCEEDED command when the snapshot is committed; this reports persistence, not every consumer's application. HACU observes READY from the original provision command, writes ENABLED using its existing immutable revision, then completes the subscription and binding without waiting for quota capabilities or ACKs.

The Node guard uses the existing shared entitlement reader for the access mode and effective interval instead of rejecting every commercial tenant. This adds no new consumer protocol or activation flag. Shared publication remains asynchronous; missing or not-yet-effective state may briefly deny Node writes after HACU completes. Deploy the Node changes as well as both backends; updating the BE image alone does not upgrade an already running Node sandbox.

The old OpenClaw HTTP/WebSocket proxy addresses a raw ip/port and has no verified target-tenant binding. Its existing direct execution, existing personal sandboxes, worker cron execution and autonomous runtime paths are not comprehensively governed by this foundation. A handshake-only check would not solve policy changes during a connection. Comprehensive governance of those entries remains separate work; it is no longer a prerequisite for first-time activation under the READY-based rule. This change does not claim complete BC-03/06 delivery.

## Verification

Policy persistence/admission tests use a real H2 JDBC transaction manager, covering preparation rollback, missing/expired policies, deployment-only exemptions, valid ENABLED admission, disabled/future/expired denial, CAS rejection and generation-fenced ACKs. Node test sources cover enabled commands, disabled/expired/invalid state, HTTP guard enforcement, legacy compatibility and projection loss. The 2026-10-29 regression sources were updated without running tests or builds; do not treat this as runtime verification. The isolated PostgreSQL 17 verification script (`byclaw-be/scripts/verify-tenant-integration-postgres.py`) also exercises the actual new DDL and verifies that no commercial member quota function or trigger is installed. The former trigger-based member concurrency checks were removed with that implementation; they are not evidence of current application-wide quota enforcement. openGauss compatibility, deployed baseline/grants, container environment propagation and cross-project integration still require environment acceptance.

When global policy enforcement is enabled, both ordinary enterprise creation (`EnterpriseInfoApplicationService.create`) and the old platform tenant creation (`TenantAdminTenantService.create`) reject with `COMMERCIAL_CREATION_REQUIRED` before database mutation. New commercial enterprises must use the authenticated reservation API. Global enforcement disabled preserves the existing creation behavior. Default-enterprise access and verified deployment exemptions govern existing enterprise execution only; they do not authorize creating an unclassified enterprise through a legacy entrance. Query, history and repair methods are not changed by this creation guard.
