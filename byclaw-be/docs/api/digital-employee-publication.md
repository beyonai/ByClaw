# 数字员工发布到官方推荐

当前规则（2026-10-08），开发分支 D0.5.0。本轮没有新增数据库迁移，没有修改 `baiying-enhance`。员工发布的新 A/B 方法仍独立实现；资源中心独立技能发布同步采用新的审核归属规则。

## 发布与编辑

开源和商业版本均支持个人数字员工发布。分享范围仍为本部署当前企业，沿用已有根组织 FORCE_USE 授权；版本开放不取消租户、角色、归属校验，也不引入新的多租户组织模型。超级助手、员工组和第三方接入员工仍不支持此流程。

发布申请的 `tenantId`、新员工的 `comAcctId` 均沿用原员工的 `comAcctId`，并校验当前登录企业一致。发布时锁定源员工并复核归属，更新已有副本时也要求副本与原员工企业一致。不再将 `po_enterprise_info` 中最大的 `enterprise_id` 作为发布范围判断依据，企业信息表中的其他记录不会阻止同企业员工发布。现有组织表没有企业 ID 字段，全员授权继续沿用本部署的组织树，不因此增加共享数据库下的多企业组织隔离能力。

升级前保存的草稿若仍显示“发布范围与当前部署企业不一致”，点击“保存待发布配置”重新生成校验结果即可；真实的登录企业不一致或缺少根组织仍会阻止发布。此调整无需修改数据库结构或手工更新已有员工归属。

个人员工 A 的配置、资源关系及权限保持不变。首次发布创建企业员工 B，名称追加本地化后缀：中文 `(企业)`，英文 ` (Enterprise)`。后缀在候选版本中展示并保存，审核语言不改已有后缀，重复保存不重复追加。最终名称仍需满足长度和企业内重名校验。已有企业员工 B 的更新沿用其名称，不自动重复加后缀。

A 的日常编辑保存始终通过普通员工更新接口直接生效。已发布、存在草稿、待审或驳回记录均不改变 A 的保存方式；个人编辑页不增加发布提示，不隐式创建草稿或提交审核。官方副本判断同时要求 `ownerType=enterprise`、有效来源标识且来源不是自身，前端也同时检查企业归属、官方副本标记和更新审核权限。

已发布的 A 卡片显示“发布更新”，另保留“查看发布记录”。只有主动发起更新才通过 `POST /digitalEmployeePublication/prepareUpdate` 读取 A 当前已保存的配置，建立更新原 B 的候选。B 的 ID、创建者和授权保留，默认沿用 B 名称；其他可发布配置及资源按候选覆盖 B。已有申请继续打开：个人来源的未提交草稿按下方规则同步最新关联资源；待审及历史申请保持原快照。驳回/撤回结果先展示原审核意见，明确点击“修改并重新申请”后，新草稿同步最新个人资源并保留之前为发布调整的其他配置，旧记录不变。后续 A 修改不改变已提交快照。列表以批量返回的 `employeePublicationUpdate` 区分“继续发布更新”和“查看更新进度”。

### 未提交草稿的资源同步

员工列表、审核中心及直接 URL 打开的发布页面统一通过 `POST /digitalEmployeePublication/open` 加载，参数为 `{"requestId":"申请ID"}`。该接口锁定申请、检查权限，只对个人来源的 `DRAFT` 同步源员工资源；`GET /current` 和 `GET /detail` 仍只读，提交后的申请及历史记录不会因打开页面而重新采集个人资源。从 B 的正常编辑建立的更新草稿也不会读取 A 的关联。

草稿在既有 `snapshot_json` 中保存服务端源资源对照信息 `_publicationSourceResources`，不新增表或数据库字段，不接受客户端覆盖。对照涵盖 `relIds`、`relSkills`、`relTools`、`relResourceInfoList`，忽略关联查询顺序、重复值及 null/空数组差异。源关联或关联配置变化时，只替换草稿的这些资源字段、重新捕获技能包并生成可用性清单，名称、描述、角色等其他待发布调整保持不变；源资源未变时，保留发布页已保存的资源调整。源关联全部移除时，清单和编辑区同时清空。旧草稿首次打开时以现有草稿资源快照对照源资源，初始化对照信息；以后沿用同一规则。

保存待发布配置和确认预览均复核源资源，避免编辑期间仍回传旧关联。同步响应包含 `sourceResourcesChanged=true` 及新修订号，前端同步编辑区并提示用户核对清单；个人正常编辑页不增加提示，也不创建发布申请。预览只有发生资源同步或旧草稿初始化对照信息时才写回草稿，其他可用性复核仍只修改预览副本；待审预览保持原配置和修订号。

提交在锁定申请及源员工后再次复核。若确认弹窗期间源资源又发生变化，接口更新并返回 `DRAFT`、`sourceResourcesChanged=true`，本次不进入审核、不执行管理员自动发布，用户核对新清单后再次确认。源资源未变才提交冻结版本。同步只影响未提交草稿，审核员显式调整待审配置仍按既有权限和保存流程处理。

更新确认页展示目标 B 和覆盖范围：基础信息、角色与能力配置、关联资源，提示 B 独立维护的这些内容可能被替换，并提供只读查看当前官方配置的入口。新更新草稿在既有 `snapshot_json` 中保存服务端对照信息，不新增数据库字段；保存候选不能修改该信息。提交及审核执行均在锁定 B 后复核可发布配置指纹；B 有变更时，提交被拒绝或审核执行记录 FAILED，不写入 B 配置或资源。用户/审核员可通过 `POST /digitalEmployeePublication/refreshTarget` 明确重新对照，保留候选内容，再重新确认提交或审核；不会自动提交。升级前无对照信息的历史更新草稿也必须先显式重新对照，避免覆盖曾单独维护的官方配置。

普通作者提交后等待 adminvip/平台管理员审核。官方管理员可代创建者发起发布申请，原员工的编辑及授权操作仍按资源权限单独判断。同步远端提交 `c58e1e64c` 后，员工由 adminvip 创建不再额外触发特殊审核；本次复制的个人技能若由 adminvip 创建，平台管理员提交后仍必须等待 adminvip 审核，不得直接通过、驳回或修改待审配置。adminvip 自己发布可免人工审核；被排除的个人技能、仅复用关联的企业技能不额外触发此规则。

平台管理员创建的个人员工或个人技能，由 adminvip/平台管理员发布时直接通过，仍保存审核人、审核时间和审核记录。资源中心独立技能发布也按来源创建人判断审核权限，不能用企业副本的代发布人身份代替来源创建人。普通作者的审核流程保留。管理员免审也执行同一资源检查及复制流程；员工携带技能发布时共享一份审核申请，不再次创建独立技能审核申请。

B 的编辑信息进入普通编辑页。管理员按原接口直接保存，原创建者通过更新草稿及确认提交审核；存在未完成申请时保护在用配置。同步远端后，员工维护权限按创建人和有效授权判断，不再额外限制为“adminvip 创建的员工仅允许 adminvip 维护”。本轮企业归属及资源过滤调整只在发布/更新申请执行时应用。

## 资源处理

| 类型 | 企业员工 B 的结果 |
| --- | --- |
| 个人/个人默认知识库、个人工具 | 排除，列出名称和原因，不阻止员工发布 |
| 当前企业有效知识库、工具、已有企业技能 | 保留关联，沿用原资源权限；未对全员授权时另行提醒 |
| 平台内置工具，包括 `*` 全部工具 | 保留 |
| 员工作者有使用权限的个人 Hub 技能，A 校验通过 | 审核通过后由新方法 B 生成企业技能副本并关联 B；记录发布申请及来源技能 |
| 技能未提供 `resourceMate.json` 或声明 `resources: []` | 按无关联资源处理，可随员工发布生成企业副本 |
| 技能依赖个人资源、技能包缺失或依赖声明格式错误 | 整项技能排除，展示依赖链/原因；不阻止员工发布 |
| 员工作者无使用权限的个人技能、未形成可读取 ZIP 的技能 | 本次不复制，明确提示；不擅自扩大权限 |
| 失效、跨企业、归属不明或无法唯一识别的资源/工具编码 | 排除，不保留失效 ID 或隐藏的工具编码 |

候选编辑页保留完整清单方便对照；只有执行发布时的 DTO 被过滤。过滤覆盖 `relIds`、`relTools`、`relSkills`、`skills` 和被排除资源的 `relResourceInfoList`，再据此生成关系及 Redis 配置。不能只提示不带入却仍在后台引用个人资源。全部资源被排除时仍可发布员工。

跨企业资源仍不带入企业员工，但有权查看该资源的用户会看到具体名称和类型，例如“技能 weather-query”，原因显示“资源所属企业与原数字员工所属企业不一致”。申请查看权限不等于资源详情权限；打开页面时按当前查看人的资源访问权限复核，无权查看或无法确认权限时仅显示“关联资源 + ID”，不补出名称和类型。已有草稿中保存的“其他企业资源”也按资源 ID 只读补充展示，无需新建申请。可见但被排除的资源仍在候选编辑区回显，便于用户移除关联；展示信息不会恢复为可发布的资源对象。仅补充名称和类型时不改变已存配置快照、修订号、审核状态或排除结果。确认预览/提交/审批时继续复核真实归属，不根据展示名称放行；个人来源 DRAFT 的资源同步遵循上方规则，不覆盖其他待发布配置或已提交快照。

个人 Hub 技能的 ZIP 路径兼容资源中心现有的 `/byclaw/resource/skill/...`、`byclaw/resource/skill/...`、`/resource/skill/...`、`resource/skill/...` 及 `skill/...` 格式，统一转换成资源目录相对路径后通过存储门面读取。该兼容仅在员工发布流程内生效，不修改原技能文件或全局存储行为。路径兼容不会绕过方法 A；文件不存在/无法读取、依赖不符合条件时仍排除技能并提醒，员工仍可发布。任意本地绝对路径、外部 URL、目录穿越和空目录路径不能作为发布技能文件读取。

升级前因路径格式被排除的个人技能，需要在可编辑的申请中点击“保存待发布配置”重新捕获技能包并校验；只读打开申请只补充展示信息，不改变已审核的技能快照或排除结果。

已发布的历史员工不批量修改。旧申请中的资源阻塞记录在预览/提交/审批时按当前规则重新检查、转换为排除提醒。基础设施错误、员工名称错误、无权限和修订冲突仍会阻止对应操作，不能伪装为发布成功。

## 新方法 A：技能依赖校验

接口为 `EmployeePublicationSkillBridge.check`，实现为新的 `EmployeePublicationSkillService`，不复用/改写旧 `personalPublicationDependencies`。

A 读取待审核 ZIP 内唯一 `SKILL.md` 根目录下的 `references/resourceMate.json`：

```json
{
  "resources": [
    { "resourceId": "2001", "resourceType": "TOOL" },
    { "resourceId": "3001", "resourceType": "KNOWLEDGE_BASE" }
  ]
}
```

`resourceId` 采用十进制 ID 字符串；`TOOL` 对应 TOOL/TOOLKIT/MCP/AGENT，`KNOWLEDGE_BASE` 对应 KG_*。按数据库实际 `owner_type`、租户、类型及资源状态复核。`personal` 和 `personal_default` 都属于个人。

技能根目录下没有 `references/resourceMate.json`，或文件明确声明 `resources: []`，均按无关联资源处理，返回 copyAllowed=true；审核通过后仍正常执行 B。只读取约定根目录内的声明，其他目录的同名文件不作为该技能的依赖声明。

文件存在时逐项检查声明的资源。有个人依赖，或声明损坏、空白文件、resources 非数组/缺失、无效 ID、类型不符、依赖不存在/失效/跨租户等，返回 copyAllowed=false 及原因，表示该技能不带入，不阻止员工发布。技能包本身仍必须有效；拒绝目录穿越、符号链接、重复文件及多个技能根目录；包上限 100 MB，声明文件上限 64 KB，声明最多 200 项。

个人依赖提醒明确技能与依赖资源的关系，例如“技能依赖了个人知识库「覃小迪的个人知识库」，因此本次不会随员工发布”；工具依赖同样标明“个人工具”和具体名称。类型和名称来自方法 A 对 `references/resourceMate.json` 声明及实际资源的检查结果，不依据名称猜测类别。多项依赖逐项列出；含义是整项技能本次不带入，员工仍可发布。已有草稿保存的旧提示需要点击“保存待发布配置”重新生成，不隐式改变已审核快照。

A 只检查声明的依赖；按业务约定，有关联资源时需在打包时同步维护此文件，没有关联资源时可省略。校验和审批以冻结的文件包为准，不在审批后改读作者最新工作目录。若旧草稿已因缺少声明文件记录为“不带入”，重新保存待发布配置即可按新规则重新检查。

## 新方法 B：生成企业技能

接口为 `EmployeePublicationSkillBridge.publish`，由同一个新实现类提供。只在管理员审核/免审执行阶段、已建立企业员工事务中调用，不调用资源中心的 `publishSkillToEnterprise`。资源中心单独发布技能仍走自身入口，同步采用本文的来源创建人审核规则和企业副本名称后缀规则。

B 校验包指纹及依赖后，将原包字节独立上传至：

```text
skill/org-hub/<tenantId>/<requestId>/<sourceSkillId>/<sha256>.zip
```

创建企业技能资源、扩展信息、文件产物记录，副本的创建者和管理者沿用员工原作者，记录发布申请及来源技能。新技能编码按申请和来源技能区分，避免运行安装目录覆盖。建立企业技能到其企业依赖的关系，以及 B 到企业技能的关系。调用方补全新技能作者权限和当前企业全员使用授权；不扩大既有依赖资源的授权。

新技能副本名称追加中文 `(企业)` 或英文 ` (Enterprise)`，已有对应后缀不重复追加。员工发布时在捕获快照阶段冻结副本名称，审核人语言不改变它；资源中心独立发布同样使用本地化后缀，重名消歧保留在后缀之前。已是企业资源的技能不生成副本、不改名，只建立原技能与新员工的关联。

B 沿用现有标准技能 JSON 生成能力；返回企业技能 ID 后，发布流程重建员工技能运行字段和 `DIG_EMPLOYEE_<B>` Redis 配置，通知运行端刷新。OpenClaw 沿用 Hub 下载/版本检查，将包安装到 `${OPENCLAW_STATE_DIR}/skills/<skillCode>`。后端发布成功不等同于所有运行节点都已完成解压。

同一申请/来源技能重试使用相同文件路径和编码；已有有效结果按文件指纹复核后复用，不重复生成。B 写入故障抛错，由员工发布事务回滚并记录 FAILED；不把部分写入伪装成正常排除。对象存储不支持数据库回滚，未关联的快照文件可供重试复用，不自动删除历史文件。

## 交互

发布编辑页将发布操作与规则说明放在同一区域，简短说明常驻，完整规则通过“查看发布规则”展开。
关联资源说明按发布结果分为“将发布到新数字员工的”和“不会发布到新数字员工的”两个 Tab，分别显示数量；知识、工具、技能仍在条目中显示类型标签。
明细默认收起，排除数量和使用范围受限数量保持可见；点击 Tab 或“展开说明”可查看名称、原因、可用范围和发布后的影响，保留关联中优先展示使用范围受限的资源。
通过校验、会生成企业副本的个人技能归入“将发布到新数字员工的”，继续提供待审技能下载入口。真实配置错误和发布失败仍单独显示，不随资源明细收起。
发布编辑页统一纵向滚动，资源明细展开后可继续滚动到下方员工配置；普通员工编辑页保留原来的滚动方式。

发布编辑页仍可以保存草稿。提交/通过会先保存当前修改，再预览最新清单：

- 优先展示“发布后保留 X 项资源，Y 项不会带入”，逐项展示名称、类型、原因和能力影响。
- 区分“不会带入”和“保留关联但使用范围受限”，避免把所有提示理解为发布失败。
- 正常资源可展开查看，个人技能标注“生成企业技能副本”。
- 提供“确认并继续发布”与“返回修改”；全部资源被排除也能继续。
- 审核中心、发布编辑页和企业副本创建者在普通编辑页发起的更新确认共用清单组件；个人员工的普通保存不进入此确认流程。
