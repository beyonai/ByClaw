# 个人服务器部署

仅在用户明确授权部署到该服务器时执行。用户配置并启用 `BYCLAW_DEPLOY_HOST` 和
`BYCLAW_DEPLOY_PRIVATE_KEY` 即可，其他参数不要求填写：默认 root、22 端口和 `~/apps`。
可选 `BYCLAW_DEPLOY_ENABLED=0` 暂停凭据提供；这是部署账号权限范围内的服务器操作授权。
凭据由执行层提供给本次任务，不能从聊天、历史文件或其他用户的配置猜测。

使用 `server-ssh`，不要自行写密钥、读取凭据上下文、打印环境、绕过主机公钥校验或转发认证代理。
未提供主机公钥时工具首次连接自动记录，之后公钥变化会拒绝连接；不要要求用户为普通部署额外填公钥。
若命令不存在、上下文不可用或连接失败，返回实际错误；不要改用历史密钥或关闭主机校验。
工具只在支持此能力的 coding 任务中可用；不要在共享宿主安装软件来绕过缺失的执行能力。

## 流程

1. 读取项目现有部署说明、启动入口、Dockerfile、Compose 和锁文件，确认发布内容及必要配置。
   若当前工作目录是平台选定的群项目 Git 仓库，先用 `git rev-parse --show-toplevel` 核对仓库根，
   用 `git rev-parse HEAD` 确认目标提交，并检查 `git status --porcelain --untracked-files=all` 为空。
   有未提交内容时先完成本任务的修改、测试和提交；遇到来源不明的改动先说明，不擅自清理或提交。
   不从脏工作区发布，也不另建可持续修改的部署源码副本；本阶段由人工保证同群没有并行写任务。
2. `server-ssh check` 验证连接，再检查目标系统、架构、可用内存与磁盘、运行环境、端口和已有服务。
   优先复用项目可用的 Dockerfile 或 Compose；结合服务器条件选择改动少、可持续运行的方案。
   Docker 不是必需条件，也可使用独立运行环境加 systemd 等方式；简短说明选择理由并继续部署。
   在用户已授权范围内安装本应用所需依赖；首次安装 Docker、变更防火墙或影响已有业务前，核对授权范围。
3. 按明确文件清单生成源码发布包。排除 `.env`、`.ssh`、`.connector-auth`、Codex 状态、
   认证文件、依赖目录、缓存和用户运行数据；检查归档清单与 `.dockerignore`。
   不直接打包整个 `/by`、用户主目录或项目父目录；不把真实密钥写入构建参数。
   Git 项目优先用 `git archive <已确认的提交> <明确的源码路径清单>` 导出到 `/tmp`，再按实际构建流程发布。
   导出包只是该提交的交付产物，不成为另一套开发正本；确认凭据和运行数据未被错误跟踪。
4. 部署目录参数是可选的，默认 `~/apps`，工具自动创建；不要要求用户为常规部署额外配置目录。
   默认按应用分子目录，使用唯一版本目录，例如
   `server-ssh upload /tmp/release.tar.gz easel/releases/v001/source.tar.gz`。
   目标路径相对部署根目录，用户自定义根目录时沿用其布局。目标上的已有文件可能被覆盖，不复用其他发布的版本名。
5. `server-ssh exec '<远程脚本>'` 在部署根目录执行。构建成功再更新服务；容器使用明确镜像版本，
   非容器部署使用应用独立环境和服务定义。持久化数据与可重建依赖分开，保留升级所需的旧版本。
   不清空服务器全局镜像、卷或目录；用户明确要求不保留旧部署时，遵循其要求。
   服务须脱离当前 SSH 连接和工具任务持续运行，并设置适合该服务器的重启策略。
6. 长时间构建或安装应在远端保留日志、进程标识及退出状态，分次检查进度；不能只因没有输出就认定失败。
   失败时依据实际错误修复，不重复执行同一失败命令或无依据地追加系统依赖。
   当前方案确实受阻时，可切换到可维护的替代方案，并说明原因；真实凭据、权限或外部条件阻塞时如实报告。
7. 分别验证服务持续运行、页面与静态资源、接口以及真实业务调用；从外部访问目标地址，不能仅检查回环地址。
   缺少模型 API 等外部配置时，区分已验证的部署结果与尚不可用的业务功能，不伪造业务成功。
   启动命令退出零、SSH 连通或页面返回 HTTP 200，都不能单独代表完整验收通过。
8. 返回实际部署方式、版本、真实访问地址、各项验证结果和回滚方式。失败也应给出明确结果：
   已完成步骤、实际错误、远端是否还有任务运行及下一步；不要只返回计划或停留在已发起构建。
   Git 项目附实际部署 commit ID；准备回群成果时只提供正文和测试结果，源码附件清单为空，仍等待用户确认发布。

`server-ssh exec` 可以执行远程 shell，部署根目录只是初始工作目录，不是服务器上的权限隔离。
普通 Docker 权限应按服务器管理权限看待。SSH 断线或取消不保证远程构建已停止；先查远程
进程、容器和版本状态，确认后才能重试。部署完成后用户可停用参数，撤销服务器上的专用公钥。
