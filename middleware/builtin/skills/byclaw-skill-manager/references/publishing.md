# 发布流程

输入为会话中的技能源码/ZIP，或已有平台工作区目录，以及目标数字员工与发布范围。先读取 [测试流程](testing.md) 的实际结果：必要测试失败时先修复；未测项如实保留，不能宣称可运行。仅调用 API 不需要重新创建技能。发布前核实用户验证通过及发布意图，复用已有验收，不把静态校验当作用户验收。

完成发布后返回实际资源 ID、绑定与同步结果；用户要求分享时进入 [授权流程](authorization.md)，要求安装到其他员工时进入 [安装流程](installation.md)。

按 [生命周期契约](lifecycle.md)，正式交付是会话内验证后的压缩包经平台注册、授权与绑定，再由广播驱动各用户运行时自动加载。下列接口说明是部署实现细节；已有目录资源化是兼容入口，不能跳过内容验证，也不能把会话目录直接当作已分发资源。

接口合并注册与绑定时，先检查本次操作范围和平台权限是否允许该副作用。用户只要求注册时不能擅自绑定，应核实独立注册接口；不为了遵循概念流程而忽略已知接口实际会写什么。

## 先选择真实路径

| 起点 | 路径 | 当前实现的副作用 |
|---|---|---|
| 沙箱内 Skill 源码或 ZIP | 检查包与覆盖范围 → uploadSkillZip → 查询回读 | 写工作区、注册/更新技能资源、绑定数字员工并安排运行时刷新 |
| 已在工作区、尚未资源化的目录技能 | 查询目录 → checkWorkspaceSkillShareConflicts → resourceizeWorkspaceSkill → 回读 | 生成个人技能资源并绑定目标数字员工 |
| 已有资源，给其他数字员工使用 | 复用技能资源 ID → 绑定目标数字员工 | 不重新上传同一份 ZIP |
| 只优化或创建文件 | 编辑 → 按业务需要验证 → 交付 | 不自动发布、授权或绑定；可按业务依赖查询平台资源并在获准范围内联调 |

以上为本指南支持的接口行为。当前部署存在差异或返回结构不符时，通过平台提供的接口说明、工具元数据或只读查询核实；不要用上传来试探是否会资源化。

**旧脚本边界：** `skill_publish.py` 固定执行“打包→上传→预检→资源化”，只取上传结果第一项，且在上传之后才请求覆盖确认。它不能作为当前后端的默认发布器，也不能保护上传时的覆盖。仅在明确验证目标后端仍为旧契约、并完成上传前覆盖检查后考虑使用。本次指南使用分步 API，不虚构脚本已有 dry-run、resume 或非交互确认选项。

## 1. 打包前准备

将创建/测试阶段确定的实际技能源目录作为 SOURCE_DIR；不要求固定前缀或 sessionId。核实目标用户、数字员工、技能稳定名称和源码目录；这四者不从例子或路径猜测。标准包保持一个 skill；目录名、frontmatter name 与 ZIP 基础名一致。当前后端从 SKILL.md 所在顶层目录名或 ZIP 文件名推导技能 code，不能只改 frontmatter 就期望改名。

在当前任务允许写入的临时或产物目录中、位于技能源目录之外保存 `<skill-name>.zip`，防止归档把自身收入。不要给根布局 ZIP 随意加版本文件名后缀，否则可能创建另一个 code。版本可记录在包摘要和发布记录中。

```bash
# SKILL_ROOT、SOURCE_DIR、PACKAGE_DIR 均来自已核实的实际路径。
python3 "$SKILL_ROOT/scripts/skill_package.py" "$SOURCE_DIR" "$PACKAGE_DIR/<skill-name>.zip"
```

现有脚本返回 `(zip_path, size_mb)`，ZIP 内 SKILL.md 位于根目录。它排除隐藏文件、虚拟环境、node_modules 和若干二进制扩展，但不是凭据扫描器，也不能保证符号链接安全。打包前核对非隐藏配置、日志、数据、链接目标；打包后用 zipfile 列表检查文件集合和引用。不要带凭据、其他用户数据、历史 ZIP 或开发缓存。

发布包还需满足 [凭据与连接发现](credentials-and-connections.md) 的跨员工约定：携带可移植的当前 Agent/用户配置解析方式，不携带开发者实际模型认证、个人连接配置或绝对会话路径。查看迁移测试结果，明确尚未验证的运行时适配能力。

## 2. 上传之前检查覆盖

查询目标完整技能列表并按技能名精确匹配；`list_workspace_skills()` 仅返回未绑定目录，**查不到不能证明不存在同名资源**。完整查询方式见 [API 契约](api-contracts.md)。再核对可见个人资源、同名 code 和已绑定数字员工；仅能查询到局部范围时，明确覆盖信息不完整，不把它当作无冲突。

存在同名目录时可用其真实 skillPath 调用冲突预检，展示返回的 updated 项、真实资源 ID 和影响员工；如果资源在别处已有同名 code，还需核对资源管理侧。当前上传注册逻辑会更新命中的同自然键资源，并刷新相关员工，不能假定影响仅限本次目标。

第一次写入前确保用户授权已覆盖具体对象和影响范围。若发生新增冲突、身份变化或范围扩大，再请求补充确认；不要求重复确认已批准的相同覆盖。未知同名情况且无法获得可靠查询证据时暂停上传，继续完成沙箱内包。

## 3. 分步上传与回读

调用 `api.upload_skill_zip(zip_path, resource_id=employee_id, user_code=target_user_code)`；通常省略 user_code 使用当前登录用户。请求中的 resource_id 是**数字员工 ID**。

保存每项 `skillName`、`skillPath`。上传 DTO 的 resourceId/resourceBacked 可能未在注册后回填，不能据此断言“未资源化”，更不能立即再调用资源化。查询完整技能列表，精确匹配 skillName/skillPath，取得非空技能资源 ID 与资源状态；再用 `get_skill_used_by(skill_id)` 核对目标绑定。无法取得 ID 时报告“上传已返回，资源确认待完成”，不能编造 ID 或重复发布。

## 4. 已有工作区技能资源化

从 `list_workspace_skills(employee_id)` 选择确切目录，使用返回的 skillPath。调用 `check_resourceize_conflicts(skill_path, employee_id)`，检查顶层 code、data.failed 和 items；失败项不能当无冲突。

有 updated 项时，说明真实覆盖范围并检查授权。只有该范围已经明确获准，才传 `overwrite_confirmed=True`；无冲突传 False。调用 `resourceize_skill` 后读取 data.items 中 success=true 的资源 ID，检查 failed 与逐项结果，最后核对目标绑定。

预检和执行不是不可分割事务。执行时遇到新增冲突，应重新获取当前证据，不绕过后端校验。

## 5. 更新、生效与恢复

更新前保存可取得的旧包、SHA-256、目标身份和当前绑定信息。覆写成功后分别报告资源版本/包更新、员工绑定、运行时加载验证。资源服务有 version、packageHash、syncStatus 等概念，但不要据此虚构可用的历史版本回滚 API。

技能内容更新与员工绑定变化分别核实，不用重复绑定代替内容同步。

失败后先查询实际状态：上传失败可能已写目录，超时可能已注册；资源化失败不意味着上传被回滚。只重做确认未完成的步骤。恢复旧内容也必须走经核实的覆盖路径，不以删除后重装作为默认回滚，不擅自重启个人沙箱。
