# @zhchxiao123/dsh-devflow-tool

English | [中文](README.zh.md)

The model-facing devflow tools: **`devflow_list`** surveys the workspace task board, **`devflow_show`** reads one card, **`devflow_create`** turns a chat-agreed requirement into a new draft card, **`devflow_take`** claims a ready card into development, **`devflow_transition`** commits one stage move, **`devflow_attach_artifact`** registers a stage deliverable, and **`devflow_read_artifact`** reads one kind's newest registration back. All are thin Consumers over [`ctx.devflow`](../devflow/README.md); journal replay, edge legality, and rejection semantics live behind the seam, so a structurally invalid journal surfaces as a tool error naming the file and line. Every tool operates on the calling session's workspace: an agent whose session header carries a `cwd` reads and writes `<cwd>/.devflow`, and a caller without one uses the store's configured default root — sessions in different workspaces see different boards from the same host.

## Contract

`devflow_list({ stage?, parent?, topLevel?, serviceClass?, set?, month?, limit?, cursor? })` returns one **page**: `{ cards, truncated, nextCursor? }` — id, title, current stage, `stageRevision`, and the optional `parent` per card. `stage` narrows to one location (a pipeline stage or `blocked`), `parent` to one requirement's breakdown, `topLevel` to the requirements without their slices, and `serviceClass` to a shortened pipeline; `parent` and `topLevel` select disjoint cards, so stating both is a usage error rather than an empty page. `set: 'archived'` reads delivered work that has been filed away — legitimate context for decomposing something similar — and `month` narrows that to one `YYYY-MM` bucket. A truncated page renders the exact call that continues it, because a page that does not say it was cut short reads as the whole board. It stays compact and directs a model to show a selected card before moving it.

Filing and restoring are **not** here: they are decisions, like abandonment, and live on the [`/devflow`](../devflow-command/README.md) command plane. This tool reads the archive; nothing on the model plane writes it. `devflow_show({ id })` returns the card's title, stage, `stageRevision`, optional `blockedFrom`, its `parent` with that card's `parentTitle`, its `children` summaries, the card-file path, registered artifacts, the optional current artifact-gate preflight, and full Markdown body — so a model holding only a child card can read the requirement it decomposes, a model holding a parent sees the whole breakdown, and neither has to attempt a transition to discover a deliverable contract. `devflow_read_artifact({ id, kind })` returns that kind's newest registration — path, revision, registering stage, and content; a card without one errors with the stable `no-artifact` message.

When `dsh-devflow-artifact-gate` is mounted and the current stage has a configured legal outgoing contract, `devflow_create`, `devflow_show`, successful `devflow_transition`, successful `devflow_take`, and `devflow_attach_artifact` include `artifactGates`: the edge plus every required kind's `missing | malformed | satisfied` status, structure template, newest registration, and defects. Create also renders the initial `stageRevision`, so the model can attach the first required artifact without an extra read. Create and successful moves therefore announce the destination stage's work immediately; attachment immediately reports malformed content without rolling back its immutable journal registration. Without an applicable contract the optional field and its rendered text are omitted.

When [`ctx.devflowSpec`](../devflow-spec/README.md) is mounted and the card's newest `spec-refs` registration declares a `## Scope` section, those same five results also include `specRefs`: one row per architecture document under a declared id prefix, carrying its id, title, optional description, path, and rolled-up `fresh | stale | unevaluable` freshness. **The index carries no bodies** — a body reaches the model through `devflow_read_spec` on demand, so a card whose scope covers a package's whole document set costs a few lines here rather than the documents themselves. Each non-empty line of the scope section contributes its first token as an id prefix, so a bullet with a trailing rationale works and the list ends at the next heading; overlapping prefixes still yield one row per document. The field is omitted whole, and without an error, when the seam is absent, nothing is registered, or the declared prefixes reach no document — a card that has not yet said what it touches is an ordinary card. A registration that yields no readable scope — the file cannot be read, no `## Scope` section, or no entry under it — instead carries a `specRefsWarning` line saying the index is not being served: that card promised a declaration, and silence would read as "no documents". This plugin does not `inject` the spec seam, so a deployment without it loads and renders exactly as before.

The mutations require an owning agent session (a non-agent caller is rejected before any effect). `devflow_create({ title, body, slug?, parent? })` creates one card at `draft` with a fresh sequence number — the body carries the requirement and its acceptance criteria, an omitted slug derives from the title, and `parent` hangs the card under the bigger requirement it decomposes; an empty title, ill-formed slug, lost sequence race, or illegal parent (unknown, already a child, or settled) returns a tool error carrying the seam's stable message. `devflow_transition({ id, to, expectedRevision, reason? })` resolves and commits one move; a stale revision, illegal edge, missing rework reason, or policy veto returns a tool error carrying the seam's stable message. `devflow_take({ id, expectedRevision })` claims the card's exclusive lease and moves it `ready -> developing`; a failed move releases the lease before the rejection reaches the model, so a failed take has no side effects. `devflow_attach_artifact({ id, expectedRevision, ... })` records a stage deliverable in the card history against the current stage, in one of two forms the tool refuses to mix: `path` registers a file the caller already wrote under the card directory, while `kind` plus `content` has the store write `artifacts/<rev>-<kind>.md` itself; registrations are immutable, so re-registering a kind writes a new revision-named file and readers take the newest. The card's `.devflow` journal is the authority for every move, and the calling agent's session log already carries each call and its result as `tool/call` and `tool/result`; these tools append no devflow-shaped session event of their own.

## Render intent

Reads are `generic` cards of kind `read`; mutations are `generic` cards of kind `edit` carrying the salient arguments as `rawInput`. Presenters are pure functions of arguments.

## Model Experience

### Tool schemas

#### What the model sees

The generated [`devflow_*` schemas](../../../docs/tool-catalog.md#deepseek-aidsh-tool-devflow): two reads, the card creation, and three revision-checked mutations whose descriptions carry the stage pipeline (`draft, designing, ready, developing, reviewing, testing, done` plus the `blocked` bypass), the `parent` relation of a decomposed requirement, the optimistic-concurrency contract, and result fields as declared output schemas. The descriptions state only per-call mechanics and obligations; cross-tool judgment — when to create a card, how to slice a requirement, rework after a veto — lives in the `devflow-workflow` skill of [`dsh-devflow-guidance`](../devflow-guidance/README.md), loaded on demand instead of resident in every request. Applicable single-card results also carry the artifact preflight and render an explicit stop instruction while any requirement is unsatisfied, and the scoped document index with each row marked by its freshness — so a stale document is never handed over as if it were current.

#### Token effect

Fixed schema cost per request while the plugin is active; results are proportional to the listed cards or the shown card body.

#### KV Cache effect

Prefix-stable while the plugin scope is unchanged; activation or disposal may invalidate reuse from the tool-schema section onward.

## Known Limitations and Deferred Work

- **No editor follow-along locations** — presenters are pure functions of call arguments and the card path is provider deployment state, so `presentCall` cannot name the card file; the show result carries `path` instead.
- **A taken lease is never heartbeated by the tool** — `devflow_take` claims but holds no background heartbeat; `/devflow takeover` is the explicit recovery plane for an abandoned owner.
- **The scope list is a convention, not a contract** — an artifact gate can require that a `spec-refs` registration carry a `## Scope` section, but nothing checks that the ids under it name real documents. A prefix written wrong reaches nothing and the index is simply absent: silence, not a defect report.
- **Document freshness is re-evaluated on every single-card call** — there is no cache, so the index costs one evaluation per document the declared scope reaches.
