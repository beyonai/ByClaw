# E2E Bootstrap Runbook

## 这个 skill 解决什么问题

每次做端到端测试时，agent 都要重新考古：翻 README、猜启动顺序、试端口、撞依赖。这既费 token，又不可靠——agent 很容易拉起一个"看起来在跑"但配置错误的环境，然后在它之上得出错误的测试结论。

这个 skill 的目标是把"如何把这个系统拉起来"这份知识，从一次性探索沉淀为仓库内的**可执行、可验证、可维护的 runbook**，让后续任何 agent 不看源码也能在几分钟内拿到一个可信的测试环境。实测中，一份合格的 runbook 能让后续 agent 在 1–2 分钟、十几次工具调用内拿到绿色的健康检查，而从零探索需要几十分钟和上百次调用。

它不限定技术形态：直接命令启动的本地进程、docker 里的 redis/postgres、需要联网的第三方服务、混合形态，都适用。skill 关注的是流程和产出质量，不是某种具体工具。

## 两种触发模式

**生成模式**：仓库里还没有 `e2e/README.md`，或者用户明确要求生成/重写启动文档。走完下面全部阶段。

**维护模式**：runbook 已存在，你在做端到端测试时按它操作却发现与现实不符（命令失败、成功信号变了、多了新依赖）。这时**先修 runbook，再继续原任务**。不要绕过去——你绕过去的坑，下一个 agent 会再踩一次。修完在文档的"变更记录"里加一行。

## 核心原则：只写你亲手跑通的东西

runbook 里每一条命令都必须是你在本次会话中实际执行并成功的；每一个"成功信号"都必须是你真实观察到的输出。**不允许根据源码推测启动步骤然后写进文档。**

原因很简单：一份基于推测的 runbook 比没有 runbook 更糟。没有文档，下一个 agent 会去探索；有一份错误的文档，它会信任它，然后在错误的环境上得出错误的结论，并且很难发现。

如果某一步你无法在当前环境验证（比如需要某个你没有的凭据、需要访问内网、没有 docker daemon、包仓库被出网策略拦截），把它明确标记为 `[未验证]`，写清原因和"在什么条件下可以补验"，而不是装作验证过。但 `[未验证]` 是**问过用户之后**的兜底，不是撞到障碍的第一反应——缺的东西用户往往一句话就能补上（见阶段二）。部分可用的 runbook（比如只能拉起一半组件）依然有价值，前提是诚实地划清边界。

## 核心原则：只删你自己创建的东西

runbook 的任何破坏性操作——停进程、删容器、删卷、drop 库、`rm`——只能作用于**它自己创建的资源**，其余一律不动。写错一份 runbook 只是浪费下一个 agent 的时间；删掉开发者的开发库是不可逆的。

"自己创建的"必须在**删除那一刻**可判定，不能靠你记得。所以：创建时带 `<project>-e2e-` 作用域名，删除时**按作用域枚举**（`docker ps -aq --filter name=<project>-e2e-`、你自己 pidfile 里的 pid、`e2e/` 目录内的路径），而不是按"这个 compose 文件里有什么"或"这个目录下有什么"枚举。后两种枚举与所有权无关，它们删的是别人的东西。由此推出两条硬规则：`docker compose down -v` 只在 project 名被你的作用域隔离时才允许；文件系统的删除只发生在 `e2e/` 以内。

还有一条容易漏的：**复用一个你没创建的资源，不会让你获得删除它的权利**。撞到一个已经在跑的同名服务而你直接用了它，它依然不是你的。

## 阶段一：侦察（Recon）

目标是在动手之前拼出系统的全貌：由哪些部分组成、依赖什么、有哪些候选启动方式。按下面的线索源逐一查看，把发现记在草稿里（后面写文档要用）。

线索源的优先级（从最可信到最不可信）：

1. **CI 配置**（`.github/workflows`、`.gitlab-ci.yml`、`Jenkinsfile` 等）。CI 里跑通的步骤天然是可复现的，往往比 README 更接近真相。特别注意 CI 里的 service containers、环境变量、缓存/安装步骤。
2. **编排与构建文件**：`docker-compose*.yml`、`Makefile`、`justfile`、`Taskfile.yml`、`package.json` scripts、`pyproject.toml`/`Cargo.toml` 等的 scripts 段。
3. **环境变量样例**：`.env.example`、`.env.sample`、`config/*.example.*`。每一个变量都是一个潜在的依赖或坑。
4. **已有的 agent 指令文件**：`CLAUDE.md`、`AGENTS.md` 及它们 `@include` 的文件。后续 agent 会先读这些再读你的 runbook，所以里面任何与启动相关的规则（包括无法执行的规则，比如要求使用一个没安装的工具）都会影响它们。记下来，写文档时要处理。
5. **README / CONTRIBUTING / docs**。人写的，可能过时，用来理解意图而不是照抄命令。
6. **入口代码**：`main.*`、`cmd/`、`app.*`、启动脚本。用来确认端口、健康检查路径、依赖的连接串。
7. **现有测试**：`e2e/`、`integration/`、`tests/` 下的 setup/fixture/conftest。这里往往藏着"测试需要什么环境"的最精确描述。

侦察结束时你应当能回答：系统由哪几个进程/容器组成？彼此的依赖和启动顺序？每个组件监听什么端口、怎么判断它就绪？需要哪些外部服务（数据库、缓存、消息队列、第三方 API）？哪些需要联网？需要哪些凭据？当前环境能满足哪些、不能满足哪些？

如果这些问题有答不上来的，先在下一阶段实跑中补，不要靠猜。

## 阶段二：实际拉起（Bring-up）

按侦察结果实际启动系统，**逐步执行，逐步记录**。每一步记下：

- 确切命令（含工作目录、环境变量）
- 真实输出中标志成功的那一行（比如 `listening on :8080`、`database system is ready to accept connections`）
- 耗时，并区分**冷启动**（依赖未安装、未编译）和**热启动**（一切就绪只是进程没起）。两者往往差一个数量级，只给一个数字会让后续 agent 无法判断该继续等还是该判定失败
- 遇到的每一个失败，以及怎么修好的

踩坑记录是这个阶段最有价值的副产品。你解决掉一个"端口被占"或"数据库没迁移"的问题之后，不要就此忘掉——它会成为文档"故障排查"章节的一条。经验上，故障排查章节是后续 agent 用得最多的部分。

实跑时的注意点：

- **先确认前置条件再启动**。工具版本、docker 是否可用、端口是否空闲、必要的环境变量是否设置。为每个前置条件找一条能单步验证的命令（`docker info`、`node --version`、`lsof -i :8080` 等），这些命令会进文档。
- **一开始就把自己的资源隔离出来**。凡是落在**与别人共享的命名空间**里的东西，名字都带 `<project>-e2e-` 前缀：容器、卷、网络、compose project、宿主机上的目录。关在你自己容器里的东西（那个容器里的库名、schema）不必再套前缀——你拥有容器就拥有了它们。compose 用独立 project（`docker compose -p <project>-e2e -f e2e/compose.yml`）而不是仓库自带的默认 project——后者会把你的对象和开发者日常在用的那套混成同一堆，到清理时再也分不开。端口避开该服务的默认端口（postgres 用 5433 而不是 5432），别和本机已有实例抢。这一步决定了 `down --reset` 能不能安全执行：现在不隔离，后面怎么写都是错的。
- **区分"必须真实"和"可以 mock"的依赖**。第三方 API、支付、邮件、LLM 这类，问自己：端到端测试真的需要打到真实服务吗？如果仓库里已有 mock/stub/sandbox 模式，优先用它并记录；如果没有，在文档里明确指出"此依赖需要真实凭据"。注意服务自带的 `/ready` 之类接口常常把这类可选依赖也算进去，缺凭据时整体报"未就绪"——要分清这是预期状态还是真的坏了，并在文档里提前说明。
- **环境缺中间件时先问用户，不要自己替一个**。系统需要一个这台机器上没有的数据库、缓存、消息队列、对象存储，而它正确的形态你猜不出来——版本、连接方式、有没有现成的共享实例、要不要种子数据、凭据从哪来——那就停下来问。一次问清：缺的是什么、你打算怎么替代、需要用户给什么（镜像与版本、连接串、凭据获取途径，或者仓库里已有的起法）。问之前先把不依赖这个答案的部分跑完，否则用户答完你还得重新探索一遍。**最危险的不是拉不起来，是你随手挑了个 `latest` 并且跑通了**——"只写你亲手跑通的东西"拦不住这种，因为你确实跑通了，只是跑通的不是这个系统要的那个，而后续每个 agent 都会在这个错版本上得结论。用户给的若是一个已经存在的共享实例，那它是**借用**的，`down` 不许删它。问不到人（非交互环境、用户没回）才降级：标 `[未验证]`，并写清缺什么、问过了、没拿到、什么条件下能补验。
- **需要联网的部分单独标出**。哪些步骤离线跑不了（拉镜像、装依赖、调外部 API），后续 agent 在受限网络下需要提前知道。
- **环境特定的绕过方法要参数化**。你在这个环境里为了绕过代理/镜像限制加的 registry 覆盖、资源受限时降的并发度，在另一个环境可能不适用甚至有害。写成带默认值的环境变量（`E2E_NPM_REGISTRY=${E2E_NPM_REGISTRY:-...}`），并在文档里说明它是针对什么情况加的。
- **主机身份不进产出物**。你这次跑通用的是 `/home/<你>/work/repo`、你的 hostname、容器里的 `172.x` 地址、你机器上碰巧空闲的那个端口——它们是你验证过的**证据**，不是写给别人执行的**指令**。产出物里写同一条命令的可移植形式：工作目录用仓库相对（脚本里 `cd "$(git rev-parse --show-toplevel)"`，文档里写"在仓库根执行"），端口用 `${FOO_PORT:-8080}`，本机服务写 `127.0.0.1` 而不是机器名。绝对家目录、用户名、hostname、局域网/容器 IP、个人 profile 目录（`~/.config/<tool>/<你的 profile>`）一律不出现。产出物是要入库、被别人 checkout 的：一份只在你这台机器上成立的 runbook，对其余每台机器都是错的，而下一个 agent 会照着它做——和本文开头判死的"凭推测写出来的 runbook"是同一种失败。
- **凭据永远不进文档**。文档里只写"需要 `FOO_API_KEY`，从 X 处获取"，值通过 `.env`（已 gitignore）或环境注入。

### 后台进程的坑（agent 环境特有，几乎必踩）

agent 的每次工具调用都是一个短命 shell。用 `cmd &` 起的服务与该 shell 同属一个进程组，调用结束时常被一起清理——症状是"上一步明明起来了，下一步就没了"，日志里只有一句正常关机。另一面是后台进程继承了调用方的 stdout 管道，导致 `up.sh | tail` 这类命令永远不返回。

启动脚本里统一用完全脱离的方式拉起服务：`setsid`（或 `nohup`）+ `</dev/null >>logfile 2>&1 &`，并把 pid 写到 pidfile。容器化的组件不受此影响，但本地进程（包括 `pg_ctl` 拉起的 postgres）都会。这条写进故障排查。

## 阶段三：建立健康探针（Health probe）

找到或构造一个能一步确认"整个系统真的可用"的检查。这是 runbook 的锚点——没有它，文档无法自我验证，后续 agent 也无法区分"启动了"和"能用"。

好的探针有层次：

1. **进程级**：各组件进程/容器都在跑（`docker compose ps`、pidfile + `kill -0`）。
2. **端口级**：关键端口可连且协议正确（`pg_isready`、`redis-cli ping`、`curl -sf .../health`）。
3. **业务级**：一条最小的真实业务路径能走通，比如用应用的数据库角色读到种子数据、登录接口返回 token、创建一条记录再读回来、服务自己报告"数据库可达"。这一层才真正证明依赖之间是通的。

**每一条断言都要做反向验证**：把它对应的组件停掉，确认这条断言真的会变红。实测中很容易写出"永远绿"的检查：前端 dev server 在后端不在时依然对代理路径返回 200（因为它吐了自己的 index.html）；一个没有 `-f` 的 curl 对 500 也返回 0。一条不会变红的断言比没有断言更危险。

把探针写成 `check` 脚本，退出码即结果，失败时输出要能直接指向哪一层、哪个组件坏了，以及文档哪一节可以查。预期内的降级（比如缺 LLM 凭据导致 `/ready` 为 false）输出为告警而不是失败，并说明原因。

## 阶段四：识别分层启动方案（Profiles）

复杂系统很少每次测试都需要全量拉起。找出常见测试场景对应的**最小启动集**，比如：

- 只需要数据层：只起 db + cache，用于直接对库的测试，几秒就绪
- 只测后端 API：起 db + api，不起前端和 worker
- 只测某个 worker：起 mq + 该 worker，上游用固定消息注入
- 全量端到端：一切都起

每个 profile 写清楚：启动哪些、跳过哪些、被跳过的部分怎么 mock 或替代、冷/热启动各多久。如果编排工具支持 profile（docker compose profiles、Makefile 目标），直接对应上；否则在脚本里用参数区分（`up.sh api`）。最小的那个 profile 还有一个附加价值：它是后续 agent 花几秒验证"这份 runbook 还准不准"的探针，在快速开始里提一句。

## 阶段五：写 runbook 并固化脚本

### 脚本优先，文档兜底

文字描述的步骤越多，agent 执行时出错的空间越大。所以把能固化的都固化成脚本，让文档退化为"运行这三个脚本；check 失败看故障排查"：

```
e2e/up.sh [profile]     # 拉起（幂等：重复执行不应出错，你自己作用域内已就绪的组件直接跳过）
e2e/check.sh [profile]  # 健康探针，退出码即结果
e2e/down.sh [--reset]   # 停止；--reset 额外清掉你创建的数据，回到干净态
```

产出物统一收在仓库根的一个 `e2e/` 目录里——文档与脚本并排放，是因为两者必须逐字一致（见下），隔在两个目录里最容易漂移。仓库里已经有 `e2e/`（放 Playwright/Cypress 用例之类）不是冲突而是正好：runbook 描述的就是怎么把环境拉起来跑这些用例。若仓库另有强惯例（已有 `Makefile` 就用 `make e2e-up`），可以调整，但要在文档里写死入口。脚本要求：

- `set -euo pipefail`；每一步 echo 出正在做什么、是做了还是跳过了。后续 agent 靠这些输出判断自己处在冷启动还是热启动，没有这个信息，"26 秒就完成"和"步骤被静默跳过"是无法区分的。
- 等待就绪用轮询加超时，打印已等待秒数，而不是 `sleep 10`。
- 失败时打印指向文档哪一节的提示。
- **作用域外的同名资源是借用，不是你的**。up 撞到一个你没创建的同名容器、卷、或占着端口的进程：不 stop、不 kill、不删、不改它的配置。打印它是什么、你为什么不动它，然后换个名字或端口继续，或者直接失败退出让人来决定。`down` 同样跳过它。
- **`down --reset` 必须从任意起始状态都到达同一个终态**——而这个终态是"你创建的资源一个不剩，其余一个不动"，不是"环境一片白地"。典型错误：数据库已经停了，于是跳过 `DROP SCHEMA`，却照样打印"已重置到干净状态"——而"一切都停着"恰恰是新 agent 最常见的起点。如果清理需要服务在线，先拉起**你自己作用域内**的那个再清；每项资源逐条打印"已删除 / 本来就不存在 / 跳过（不是我创建的）"，只在真的干净时才说干净。
- 明确定义 `--reset` 的边界：清你创建的数据、状态、pidfile。`node_modules`、`~/.m2`、镜像、`e2e/` 以外的仓库文件都不是你创建的，一律不动（顺带，它们也确实重建很慢）。文档里写清保留了什么、彻底重来要额外删什么——**写成给人看的说明，不是脚本里的一条 `rm`**。
- **reset 不要删掉故障排查章节让人去看的日志**。"重置后重试"是最常见的排障动作，如果它同时销毁了证据，排障就断了。日志目录单独放、reset 时轮转而不是删除。

### 文档固定路径与结构

统一写到 `e2e/README.md`——就在脚本旁边，且 GitHub 点进目录会直接渲染它，人不用被告知也能看到。结构固定，不同系统长得一样，后续 agent 进任何仓库都知道去哪找、怎么读：

```markdown
# <系统名> E2E 环境启动指南（agent runbook）

> 本文档给 agent 使用。除第 8 节标记项外，所有命令均已于 <日期> 在 <环境类别：OS 家族/架构/是否容器/关键工具> 实际验证——写环境类别，不写这台机器（无主机名、用户名、家目录）。
> 发现与现实不符时：先修本文档与脚本，再继续你的任务，并在末尾变更记录追加一行。

## 0. 快速开始
三行：up / check / down，每行自带工作目录且不含绝对路径（`cd "$(git rev-parse --show-toplevel)"`，或注明"在仓库根执行"）。90% 的情况到这里就够了。再给一行最小 profile 作为几秒钟的"runbook 还准不准"探针。

## 1. 系统组成
组件列表：名称、作用、端口、依赖谁、就绪信号、本环境能否启动。一张表即可。同一端口出现两次要说明为什么（互斥？不同 profile？）。

## 2. 前置条件与检查命令
每项一条可单步验证的命令及预期输出。版本写最低要求而不是你碰巧装的那个版本号。含：工具、docker、端口空闲、环境变量、需要联网的步骤、需要凭据的项（只写名字和获取途径）。

## 3. 启动步骤（脚本内部在做什么）
按顺序：命令 → 成功信号 → 冷/热启动各预计多久。这是 up.sh 的可读版，脚本坏了时按这里手动走。

## 4. 健康检查
check.sh 检查的三层各是什么、失败各意味着什么、哪些告警是预期的。贴一份真实的通过输出。

## 5. 分层启动方案
各 profile：适用场景、启动什么、跳过什么、替代方式。

## 6. 故障排查
每条：症状（原样贴报错关键行）→ 原因 → 处理命令。按出现频率排序。无解的明确写"无解，不要再试"，省得下一个 agent 再花十分钟。

## 7. 清理与重置
down / down --reset 各自做什么、保留什么、什么情况该用哪个、哪些端口只有 reset 才会释放。逐条列出 reset 会删的资源（带作用域名），以及它明确不碰的东西——读者要能一眼确认自己的数据不在删除列表里。

## 8. 未验证项
本次无法验证的步骤、原因、在什么条件下可补验、补验后该回填到哪一节。没有则写"无"。

## 9. 变更记录
日期 · 改了什么 · 为什么（一行一条）
```

写作要求：面向执行而不是解释。少写"为什么这样设计"，多写"做什么、看到什么算成功、失败了怎么办"。命令用代码块给出可直接复制的完整形式——"完整"指参数、环境变量、工作目录都不省略，不指从你机器上抄一条绝对路径。

### 文档与脚本必须逐字一致

后续 agent 会拿文档里的文件名、成功信号、数字去和实际输出做字面匹配，任何漂移都会让它停下来怀疑环境。实测中最常见的漂移：文档写 `logs/redis-server.log` 而脚本写的是 `logs/redis.log`；文档说 161 张表而实际 160；前置条件写了一个精确版本号而实际跑的是另一个。这些在探索过程中都是对的，是后来改脚本时没同步文档。

所以文档要在脚本**定稿之后**写或重写：运行最终版本的脚本，把真实输出贴进文档，而不是凭记忆写。会变的精确数字（表数、行数、耗时）写"约"或写成范围。

### 与仓库已有的 agent 指令对齐

在 `CLAUDE.md` / `AGENTS.md`（没有就创建）里加一段：

```markdown
## 端到端测试环境
启动/检查/停止服务前，先读 e2e/README.md，用 e2e/ 下的脚本，不要自行探索启动方式。文档与现实不符时先修文档。
```

文档存在但 agent 不知道去看，等于没写。

同时读一遍这些文件已有的内容（含 `@include`）。如果里面有与你的 runbook 冲突的规则、或在当前环境根本无法执行的规则（比如要求每条命令前缀一个没安装的工具），不要假装没看见：在 runbook 开头明确写出"此文档中的命令不适用 X 规则，原因是…"。后续 agent 读到的第一条规则如果就无法执行，它对后面所有规则的信任都会打折扣。是否修改那条规则本身，向用户确认。

## 阶段六：从零复验（Clean-room verification）

这是质量闸门，不可跳过。

1. 执行 `down.sh --reset`，然后**确认**真的干净了（你创建的那些端口关闭、数据不在），而不是相信脚本的打印。再从"一切都停着"的状态跑一次 `--reset`，确认它不会静默跳过任何清理。同时反向确认**作用域外一个没少**：reset 前后各跑一次 `docker ps -a`、`docker volume ls`、`git status`，逐行对比。多删比漏删严重得多——漏删下次再清，多删没有下次。
2. **只看文档和脚本，不看源码**，重新走一遍 up → check。把文档里写的每一个文件名、成功信号、数字和实际输出逐字对一遍。
3. **验一次可移植性**。上一步在同一台机器、同一个用户、同一个路径下跑，硬编码的主机信息在那里永远是绿的。把 checkout 换个路径再跑一遍 up → check（`git worktree add` 到别处，或整目录复制）；然后扫一遍产出物：`grep -rnE "/home/|/Users/|$(whoami)|$(hostname -s)" e2e/`，任何命中都是缺陷，不是例外。
4. 对 check 的每条业务级断言做一次反向验证（停掉对应组件，确认变红）。
5. 再跑一次 `up.sh` 确认幂等。
6. check 通过、以上全部对得上才算完成。任何一步需要你回头翻源码才能继续，说明文档漏了东西——补上，再来一遍。

如果条件允许，用一个新的子 agent 来做这一步效果更好：它没有你探索时的记忆，更接近后续真实使用者。给它的指令只有"从仓库根目录的 CLAUDE.md/AGENTS.md 开始，把服务拉起来并让 check 通过，不许看源码，记录每一个摩擦点：歧义、与文档不符的输出、不知道该不该继续等的时刻"。它记录的每一个摩擦点都回填进文档。

## 完成时向用户汇报

简短说明：生成了哪些文件；有几个 profile 及各自耗时；哪些步骤标了未验证及原因；实跑中踩到的主要坑（已进故障排查）；仓库已有指令中需要用户决定的冲突。不要复述文档内容。

## 反模式（看到自己在做这些就停下来）

- 把 README 的命令直接抄进 runbook 而没跑过。
- 文档写了成功但 check 脚本没写、或其断言从来不会变红。
- 用 `sleep N` 代替就绪轮询。
- 用 `cmd &` 起后台服务而不脱离进程组。
- reset 在没清干净时宣称干净。
- reset 删掉了不是你创建的资源：复用仓库自带的 compose project、删默认名的卷、动 `e2e/` 以外的路径。
- 环境缺中间件，没问用户就自己挑了个版本替上，跑通了当作验证过。
- 把凭据、token、密码写进文档或脚本。
- 把家目录绝对路径、用户名、主机名、你这台机器的端口写进文档或脚本。
- 把只适用于当前沙箱的绕过方法硬编码进脚本。
- 在维护模式下绕过文档错误直接完成任务，不回填。
- 为了"完整"把架构解释、设计背景写进 runbook，稀释了可执行内容。
