# Agent Note:devflow —— driver 驱动每一个阶段,而不只是第一个

Status: implemented

[English](2026-08-27-devflow-driver-multi-stage.md) | 中文

## Problem

**当前状态。**本 note 修复的包已不在发布线中；当前边界归[由 Harness 所有的执行决策](../architecture/2026-08-29-harness-owned-workflow-execution.zh.md)所有。本 note 继续保持 active，因为其中的事件重新进入故障会约束未来任何后台编排器的状态机。

`Config.stages` 是一张表,[bundle 自己的示例](../../../../packages/devflow-bundle/README.md)也配了不止一项 —— 但卡片只走得到其中第一项。`engaged` 集合背负了两重含义,而它们正确的生命周期并不相同:*已入队*(入队 → 出队)与*正在被驱动*(派发 → 子代理退出)。一个集合取了两者中更长的那个,于是运行中的子代理为自己那次移动发出的 `devflow/stage-changed` 到达时,卡片仍处于 engaged,监听器把它当作重复丢弃。等 `drive()` 释放这个键时,队列已空,再没有东西把卡片重新送进来。只有进程重启、其激活扫描重读看板,卡片才会再次移动。

per-file 100% 覆盖率没有抓到它。每条 driver 用例都在 settle 子代理后就结束;它们做出的阶段移动都是在派发之外通过 `store.transition` 完成的,所以从来没有一条测试让卡片**在 engaged 期间**前进。行覆盖率覆盖的是代码,不是状态机的边。

同一个文件里还有两处更小的缺陷。`park()` 重读卡片来填自己的 `expectedRevision`,这让比较并交换变成无条件通过:一个推进了卡片而后失败的子代理,会让它到达的那个阶段被打成 blocked,记下一个卡片从未离开过的恢复点。而 revision 回退 —— 分支切换的情形 —— 重扫的是 store 的默认 root,而不是出事那张卡所在的 root,于是次级 root 的看板从来不是被重读的那一个。

## Decision

**`engaged` 保留"派发到退出"的生命周期,卡片通过一次重读重新进入。** `drive()` 结束时,driver 再读一次卡片,若 revision 变了就入队。`enqueue` 本来就拒绝未被驱动的阶段,所以停在 `done`、停在 `blocked`、或停在任何未配置阶段的卡片会自己停下。

**`park()` 使用卡片被派发时的 revision。** `revision-mismatch` 不再是需要上报的失败:它是执行器在告诉我们,它在死掉之前推进了卡片,因此卡片保持原位,不匹配记在 `debug`。只有真正的 park 失败仍然 warn。

**回退重扫取卡片自己的 root,并能跨过仍 engaged 的 child。** `sweep()` 接受一个可选 root,监听器传入 `card.root`。如果该卡仍 engaged,driver 会记下一次必须发生的重新进入,等 child 退出后执行;否则立即重扫会把卡片当作重复丢掉。激活扫描仍然只读默认 root,这是一条已记录的限制:缝上没有任何枚举 root 的操作,所以激活时停在其他 root 里的卡片通过自己的下一个事件进入。

## Alternatives considered

- **派发时就释放 `engaged`,由租约阻止第二个子代理。** 这是更小的改动,也是正确的终局形态 —— 但租约今天是咨询性的:没有任何写路径读 `claim.json`,而 `claim` 失败会让 `drive()` 直接返回、不做重排。把正确性押在它上面,就是押在 store 尚未做出的保证上。
- **让 `engaged` 的键带上 revision。** 它阻止了事件被丢弃,但此后没有任何东西能阻止新阶段的派发在旧阶段的子代理仍然存活时启动 —— 一张卡上两个子代理。那是拿停摆换竞态,而且集合会无界增长。

## Consequences

**配置了不止一个被驱动阶段的部署,现在会花掉此前不花的模型预算。** 停摆是静默的,任何阶段表里列了多个阶段的人,此前每张卡每进程只得到一次派发。这是本该有的行为终于到来,不是新增成本 —— 但它是在没有配置变更的情况下到来的,因此属于发布说明。

每完成一次派发,卡片多一次读。这次读在派发路径之外,发生在槽位已经释放给排队卡片之后,因此不延迟任何事情。

三条用例锁定这些修复:子代理在派发中推进卡片会引出第二次派发;先推进后失败的执行器让卡片保持原位;次级 root 在 child 仍 engaged 时发生回退,会在 child 退出后重新进入。它们检验的是"移动**发生在**一次派发期间",而非"发生在两次派发之间"。
