# Agent Note: runbook skill 让 agent 把自己那台机器提交进了仓库

Status: implemented

## Problem

`devflow-e2e-bootstrap-runbook` 的产出物是要被目标仓库**入库**的：`e2e/README.md`
与并排的 `e2e/up|check|down.sh`。正文有三处在推动执笔的 agent 把**它自己这台机器的
身份**写进这份产出物。

最直接的一处是写作要求：*「命令用代码块给出可直接复制的完整形式（含 cd 和环境变量）」*。
agent 实际跑的那条 `cd` 就是 `cd /home/<user>/work/repo`，于是「可直接复制的完整形式」
被解为一条带用户名的家目录绝对路径。快速开始一节重复了同一次施压（*「含 cd 的三行」*），
文档头模板则要求填 `<OS/资源/可用工具简述>`——这是在邀请作者写出这台机器，而不是它的类别。

正文本来已经禁止了三件相邻的事：凭据、把只适用于当前沙箱的绕过方法硬编码进脚本、
以及写碰巧装着的版本号而不是最低要求。主机身份与它们是同一形状的规则，只是没人写。
绝对家目录、用户名、hostname、局域网/容器 IP、个人 profile 目录，以及只在执笔那台
机器上碰巧空闲的端口，全都不在任何规则的覆盖范围内。

为什么这比「产出不整洁」严重得多：一份带着某台机器身份的 runbook，对**其余每一台机器
都是错的指令**，而正文开头早已给这种失败定过罪——*「有一份错误的文档，它会信任它，
然后在错误的环境上得出错误的结论，并且很难发现」*。凭推测写出来的 runbook 与绑定机器的
runbook，对下一个 agent 是同一种失败。产出物同时进入 git 历史，把用户名、目录结构、
有时还有内网寻址一并带走。

这个缺陷能存活下来，是因为协议观测不到它。从零复验（阶段六）是**以同一个用户、在同一个
路径、在同一台机器上**重跑的，硬编码的 `/home/<user>/repo` 在那里永远是绿的。

## Decision

正文带上了可移植性规则，从零复验带上了一个能观测到违规的步骤。

**该规则把证据与指令分层。** 这一层是承重的，因为正文的第一原则——*「只写你亲手跑通的
东西」*——与「别写你机器的路径」表面冲突：你亲手跑的那条命令**就是**带 `/home/<user>` 的。
把两条规则并列写下，只会让后续 agent 在二者间随机择一。新 bullet 用分层解开它：跑过什么
是**证据**，留在验证过程里，并以环境**类别**出现在文档头与第 8–9 节；写下什么是**指令**，
是同一条命令的可移植再表达，且要在阶段六重新验证。两条原则不再竞争，新规则也因此变得可
机械检查。

这条 bullet 放在阶段二凭据规则的旁边，而不是自立一节，因为二者属于同一族——本地事实
不进产出物——而相邻正是让这个族属可被读出来的东西。

**三处施压点被切断**，原意未失：「完整形式」现在指参数、环境变量、工作目录都不省略，
明确**不**指从执笔者机器上抄一条绝对路径；快速开始的三行给出仓库相对的工作目录
（`cd "$(git rev-parse --show-toplevel)"`）；文档头占位符改为要求环境类别，并在同一行
写明不要写出这台机器。

**阶段六新增第 3 步**，其余步骤顺延为 4–6。它做两件互补的事：从另一个 checkout 路径
重跑 `up → check`，这是让硬编码路径真的变红的唯一手段；以及 grep 扫描产出物，接住
hostname、容器 IP 和写死的端口——这些未必会导致失败。这与正文既有的
`每一条断言都要做反向验证` 同构：一个不会变红的检查比没有检查更危险。

反模式清单补上了对应的一行。

## 由什么钉住

`skill.spec.ts` 用 `toContain` 钉住承重句，而这个 spec 是**唯一**保护正文的东西——
本包没有别的机制。新增三条 pin，遵循本包既定的「少而稳」标准而非全文比对：规则的加粗
标题、`cd "$(git rev-parse --show-toplevel)"` 这个写法、以及阶段六那一步的标题。

这三条 pin 是**先于**正文改动加入并被观察到失败的，改完正文后再被观察到通过。只跑绿无法
区分「pin 守住了正文」与「断言恰好写中了正文里已有的串」。

## 这项改动使哪条声明失效

`src/skill.ts` 的模块注释、两份包 README、以及 Trellis backend spec，都声称相对作者
原文恰好只有**两处**差异——skill 名与产出路径。本次改动使它变成三处，四处声明在同一次
改动中一并更新。放着不管，它们立刻全是假话；而模块注释恰恰是后续 agent 在判断「能不能
改这里的措辞」之前会读的那一条。

两份 README 的「已知限制」一节同时记下了新规则的执行缺口：正文禁止主机身份、并让阶段六
去 grep 它，但 agent 跳过那次 grep 时，留下的机器绑定 runbook 不会被下游任何东西发现。

## Alternatives considered

**在插件服务 skill 时剥离主机信息。** `skill.ts` 按字节服务 asset，
`serves the body from the shipped asset byte for byte` 钉着这个契约。更根本的是，缺陷发生在
agent **写产出物**那一刻，而不是正文被服务那一刻——在服务时剥离，够不到那个带泄露的文件。

**做一个扫 `e2e/` 的校验器。** 本包已于 2026-09-11 从执行器退回纯判断层，「没有任何东西
校验产出」是**已记录的边界**，不是疏漏。加校验器等于把刚删掉的执行面请回来，代价远高于
一条规则加一次 grep。重新考虑的条件：出现同一缺陷跨多个仓库反复复发的证据。

**只删掉「含 cd」，不加正面规则。** 移除施压却不给替代写法，agent 照样写它跑过的那条绝对
路径；而且端口、hostname、容器 IP 从来就不在那个短语的射程内。

**在 `Config` 里声明允许的主机前缀。** 违反本包的 no-tunables 形态，也违反 `AGENTS.md` 的
"Require a current owner and need"——没有任何消费者需要它可变。

**自立一节而不是做阶段二的 bullet。** 会切断它与凭据、沙箱绕过两条规则的族属链接，而那正是
告诉后续 agent「这是哪一类规则」的线索，同时无谓加深正文目录层级。

## Consequences

相对作者原文的差异从两项增为三项，此后每次再变都要四份文档一起动。这个代价是接受的：
另一种选择是一份对「究竟改了什么」说谎的模块注释。

阶段六变贵了——多一次 checkout 与重跑。换来的是这类缺陷**第一次**变得可观测；此前的从零
复验根本不可能在它上面失败。

执行仍然完全依赖读到正文的那个 agent。grep 是自查，跳过它就会产出一份机器绑定的 runbook，
而下游没有任何东西会标记它。这与正文里其余每一条规则的姿态相同，且已写进两份 README，
而不是默默接受。

运行期行为无变化：导出面、`Config`、注册 rank、dispose 语义均未触碰，`src/` 未新增分支，
per-file 覆盖率门不受影响。其他仓库里已存在的产出物不做追溯改造——正文的维护模式会在下一个
agent 按它操作时逐份修复。
