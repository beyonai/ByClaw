# Agent Note: runbook skill 的 `--reset` 删掉了不是它创建的东西

Status: implemented

## Problem

`devflow-e2e-bootstrap-runbook` 要求执笔的 agent 产出 `e2e/down.sh --reset`——
一个全部工作就是破坏的脚本。正文对「怎么把这件事做彻底」说了很多，对**爆炸半径**
一个字没说。压力是单向的，产出物照着走了。

一份真实产物就是证据。`/e2e-test-samples/repos/fastapi-template/` 满足正文的每一条
要求，同时：

- `e2e/up.sh:57` 用 `docker compose up -d --wait db mailpit` 拉起服务——仓库自带的
  `compose.yml`、它的默认 project 名、它的 `app-db-data` 卷（`compose.yml:88`）、
  它的默认端口。
- `e2e/down.sh:49` 接着跑 `docker compose down -v --remove-orphans`。

于是 `--reset` 删掉的正是开发者自己的开发库所在的那个卷；`--remove-orphans` 还会
顺手清掉该 project 下 runbook 从未列出的容器。`e2e/up.sh:51-53` 另外会跑
`docker compose stop backend`，停掉开发者自己起的进程。
`/e2e-test-samples/repos/excalidraw/e2e/down.sh:56` 是同一形状。

这不是 agent 跑偏。这就是脚本本身。

**缺陷在 `up`，不在 `down`。** 等到 `down.sh` 运行时，「我创建的那个卷」和「本来就在
那儿的那个卷」已经是同一个对象了，因为 `up.sh` 加入了仓库既有的 compose project。
**清理能不能安全，在拉起的那一刻就决定了。** 而阶段二——拉起阶段——关于隔离一个字
没有；所有关于 reset 的文字都在阶段五。

四处在推动删过头：

- `up.sh` 的幂等要求写的是 *「已就绪的组件直接跳过」*，这会把别人正在跑的同名资源
  静默收编，reset 再把它删掉。
- *「`down --reset` 必须从任意起始状态都到达同一个终态」* 只点了终态而没有划定它的
  范围，且举的例子只惩罚「删不够」那一侧（跳过 `DROP SCHEMA` 却宣称干净）。它还进
  一步要求：为了清理，**先把服务拉起来**。
- 正文唯一划出的边界——保留 `node_modules`、`~/.m2`、镜像——理由是重建成本。
  性能边界在重建变便宜的那一刻就失效了。
- 反模式清单里关于 reset 只有 *「reset 在没清干净时宣称干净」*。

作为对比，正文给主机身份和凭据各写了一整条。而破坏性操作的作用域——文档里唯一
不可逆的那种失败——一条都没有。

## Decision

不变式写在**核心原则**一级，作为与 *「只写你亲手跑通的东西」* 并列的第二条
`## 核心原则`，而不是塞进阶段五的项目符号里。

位置本身就是决策，不是排版偏好。放在第 111 行的项目符号里，它会紧挨着
*「必须从任意起始状态都到达同一个终态」*——而在两条互相拉扯的指令之间，模型会执行
更具体、更强硬的那条。旧措辞两样都占。所以那四处冲突句是被**原地改写**的，不是简
单增补；只做增量添加，旧压力会原封不动地留下并胜出。

**所有权在删除那一刻可判定**，靠的是命名。因为写 `down.sh` 的 agent 没法依赖「记得
`up.sh` 创建过什么」——那往往是另一个会话里的另一个 agent。落在共享命名空间里的
资源带 `<project>-e2e-` 前缀，删除时**按该作用域枚举**
（`docker ps -aq --filter name=<project>-e2e-`、runbook 自己的 pidfile、`e2e/` 下的
路径），而不是按「这个 compose 文件声明了什么」或「这个目录下有什么」枚举。后两种
枚举正是缺陷所在：它们与所有权毫无关系。由此落下两条硬规则——`docker compose down -v`
只在 project 名被作用域隔离时才允许；文件系统的删除只发生在 `e2e/` 以内。

**所有权可以传递。** 关在 runbook 自己创建的容器里的库不需要再套前缀；拥有容器就
拥有它的内容。这一条不在初稿里——见下。

**隔离要求前移到阶段二**，独立成一条：作用域名、独立 compose project
（`-p <project>-e2e`）、避开服务默认端口。结尾点明它买到了什么，因为这个后果从规则
所在的位置看不见：这一步做错，后面怎么写都是错的。

**借用不等于拥有**成为一条明确的脚本要求。撞到一个你没创建的同名资源，就不 stop、
不 kill、不删、不改它的配置——换名字、换端口，或者明确失败让人来定。幂等规则由此
得到修复：保留，但限定为「跳过**你自己作用域内**已就绪的」。

终态重新定义为「你创建的一个不剩，其余一个不动」，并明确**不是**「环境一片白地」。
阶段六加了一条反向检查，因为原来的复验只可能观察到「删不够」：reset 前后对比
`docker ps -a`、`docker volume ls`、`git status`——多删没有下次，漏删有。

通读时又发现两处同类的松措辞并一并收紧：`down.sh` 的用法注释
（*「额外清数据回到干净态」*），以及 README 模板的第 7 节——现在要求生成的文档既列出
reset 会删什么，**也**列出它刻意不碰什么。

## 反向检验查出了什么

验收门不是「测试绿了」——prompt 改动没法那样证明。验收门是：拿已知的坏产物确认新规则
判它红，拿已知的好产物确认新规则判它绿。完整记录在任务的
`research/ac11-reverse-check.md`。

fastapi-template 三条全红（compose project 未隔离；停了开发者的 backend；在共享
project 上跑 `down -v`）。miniflux 判绿——`miniflux-e2e-pg`、`miniflux-e2e-pg-data`、
端口 5433、只按这两个名字删。

真正值回票价的是那个**绿**。初稿要求「你创建的每个有名字的东西」都带 `<project>-e2e-`
前缀，列举里包含「**数据库/schema**」，据此 miniflux 的 `E2E_DB_NAME=miniflux_test`
会被判红。这个判决是错的：那个库活在 runbook 自己创建的容器里，从不出现在任何删除
列表中，也够不到别人的数据。规则于是改为按**命名空间是否共享**划线——那才是所有权
真正追踪的东西。如果只跑负面对照，一条过严的规则就发布了，而照字面执行的 agent 会
接着去给表名加前缀。

## 同一次变更里带的第二条规则

评审这次改动时，在正文的同一片区域发现了一个不相关的缺口，小到单独立一次变更只会让
两处编辑抢同一个段落。

正文对「这个环境缺一个系统需要的依赖」只有一条出路：标 `[未验证]`，末尾汇报。没有
任何一处让 agent 去**问**。这产生两种失败：降级过早——用户一句话（「X 上有个共享
测试实例」「跑 `make db`」）就能解开的事，被写成半份 runbook；以及一种 `[未验证]`
在结构上根本抓不到的更糟情形——agent 自己起了个 `postgres:latest`、密码自编，健康
检查绿了，写进文档。*「只写你亲手跑通的东西」* 是满足的——它确实跑通了——所以没有
任何闸门触发，而后续每个 agent 都在一个没人部署过的中间件版本上做推理。
**跑通了某个东西，不等于跑通的是对的那个**，而正文从没说过这句。

规则现在落在阶段二、紧挨着「必须真实 vs 可以 mock」那条：正确形态猜不出来时就问
（版本、连接方式、有无现成共享实例、种子数据、凭据来源）；一次问清；先把不依赖答案
的部分做完；绝不悄悄替代。两处接缝把它与其余部分连起来——用户交出来的共享实例是
**借用**的，所有权规则禁止删它；而 `[未验证]` 在核心原则里被重述为「问过之后」的
兜底，覆盖没人可问的非交互场景。反模式清单加了对应的一条。

## What pins it

`skill.spec.ts` 是唯一保护正文的东西，本包没有别的机制。按既定的「少而稳」粒度加了
六条 pin——都是单句而非整段：新标题、借用那句、`docker compose down -v` 的限定条件、
反模式新条目、求取规则的加粗标题、以及点出静默替代陷阱的那句。

每一条都拿改动前已提交的正文撞过、确认不存在——这才区分得开「这条 pin 在守护文本」
与「这条断言写的是一个本来就在的字符串」。

## 这次作废的那条声明

「相对作者原稿的刻意偏离」从三处变为五处——所有权不变式与求取规则。`src/skill.ts`
的模块文档、两份 README、以及 Trellis backend spec 各自声明了这个数，四处在同一次
变更里一起改——这正是 host-identity 那次修复记下的义务，因为同样的原因再次到期。

这条声明在十一天内被两次不相关的改动作废了两回，值得留意一下。一个靠手工维护在四处
的计数，是往后每次变更都得记得的东西；继续付这个成本的理由是：模块文档恰恰就是后来
的 agent 在判断「能不能改正文」之前会读的那份。

## Alternatives considered

**只在阶段五加一条项目符号，别的不动。** 最省事，也一定失败：它落在一条更强硬的
竞争句下面，而且它管的是清理，缺陷却是在拉起时铸成的。

**做一个扫描生成的 `e2e/` 脚本、检查未加作用域的删除的 checker。** 本包 2026-09-11
已从执行器退回纯判断，「没有任何东西验证产出物」是记录在案的边界而非疏漏。当初否掉
host-identity checker 的理由原样适用。

**要求生成的 `down.sh` 带交互确认或 `--dry-run`。** 消费者是短命非交互 shell 里的
agent；确认要么永远阻塞，要么被自动应答。它还会破坏正文赖以成立的 up/check/down
幂等契约。

**干脆禁止 `docker compose down -v`。** 说起来简单，但是错的——在一个正确隔离的
project 上它恰恰是对的命令，禁掉只会把 agent 推向手写删除循环，那更容易出错。

## Consequences

生成的 runbook 拉起会略贵一些：独立 compose project 无法按 project 作用域复用仓库
已拉取的镜像，非默认端口意味着开发者惯用的 `psql` 命令连不到测试库。两样都接受——
否则测试环境与开发环境无法区分，而那正是缺陷本身。

其他仓库里已有的产出物不做追溯修复，由正文的维护模式在下一个 agent 用到它时各自修好。
在那之前那些 `--reset` 依然是破坏性的；`/e2e-test-samples/` 下的两份样本刻意保持原样
作为证据。

执行仍然全靠阅读的 agent 自觉，与正文里其他每一条规则同一姿态。

运行期行为无变化：导出面、`Config`、注册 rank、disposal 均未动，`src/` 没有新增分支，
per-file 覆盖率门不受影响。
