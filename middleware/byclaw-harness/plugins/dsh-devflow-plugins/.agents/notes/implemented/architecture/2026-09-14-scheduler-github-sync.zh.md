# Agent Note: 持久化定时调度与 GitHub 内容接入

Status: implemented

[English](2026-09-14-scheduler-github-sync.md) | 中文

## Problem

仓库监控需要在聊天会话不活跃时继续工作，并在宿主重启后恢复。把定时、远端同步、模型评估和开发放在一起会耦合不同消费者，也会混淆工作投递与工作完成。只存在于内存的通知会丢失消费者离线期间的变化。

## Decision

两项可选能力分别持有状态。定时器负责计划与触发投递；GitHub 同步负责订阅、同步运行、内容版本、持久化变更及独立消费位置。每项能力都有服务定义和本地 SQLite 提供者，通过 Cordis 服务协作。现有 Harness agent 仍是 Devflow 工作流执行者。

可选的 `github.sync` 处理器接收稳定的触发 ID，只在运行接收记录持久化后返回。定时器查询特定运行的状态，不把 agent 空闲或接收成功解释为工作完成。处理器注册由注入 fiber 持有，任一服务不可用时释放。手动同步不依赖定时器。

快照与对应变更在同一个 SQLite 事务中提交。消费者读取变更对应的内容版本，确认自己已经读取的序号，并容忍确认未完成后的重复投递。外部内容只作为数据，不授权执行工具或修改权限。凭证不进入内容记录。

本地数据库事务与执行代次约束取消或接管后的持有权。SQLite 文件必须位于受支持的本地文件系统，这不是分布式执行集群。运行错误与资源限制必须可见，不能表示为同步成功。

取消重试携带持久化取消标记；如果尚无运行，GitHub 接收时保存已取消回执，因此迟到的普通投递不能新建工作。显式恢复保留失败或部分完成的运行标识及已提交页面检查点，但拒绝已变化的基线或存在其他活跃同步的情况。容量管理持久化调用者和时间。定时器参数是无损 JSON 快照，在校验和保存前复制。

## Alternatives considered

**会话提醒。** 现有提醒需要存活的根 agent 才能投递后续消息，仓库监控则必须在没有活跃会话时继续运行。

**单个 Issue 到开发插件。** 将发现与业务决策组合会妨碍摘要和知识整理复用。评估与 Devflow 接入保持为同步内容的消费者。

**纯内存事件。** 仅依靠事件不能支持离线消费者和重启恢复。持久化记录拥有投递历史，通知仅改善延迟。

**共享工作流状态。** 复制 Devflow 阶段会与已有 gates 和 journal 状态竞争。这些能力不创建或流转卡片。

## Consequences

四个包可以在不修改 Harness、不启用自动开发的情况下组合。调用方必须区分接收与完成，并保证消费副作用幂等。保留历史内容支持回放，同时需要明确的容量管理。真实 Loader 测试覆盖可选接入、下游失败、取消和持久化消费；安装与运行验收证据独立于构建结果记录。
