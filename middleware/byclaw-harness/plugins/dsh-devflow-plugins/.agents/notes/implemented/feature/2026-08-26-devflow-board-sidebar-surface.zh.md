# Agent Note：devflow——看板只呈现一套面，侧边栏页面或悬浮控件

Status: implemented

[English](2026-08-26-devflow-board-sidebar-surface.md) | 中文

本记录中的宿主集成决策已由[接入 Harness 官方右侧栏](2026-09-08-devflow-official-right-sidebar.zh.md)取代。这里保留历史理由，用来解释已经删除的兼容路径。

## Problem

devflow 看板此前是一个悬浮弹层：经 body portal 固定在对话区右上角，宽 344px（打开详情加宽到 460px）、高度封顶 `min(480px, 60vh)`。前三份 PRD 加进来的东西——需求正文 Markdown、标注阶段名的流水线、拆分关系、完整流转时间线——全都在这个盒子里抢地方；而且弹层点击外部或按 Esc 就消失，因此它永远不可能成为"你一边干活一边开着"的那样东西。与此同时，工作区之外的生态插件 [`dsh-better-sidebar`](https://github.com/omdsh-dev/DSH-better-sidebar) 已经把自己做成了开放的侧边栏底座：`ctx.betterSidebar` 服务注册三方页面，与它自带的七个内置页面能力完全对等——整列高度、用户可拖拽宽度、按会话隔离，正是看板需要的容器。

## Decision

看板有两套面，且任一时刻只呈现一套。

- **由底座是否在场决定用哪一套，且决定发生在同一处。** 一个选择器按服务名读取底座，把悬浮面或侧栏面作为子 fiber 挂载，并在 `internal/service` 报告底座出现或离开时换掉。两条各自判断底座的注册路径，正是"部署里冒出两个看板"的成因；选择器让那种状态无法表示。
- **对底座零依赖。** 既不 import（连 type-only 也不）也不写进 `package.json`；只在本地重述本插件调用的那一小片服务，一切经服务名交互。type-only import 虽能同时满足两边的纯度门，却会引入一条指向本仓库无法解析的包的声明依赖，而 `verify-client-packages` 只认工作区包。生态里的三方页面（`dsh-sentinel`、`ego-browser`）也是同一种接法。
- **可选注入，而不是声明式注入。** `ctx.inject([...], cb)` 无法表达"当它**不在**时激活"，因此悬浮面不能骑在它上面；选择器改为读 `ctx.get(name)` 并监听变化。把底座写进插件自己的 `inject` 从来不是选项——那会让所有没装底座的部署里插件根本不激活。
- **视图与面无关，只有外壳不同。** 紧凑卡片列表与详情表单接收的都是普通值——没有 slot 合成的 hook，没有 store 句柄。悬浮面保留胶囊、portal、紧凑列表与消失行为；侧栏页没有这些外壳，负责填满底座持有的 pane，并默认使用[以阶段为中心的 Kanban](2026-08-31-devflow-stage-centric-kanban.zh.md)，同时保留紧凑列表替代视图。侧栏路径自己组装原本由 slot 渲染机器合成的东西：翻译取自 `ctx.locale.bind`，快照来自订阅插件自己的 store。
- **注册被拒绝只告警，然后继续。** 底座会拒绝重复的页面 id；那是部署的组合问题，不构成把插件的词典、拉取与会话反链一并拖垮的理由。
- **页面绑定自己的 scope；重取跟随"有人在看"。** 看板状态按会话一个绑定；页面用的是底座交给它的那个 scope 的绑定，而不是应用当前摆在前面的会话。转发的 devflow 事件重取"有可见页面正在关注"的绑定**加上被选中会话的那个**——也就是 tab 角标与 `+` 菜单报告的那个——因此属于其他会话的后台 tab 不产生任何开销，而用户眼前的角标保持实时。角标与页面统计头用同一个谓词计数"进行中"，因此 tab 上的数字不可能与它下面那行自相矛盾。描述符的只读回调只查不建：底座会在每次 tab 栏渲染时、对它手上任意 scope 调用它们。
- **能力按名字探测，而不是按版本号。** 角标、页面自有设置与状态订阅各自按底座的 `features` 清单门控；一个都不宣告的底座仍然得到一个可用的页面。
- **并列是持久化的页面设置，不是宽度断点。** 面板宽度由用户拖拽且跨会话共享，jsdom 又量不出布局，因此断点既无法验证也不可预期。底座本就持久化页面自有设置并重新发布，这让这个偏好在宿主设置页里可被发现，在这里也可被测试。

## Alternatives considered

- **两套面并存**——拒绝：一个看板两个入口、两份开合状态，而且没有任何东西告诉用户该点哪个。
- **无条件搬进侧栏**——暂时拒绝：那会让所有没安装底座的部署失去看板，而底座是我们并不控制的生态插件。
- **为拿到描述符类型而 type-only import 底座**——拒绝：理由同上；本地重述只花几个接口，且不欠工作区之外的包任何东西。
- **在激活时一次性决定**——拒绝：插件激活顺序不由我们掌握，晚于看板激活的底座将被永远错过。

## Consequences

组合了底座的部署里看板是一个侧边栏页面（`dsh-devflow:board`，单实例，order 60，标题按渲染重读因而跟随语言切换）；其余部署里悬浮控件与此前逐字节一致，这一点由既有的双工作区浏览器 e2e 持续证明。底座无法在本仓库的测试通道里启动，因此组合经注册在同一服务名下的桩服务验证——注册、双向互斥、处置、拒绝隔离——侧栏页面的渲染则在 jsdom 里针对插件真实的 store 验证。真实侧栏渲染靠在装了底座的 profile 上手测，这一缺口是有意的，并已记录在 PRD 中。
