# Agent Note: devflow — file-backed task cards behind a capability seam

Status: implemented

English | [中文](2026-08-25-devflow-file-based-task-cards.zh.md)

## Problem

The harness has no cross-session, cross-agent record of development work: todos are per-session, a goal is one objective in one session, and a workflow run is one foreground execution. Nothing answers "which stage is this piece of work at, who holds it, and what history led here" in a form that humans, git, CI, and agents can all read and write without a service. The PRD (`.agents/prd/2026-08-25-devflow-file-based-dev-state.md`) requires the state carrier to be files with an auditable, replayable history.

## Decision

A new capability seam `ctx.devflow` in `packages/devflow/`, three roles from the start:

- `dsh-devflow` (Service Definition) owns the vocabulary — `DevCard`, the closed `DevStage` union (`draft | designing | ready | developing | reviewing | testing | done`, with `blocked` as a bypass location that remembers its origin stage), branded `DevflowCardId`, the journal entry union — plus the journal decode/replay every consumer shares and the abstract `DevflowStore`.
- `dsh-devflow-filesystem` (Service Provider) maps cards to `<root>/tasks/<id>/` directories: `card.md` (YAML frontmatter projection + Markdown body) and append-only `journal.jsonl`.
- `dsh-tool-devflow` (Consumer) registers the model-facing tools: reads (`devflow_list` / `devflow_show`), lease-taking and revision-checked moves (`devflow_take` / `devflow_transition`), and artifact registration (`devflow_attach_artifact`).
- `dsh-devflow-gates` (policy Consumer) runs deployment-configured gate commands on the `devflow/transition` waterfall through `ctx.shell`; a failing command vetoes before the commit with a bounded output summary. Gate commands live only in configuration (global per-edge lists plus per-card-id overrides), never in card files, so a developing agent cannot rewrite its own gates. `approvals` edges additionally require a one-shot human decision over `ctx.approval` — the interaction plane, never the model conversation, because the gate exists to check the agent — and an approved commit carries `gate.approvedBy` in its journal entry. With no reachable responder (non-agent initiator, absent service, or fail-closed `unavailable`) the move is vetoed and the card parked `blocked` by a `command devflow-gates` actor, so unattended runs exit cleanly and a human resumes later.

The journal is the authority and the frontmatter a projection: reads replay the journal (`foldJournal` enforces contiguous revisions, created-first, current-location departures, and exact blocked recovery), a structurally invalid journal fails the read loudly naming file and line, and projection drift is warned and overridden. This mirrors the session log's event-sourcing posture, so later slices can log agent-driven transitions with "model-visible ⟺ logged" intact.

The write path commits at the journal append: `transition` runs revision CAS, edge legality, and the `devflow/transition` waterfall (the gates extension point) before appending, then rewrites the projection (failure only warns) and emits `devflow/stage-changed`, whose revision-monotonicity invariant the Definition companion owns. Domain rejections resolve with stable codes rather than rejecting, mirroring the shell seam's result posture. `claim` is an `O_EXCL` lease file with heartbeat and idempotent release — the cross-process exclusivity mechanism, since the journal append itself carries no file lock. The model-facing mutations (`devflow_take`, `devflow_transition`) require an owning agent session and record each committed move as a `devflow/transition` Session event, keeping "model-visible ⟺ logged" while the `.devflow` journal stays the authority. Event vocabulary was declared together with its first dispatcher, per the repository's dead-vocabulary gate. The stage driver (`dsh-devflow-driver`) is a queueing Consumer over the subagent seam: one synthetic never-prompted parent per card root anchors lineage and workspace, each dispatched child receives the current deployment model route plus the card objective and a fixed tool contract, leases heartbeat while children run, failures park the card `blocked`, and revision regressions trigger a quiet rescan. One executor kind ships (one-shot subagent); the PRD's `goal` and Ralph executors are deferred until the driver can own a live host agent per card. The read face reaches the browser over the Remote BFF: `DevflowStore` extends `TypertRemoteService` with `@Remote` `list`/`read` adapters, the API layer forwards `devflow/stage-changed`, and `dsh-client-ui-devflow` contributes one read-only board control in the session header's right-aligned utility cluster (the design's top-right anchor) whose activation defers on the mounted `remote.devflow` namespace sub-service (the `remote.<namespace>` inject pattern every Remote consumer follows) and that fetches at activation, once per established connection (`connection/reset`), and once per forwarded event — no write channel, because approval responses already ride the existing approval composer and every mutation belongs to the model tools or the command plane. That deterministic plane is `dsh-command-devflow`: `/devflow` (board), `show`, `move` (through the ordinary executor at the card's current revision, so gates still decide), `takeover` (any past heartbeat counts as stale; the eviction journals `claim-expired` and the stale holder's next commit fails the CAS), and `archive` over the seam's `archiveDone`, which renames each `done` card's directory whole into `archive/<YYYY-MM>/<id>/` keyed by its last journal entry's month. Every command effect carries the `command devflow` journal actor.

## Alternatives considered

- **Directory-per-stage (moving card files between stage folders)** — rejected: renames break watcher identity and git continuity, and the state transition would live in a filesystem move that cannot carry a validating pipeline.
- **Frontmatter as authority with no journal** — rejected: no audit trail, no replay after corruption or manual edits, and concurrent writers would silently overwrite each other's state.
- **A single package** — rejected: the seam's three roles evolve independently (a future GitHub-Issues or SQLite provider must not touch the tools), and the glossary's capability-seam rule requires the complete trio.

## Consequences

Humans can hand-edit cards and the provider converges on the journal instead of trusting the edit — bought auditability, cost a mandatory journal file per card and fail-loud reads that make a malformed journal block that card until repaired. Putting every rejection in the executor (CAS, edges, rework reasons, gate vetoes) bought bypass-proof enforcement at the cost of the waterfall dispatch on every move. The driver's single-executor scope bought an early end-to-end pipeline while deferring per-card host agents; until then a driven child that lacks the devflow tools can only report, leaving its card in place. Archiving is write-only — no seam operation lists or restores archived cards — and the forced takeover's staleness test is a strict age comparison, so a same-millisecond or future-dated heartbeat still counts as live.
