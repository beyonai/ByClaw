# Agent Note：升级 Harness 至 `0.1.3-alpha.2`，以及 session seam 的三处移除

Status: implemented

[English](2026-09-08-harness-0.1.3-alpha.2-adaptation.md) | 中文

## 问题

按 `AGENTS.md` 的"Harness version"规则，本插件线把每个 `@deepseek-ai/*` 依赖固定在
`0.1.2-alpha.3`。DeepSeek Harness 已发布 `0.1.3-alpha.2`（tag `dsh-v0.1.3-alpha.2`），
两个 tag 之间有四个标记为 `!` 的提交，全部落在 session 域：

- `f99b06eaed feat(session)!: embed assistant streams in format v2`
- `bec6805d6a refactor(session-persistence)!: handle-based seam with a lifecycle-owned write path`
- `d1521ea783 feat(session)!: add released format migration`
- `27bf1039db refactor(session)!: distinguish event seqs from log offsets`

## 决定

所有 `@deepseek-ai/dsh-*` 依赖移至 `0.1.3-alpha.2` —— 根清单与全部 19 个
`packages/*/package.json` 中共 160 条，`dependencies`、`peerDependencies`、
`devDependencies` 一并处理 —— 另加 `pnpm-workspace.yaml` 中 65 条对应的
`minimumReleaseAgeExclude` 条目。

**本次无需做任何包迁移。** 本线依赖的 33 个 `dsh-*` 包逐个用
`npm view <pkg>@0.1.3-alpha.2 version` 验证，33 个全部可解析。这正是 versioning spec
§2 的调研命令用来判别的场景，而结论与 `0.1.2-alpha.3` 那次相反 —— 那次
`dsh-client-runtime` 已被上游删除。

`cordis`（`4.0.2`）、`cordis-plugin-include`（`1.0.7`）、`cordis-plugin-loader`
（`1.0.3`）与 `schemastery`（`^3.18.1`）保持不变：各自已与该 tag 下 harness 自身
`vendor/` 树中的版本一致。

`pnpm install` 向 `minimumReleaseAgeExclude` 新增了三个传递依赖 ——
`dsh-client-file-upload`、`dsh-http-proxy`、`dsh-win32-process`，均为
`0.1.3-alpha.2`。它们由已固定的包间接引入，本仓库并不直接依赖。

## 升级破坏了什么，以及用什么替代

本线导入的每个符号在新版本中都依然存在；三处破坏全部是调用点的形状变更。

| 移除 / 变更 | 此处采用的替代 | 调用点数 |
|---|---|---|
| `SessionHeader` 新增必填 `isSeeded: boolean` | `isSeeded: false` | 16（`src` 1 处，测试 15 处） |
| `SessionPersistence.inspect(id)` → `.meta` | `SessionPersistence.stat(id)` → `.header` | 1（`packages/devflow/src/index.ts`） |
| `Session.events`（getter） | `Session.snapshotEvents()` | 3（`src` 1 处，测试 2 处） |

**`isSeeded`** 记录一个 Session 是否携带 fork 继承来的事件前缀。本线构造的每个 header
都是全新的合成 session —— `devflow-agent-gate` checker 的合成父级，以及各包的测试
fixture —— 因此 16 处一律填 `false`。这与 harness 自身在不带 header 调用
`Session.create` 时所盖的值一致。

**`stat` 取代 `inspect`**，用于在不读取事件日志的前提下读出已存储 session 的 `cwd`，
对本用途也是更轻的调用。真正要紧的是契约差异：`inspect` 对不存在的 session **抛错**，
而 `stat` **解析为 `undefined`**。`DevflowStore.sessionRoot` 的文档写明"未知 session
是一次稳定的拒绝，而非静默读取默认根"，因此 `undefined` 分支现在显式抛错。若直接照搬
替换，每个未知 session 都会变成静默读取默认根。

`packages/devflow/tests/devflow.spec.ts` 中的 `sessionPersistence` 替身改用 `stat`，
并且现在同时建模真实 seam 的两种失败模式 —— 不存在（`undefined`）与故障（拒绝），
此前它只建模了拒绝。

**`snapshotEvents()` 取代 `events` getter。** 不传参时覆盖整个日志，这正是 `events`
的返回范围。同族的 `ownEvents()` 在这些调用点被否决：它会丢掉 fork 继承前缀，从而让
`devflow-iron-rules` 把 fork 之前已发布的规则视为从未发布，并在 forked session 的每
一步重复发布。

**checker 的合成父代理不再在运行时导入 `Inbox` 构造器。** 已发布 alpha 会导出该构造器，
但 Harness master 后续版本把 Inbox 改成了驱动拥有的接口，因此不再导出运行时值。
`devflow-agent-gate` 并不需要任何一边的实现：它的父代理只是注册过的谱系/工作区锚点，
永远不会被驱动。现在它提供一个惰性的结构化 Inbox，同时包含已发布 alpha 的旧
`hasPending` 与 `claim` 成员，并把兼容性断言收口在一处；`InboxTarget` 只作类型依赖。
因此包仍固定在已发布表面，同时同一个 tarball 也能在较新的纯接口运行时中加载。

seq/offset 品牌分离（`27bf1039db`）无需改动。本线两处涉及 seq 类型的调用点 ——
`devflow-iron-rules` 的 `visible.has(event.seq)` 及其 loader-composition 用例中的
`surfaceOp` 区间 —— 都是从 session 值中取出品牌再传回 session API，没有任何一处用裸
`number` 构造品牌值。

## 一次值得记录的假绿 typecheck

在依赖图已换新、而 `packages/devflow-iron-rules/src/inject.ts` 仍调用已移除的
`Session.events` 时，`tsc -b tsconfig.json` 报告成功。原因是增量构建：`.tsbuildinfo`
早于 `node_modules` 的替换，而依赖的 `.d.ts` 变化并未改动任何输入文件，项目看上去仍是
最新的。`tsc -b --force` 立刻报出了该错误。

`oxlint` 独立地发现了它，形式是 `error` 类型的成员访问而非属性缺失 —— 其类型感知
pass 自建 program，不读取 `.tsbuildinfo`。

**依赖升级之后，请用 `tsc -b --force` 做类型检查。** 一次增量 `tsc -b` 不足以证明新
接口能对上。

`tsc -b` 同样不覆盖 `packages/*/tests/**`；那里残留的两处 `Session.events` 调用点由
`oxlint` 发现，否则会在 `vitest` 下以运行时 `TypeError` 的形式暴露。

## 发布门禁的跨平台收尾

第一次 `0.4.0-dev.2` 发布尝试在上传任何包之前停止：Linux 发布 runner 暴露了两个
对调度敏感的测试，Windows CI runner 则暴露了 75 个失败。Windows 的失败并不是 75 个
产品缺陷，而是共同来自四个跨平台问题：

- 部署命令替身用写死的 `:` 拼接 `PATH`，导致 Windows 实际调用了 runner 上的 Docker
  与 SSH；
- 文件 URL 与一处规则目录期望没有转换 Windows 盘符；
- Job 终止的进程在 Windows 上返回数字退出码，而 POSIX 返回信号，即使上层语义明确是
  超时或取消；
- Vitest 默认的 5 秒外层预算在 CI 负载下会与真实进程清理竞争，而被测行为已有自己的
  明确截止时间。

命令替身现在使用平台 `PATH` 分隔符，并在 Windows 安装由 Node 承载的原生 `.exe`
入口，再由预加载分派器转发到保持原始运行时相对路径的 Git shell。测试替身把部署主机
的 POSIX 路径与本机断言使用的原生路径明确分开。`fileURLToPath`
统一处理文件 URL，路径期望从解析后的根目录推导；真实进程夹具改用 Node 报告的 PID
与工作目录，不再依赖仅适用于 POSIX 的 `$$` 和 `pwd` 表示。Testenv 把超时
和取消归一化为“没有正常退出码”，并把取消后 runner 的拒绝视为所请求的取消结果。
Iron-rule 的超时标记来自它自己持有的截止时间，不再依赖平台特定的退出形状。测试外层
预算调整为 20 秒，所有产品内部截止时间保持不变。

## 考虑过的替代方案

**跟随 harness `master`（`c389f96bf3`）而非已发布的 tag。** 否决：versioning spec §3
只接受 npm 已发布的依赖，其 §3.3 的 git 依赖 fallback 仅保留给"上游删包且无已发布后继"
的情形 —— 本次并非如此，33 个包全部可解析。

**导入较新驱动的具体 Inbox 实现。** 否决：该实现属于 `dsh-agent-loop`，不是本包依赖的
缝，而且会把一次兼容修复变成对未发布内部实现的依赖。合成父代理没有要驱动的 loop，
惰性结构值表达的是更窄也更真实的契约。

**用 `ownEvents()` 替代 `events`。** 否决：它会改变 forked session 上的行为，而非保持
原行为。理由见上。

**让 `stat` 的 `undefined` 直接落到 `rootOfCwd(undefined)`。** 否决：这能编译通过、也
能让旧断言通过，却会把"未知 session"静默转换为"读取默认根" —— 正是该方法自身文档所
禁止的失败方式。

## 后果

`pnpm run verify`（typecheck + lint + test）、`pnpm run test:coverage`、
`pnpm run build` 与 `pnpm run preflight:tarballs` 在新固定版本下全部通过：
1221 个测试，`packages/*/src` 的语句/分支/函数/行覆盖率均为 100%。

把 `peerDependencies` 移到 `0.1.3-alpha.2`，对仍在 `0.1.2-alpha.3` 上组合的消费者是
破坏性变更；这是精确固定规则的既定后果，而非此处引入的回归。

两个发布通道都未执行。本次改动只准备好固定的依赖图 —— versioning spec 视
`pnpm publish` 为不可逆操作，要求单独的人工确认。
