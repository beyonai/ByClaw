# Agent Note: Harness bump to `0.1.3-alpha.2`, and the session seam's three removals

Status: implemented

English | [中文](2026-09-08-harness-0.1.3-alpha.2-adaptation.zh.md)

## Problem

This line pinned every `@deepseek-ai/*` dependency to `0.1.2-alpha.3`, per
`AGENTS.md`'s "Harness version" rule. DeepSeek Harness published
`0.1.3-alpha.2` (tag `dsh-v0.1.3-alpha.2`), and the window between the two
tags carries four `!`-marked commits, all in the session domain:

- `f99b06eaed feat(session)!: embed assistant streams in format v2`
- `bec6805d6a refactor(session-persistence)!: handle-based seam with a lifecycle-owned write path`
- `d1521ea783 feat(session)!: add released format migration`
- `27bf1039db refactor(session)!: distinguish event seqs from log offsets`

## Decision

Every `@deepseek-ai/dsh-*` dependency moves to `0.1.3-alpha.2` — 160 entries
across the root manifest and all 19 `packages/*/package.json`, in
`dependencies`, `peerDependencies`, and `devDependencies` alike — plus the 65
matching `minimumReleaseAgeExclude` entries in `pnpm-workspace.yaml`.

**No package migration was needed this time.** Each of the 33 `dsh-*` packages
this line depends on was checked individually with `npm view <pkg>@0.1.3-alpha.2
version`; all 33 resolve. This is the case the versioning spec's §2 research
command exists to distinguish, and it came out the opposite way from the
`0.1.2-alpha.3` bump, where `dsh-client-runtime` had been removed upstream.

`cordis` (`4.0.2`), `cordis-plugin-include` (`1.0.7`), `cordis-plugin-loader`
(`1.0.3`), and `schemastery` (`^3.18.1`) are unchanged: each already matches the
version in the harness's own `vendor/` tree at this tag.

`pnpm install` added three new transitive packages to
`minimumReleaseAgeExclude` — `dsh-client-file-upload`, `dsh-http-proxy`, and
`dsh-win32-process`, all at `0.1.3-alpha.2`. They are pulled in by the pinned
packages, not depended on directly here.

## What the bump broke, and what replaced it

Every symbol this line imports still exists at the new version; all three
breakages are shape changes at a call site.

| Removed / changed | Replacement used here | Sites |
|---|---|---|
| `SessionHeader` gained a required `isSeeded: boolean` | `isSeeded: false` | 16 (1 in `src`, 15 in tests) |
| `SessionPersistence.inspect(id)` → `.meta` | `SessionPersistence.stat(id)` → `.header` | 1 (`packages/devflow/src/index.ts`) |
| `Session.events` (getter) | `Session.snapshotEvents()` | 3 (1 in `src`, 2 in tests) |

**`isSeeded`** records whether a Session carries a fork-inherited event prefix.
Every header this line constructs is a fresh synthetic session — the
`devflow-agent-gate` checker's synthetic parent, and per-package test
fixtures — so all 16 declare `false`. That matches what the harness itself
stamps when `Session.create` is called without a header.

**`stat` replaces `inspect`** as the way to read a stored session's `cwd`
without reading its event log, and it is the lighter call for this use. The
contract difference is the part that mattered: `inspect` *threw* for an absent
session, while `stat` *resolves `undefined`*. `DevflowStore.sessionRoot`
documents "an unknown session is a stable rejection, not a silent default-root
read," so the `undefined` case is now an explicit throw. A naive swap would
have turned every unknown session into a silent read of the default root.

`packages/devflow/tests/devflow.spec.ts`'s `sessionPersistence` double moves to
`stat` and now models both failure modes the real seam has — absent
(`undefined`) and faulted (rejection) — where it previously modelled only
rejection.

**`snapshotEvents()` replaces the `events` getter.** With no arguments it spans
the whole log, which is what `events` returned. The sibling `ownEvents()` was
rejected for these call sites: it drops the fork-inherited prefix, which would
make `devflow-iron-rules` treat rules published before a fork as never
published and republish them on every step of a forked session.

**The synthetic checker parent no longer imports the `Inbox` constructor at
runtime.** The published alpha exposes that constructor, but later Harness
master revisions make Inbox a driver-owned interface and therefore export no
runtime value. `devflow-agent-gate` needs neither implementation: its parent is
a registered lineage/workspace anchor that is never driven. It now supplies an
inert structural Inbox, including the published alpha's legacy `hasPending` and
`claim` members, behind one localized compatibility assertion. `InboxTarget`
stays a type-only dependency. This keeps the package pinned to the published
surface while allowing the same tarball to load when the newer interface-only
runtime is present.

The seq/offset brand split (`27bf1039db`) required no change. This line's two
seq-typed call sites — `devflow-iron-rules`'s `visible.has(event.seq)` and its
loader-composition spec's `surfaceOp` range — read brands out of session values
and pass them back into session APIs; neither builds one from a bare `number`.

## A false-green typecheck worth knowing about

`tsc -b tsconfig.json` reported success against the new dependency graph while
`packages/devflow-iron-rules/src/inject.ts` still called the removed
`Session.events`. The build was incremental: `.tsbuildinfo` predated the
`node_modules` swap, and changing a dependency's `.d.ts` without changing any
input file left the project looking up to date. `tsc -b --force` reported the
error immediately.

`oxlint` caught it independently, as `error`-typed member access rather than a
missing property — its type-aware pass builds its own program and does not
consult `.tsbuildinfo`.

**After a dependency bump, typecheck with `tsc -b --force`.** An incremental
`tsc -b` is not evidence that the new surface fits.

`tsc -b` also does not cover `packages/*/tests/**`; the two remaining
`Session.events` call sites there were found by `oxlint` and would otherwise
have surfaced as a runtime `TypeError` under `vitest`.

## Release-gate portability follow-up

The first `0.4.0-dev.2` release attempt stopped before publishing when the
Linux release runner exposed two scheduling-sensitive tests and the Windows CI
runner exposed 75 failures. The Windows failures shared four portability
causes rather than 75 product defects:

- deployment command doubles joined `PATH` with a literal `:` and therefore
  reached the runner's real Docker and SSH executables on Windows;
- URL pathnames and one expected rules path were used without Windows drive
  conversion;
- a Job-terminated process reports a numeric exit on Windows where POSIX
  reports a signal, even when the higher-level result is a timeout or cancel;
- the default five-second Vitest envelope raced real-process teardown under CI
  load, while the behavior under test had its own explicit deadline.

Command doubles now install native `.exe` entry points backed by Node on
Windows, with a preload dispatcher forwarding to Git's shell at its original
runtime-relative location, and use the platform `PATH` delimiter. Test doubles
keep deployment-host POSIX paths separate from native paths used for local
assertions. File URLs cross `fileURLToPath`; path expectations derive from the
resolved root. Real-process fixtures use Node-reported PIDs and working
directories rather than POSIX-only `$$` and `pwd` representations. Testenv
normalizes timeout and cancel to no normal exit code and treats a
post-cancellation runner rejection as the requested cancellation outcome.
Iron-rule timeout reporting is derived from its owned deadline rather than a
platform-specific exit shape. The outer test envelope is 20 seconds, while all
product deadlines remain unchanged.

## Alternatives considered

**Track harness `master` (`c389f96bf3`) rather than the published tag.**
Rejected: the versioning spec's §3 admits only npm-published dependencies, and
its §3.3 git-dependency fallback is reserved for a package removed upstream with
no published successor — which is not this case, since all 33 resolve.

**Import the newer driver's concrete Inbox implementation.** Rejected: the
implementation belongs to `dsh-agent-loop`, is not the seam this package
depends on, and would turn a compatibility fix into a dependency on an
unreleased internal. The synthetic parent has no loop to drive, so an inert
structural value states the narrower truth.

**Use `ownEvents()` for the `events` replacement.** Rejected: it changes
behavior on forked sessions rather than preserving it. See above.

**Let `stat`'s `undefined` fall through to `rootOfCwd(undefined)`.** Rejected:
it compiles, passes the old assertions, and silently converts "unknown session"
into "read the default root" — the failure the method's own doc comment forbids.

## Consequences

`pnpm run verify` (typecheck + lint + test), `pnpm run test:coverage`,
`pnpm run build`, and `pnpm run preflight:tarballs` all pass at the new pins:
1221 tests, 100% statements/branches/functions/lines on `packages/*/src`.

Moving `peerDependencies` to `0.1.3-alpha.2` is a breaking change for consumers
still composing against `0.1.2-alpha.3`; that is the standing consequence of the
exact-pin rule, not a regression introduced here.

Neither publish channel was run. This change prepares the pinned dependency
graph only — the versioning spec treats `pnpm publish` as irreversible and
requires separate human confirmation.
