# Agent Note:将 harness 升级到 `0.1.2-alpha.3`,以及 `dsh-client-runtime` 的拆分

Status: implemented

[English](2026-08-31-harness-0.1.2-alpha.3-adaptation.md) | 中文

## Problem

本线将每一个 `@deepseek-ai/*` 与 `cordis*` 依赖都钉死在一个确切的预发布版本上(`0.1.1-rc.2` / `cordis@4.0.1`),这是 `AGENTS.md`"Harness version"一节定的规矩。DeepSeek Harness 的 `master` 已领先这个钉住的版本 1430 个提交(到 `dd6322d604`,tag `dsh-v0.1.2-alpha.3`),`npm view <pkg> versions --json` 显示本线所依赖的每一个包都已发布 `0.1.2-alpha.3` —— 唯独 `@deepseek-ai/dsh-client-runtime` 没有任何 `0.1.2-*` 版本,因为 harness 已将其移除
(`be531688f3 refactor(client): migrate consumers and remove Runtime`、`3a23185edb chore(client): align split package graph`)。若继续钉在 `0.1.1-rc.2`,本线就会依赖一个永远不会再发布目标版本的包 —— 这正是 `.trellis/spec/dsh-devflow-plugins/versioning.md` 里已经点名的"Bad"用例。

## Decision

每一个 `packages/*/package.json` 里的 `@deepseek-ai/*` 与 `cordis*` 依赖(不只是设计文档列出的根 manifest 与 `devflow-ui`)现在都钉住 `0.1.2-alpha.3`(`cordis` `4.0.2`、`cordis-plugin-include` `1.0.7`、`cordis-plugin-loader` `1.0.3`)。本线自身各包的版本号也通过 `pnpm run set-version 0.1.2-alpha.3` 对齐到同一版本。

`@deepseek-ai/dsh-client-runtime` 被移除。本线对它的实际用法(通过 `grep -rl 'dsh-client-runtime' packages` 找出,再对照 harness 移除前的最后一份源码 `packages/client/runtime/src/client/index.ts` 确认)拆分为三份:

| 旧符号(来自 `dsh-client-runtime/client`) | 新来源 | 种类 |
|---|---|---|
| `ClientContext` | `import type { Context as ClientContext } from '@deepseek-ai/cordis'` | 仅类型 |
| `SlotRegistry` | `@deepseek-ai/dsh-client-ui-renderer/client` | 值(类) |
| `createSnapshotStore`、`SnapshotStore` | `@deepseek-ai/dsh-client-store`(根入口 —— 该包不带 `./client` 子路径) | 值 + 类型 |
| `SettingsScope`、`SettingsScopeSnapshot` | `@deepseek-ai/dsh-client-ui-settings/client` | 仅类型 |

`packages/devflow-ui` 的六处调用点(`src/client/{binding,index,board}.ts`、`tests/{harness-doubles.ts,browser-plugin.client.spec.tsx}`,以及它自己的 `package.json`)现在都改为从这些继任包导入。

**`packages/devflow-ui/package.json` 的 `dsh.client.inject` 数组里还藏着第三处 `dsh-client-runtime` 引用**(设计文档基于 grep 的调用点清单只找到了 `devDependencies` 与 `peerDependencies` 两处)。这个数组是 harness loader 的挂载顺序声明 —— 在本插件的 `apply()` 运行之前必须已存在的那些包的 `ctx` 服务 —— 不是一份导入清单,所以 `tsc` 推断不出它。`devflow-ui` 的插件体声明了 `inject = ['sessions', 'slots', 'locale']`;`dsh-client-runtime` 过去同时提供 `sessions`(`SessionRuntime`)与 `slots`(`SlotRegistry`)。对比 `3a23185edb` 中若干同样迁移了这个 `inject` 数组的 harness 包(`ui-commands`、`ui-goal`、`locale`、`ui-brand-official` 等)后,可以看出一致的继任映射:`slots` 现在来自 `@deepseek-ai/dsh-client-ui-renderer`,`sessions` 来自 `@deepseek-ai/dsh-api-session-controller`(通过在 harness 源码里搜索 `rootCtx.reflect.provide('sessions', ...)` 确认,如今它位于 `packages/api/session-controller/src/client/sessions/service.ts`,而不是某个与 runtime 相邻的包里)。`devflow-ui` 现在把两者都声明为 `peerDependencies`/`devDependencies`,并在 `dsh.client.inject` 里同时列出两者(以及已有的 `dsh-client-locale`、`dsh-client-ui-conversation`、`dsh-client-ui-primitives`)。`@deepseek-ai/dsh-client-store` 不需要任何加载顺序条目 —— 它发布出来的形态是一个普通的 node/ESM 库(只有 `main`/`exports['.']`,没有 `dsh.client` 字段),不是一个 `dsh.client` 插件,所以它只是一个普通依赖,外加浏览器打包模块表里的一条记录。`@deepseek-ai/dsh-client-ui-settings` 仍只作为 `devDependencies` 条目:目前找到的所有用法(`tests/harness-doubles.ts` 里的 `SettingsScope`、`SettingsScopeSnapshot`)都是 `import type`,局限在测试内,从未出现在 `devflow-ui` 自己对外的类型表面里。

浏览器打包模块表(`tsdown.client.ts` 的 `MODULE_TABLE`、`tests/loader-factory.ts` 的 `STATIC_TABLE`、`vitest.config.ts` 的 `CLIENT_BUNDLES`)现在改为提供 `@deepseek-ai/dsh-client-store`(普通导入,不带 `/client`)与 `@deepseek-ai/dsh-client-ui-renderer/client`,替换掉 `dsh-client-runtime/client`。`tests/loader-factory.ts` 还需要额外补上普通的 `dsh-client-store` 条目,原因看似无关:一旦加载,`@deepseek-ai/dsh-client-locale/client` 自己发布的 bundle 内部会 `require()` `@deepseek-ai/dsh-client-store`(harness 自己的 `locale` 包在 `3a23185edb` 迁移时选用了同一个继任包),于是递归的模块表解析器在本仓库自己的表能回答这个请求之前就会抛错 —— 这正是 `tests/loader-factory.ts` 自己文档注释里点名的"bundle 请求了表里没有的东西就在这里抛错"这一种情况,不是本仓库用法上的缺陷。

## 这次升级还暴露出的、设计文档之外的破坏

同一个 `0.1.1-rc.2 → 0.1.2-alpha.3` 区间里恰好落进了两个互不相关的上游改动,各自独立地破坏了 `typecheck`/`test`,与 `dsh-client-runtime` 拆分无关;两者都是先在 `/workspace/deepseek-harness` 里用 pickaxe 确认之后才修的,不是盲改:

- **`@deepseek-ai/dsh-llm` 的 `CallId` 改名为 `ToolCallId`**(`a789637db6 refactor(llm): rename CallId to ToolCallId`,纯改名,语义不变)。两个测试文件手工构造 `SubagentStartRequest` 时用了旧名字:`packages/devflow-tool/tests/loader-composition.spec.ts` 与 `packages/devflow-fs-guard/tests/guard.spec.ts`。
- **`@deepseek-ai/dsh-client-ui-primitives` 的 `MarkdownText` 新增了必填的 `labels: MarkdownLabels` 属性**(`3c10f5d2d3 fix(client): route UI copy through locale`),取代了原先更窄的 `codeLabels` 属性。`packages/devflow-ui/src/client/board-view.tsx` 现在用一个本地的 `markdownLabels(t)` 辅助函数构造这组标签,对照的是 harness 自己的 `packages/client/ui-chat/src/client/markdown-labels.ts` 适配器:`t('copy')`、`t('copied')`、`t('markdown.footnotes')` 都通过本包自己按命名空间绑定的 `t` 解析,而它本就会回落到 harness 共享的 `common` locale 命名空间(`LocaleKeysOf<N> = (LocaleNamespaceMap[N] & string) | CommonKeyOf`)——不需要新增任何词典条目,`@deepseek-ai/dsh-client-locale` 的 `common` 词典里已经带有 `copy`、`copied`、`markdown.footnotes`。
- **`@deepseek-ai/dsh-subagent` 的 `SubagentCapabilities` 新增了必填的 `agentOptions: boolean` 字段**,其服务现在会拒绝一个未声明该能力的 provider 收到 `SubagentStartRequest.agentOptions`。`devflow-agent-gate` 的 checker 派发逻辑(`packages/devflow-agent-gate/src/index.ts`)过去无条件发送 `agentOptions`(部署方默认的模型/provider 路由);现在它按已有的工具过滤同样的方式加了门槛(`checkerAgentOptions`,对照既有的 `checkerToolFilter`):不具备该能力的 provider 会用它自己默认的 provider/model 派发,而不是让整次检查报错。`packages/devflow-agent-gate/tests/checker-provider.ts` 里的测试替身现在默认声明 `agentOptions: true`(和 `toolFilter` 一样可参数化),因为这个包里几乎每条既有 spec 都假定模型路由能传到 checker;`fail-closed.spec.ts` 与 `fault.spec.ts` 里两处内联的 provider 字面量声明 `agentOptions: false`,因为那两组故障注入 spec 从不断言这个字段。

`.trellis/spec/dsh-devflow-plugins/versioning.md` 的 Good/Wrong/Correct 示例此前把拆分描述成 `dsh-client-store` + `dsh-client-connection` + `dsh-client-modules` + `dsh-client-hmr` —— 那是 harness 那一侧完整的拆分,不是本仓库实际用到的依赖面。该文件的示例已在本次改动的同一次提交里更正,依据的正是它自己"Source of truth"一节的说明。

## Alternatives considered

**把依赖升级范围收窄到设计文档列出的那两个文件(`package.json`、`packages/devflow-ui/package.json`)。** 被否决:`AGENTS.md` 自己的"Harness version"规则以及本 PRD 的验收标准都要求工作区里每一个 `@deepseek-ai/*`/`cordis*` 钉住版本一起挪动,而 `pnpm` 按包解析依赖的方式意味着一个留在 `0.1.1-rc.2` 的包会在自己的构建里悄悄继续解析旧的 harness 表面而非新的 —— 这正是 `pnpm run preflight` 用来拒绝的那种"漂移"。

**让 `checkerAgentOptions` 保持"必须要求该能力,provider 不具备就报错"。** 被否决:既有的 `toolFilter` 能力早已把"不具备"当作"无限制派发,而非报错"处理,而一次 checker 报错会把卡片停在 `blocked` —— 相比派发到 provider 自己默认的 provider/model,代价大得多。

## Consequences

`pnpm run verify`(typecheck + lint + test)与 `pnpm run preflight:tarballs` 在新的钉住版本下都通过。dev 渠道发布(`<version>.dev.<sha>`)与 release 渠道发布是两个独立、仍待确认的步骤,依据的是版本管理规范 —— 本次改动只准备好钉住版本的依赖图与本仓库自身的版本号,不发布任何一个渠道。

`devflow-ui` 的 `src/client/index.ts` 所依赖的 `sessions`/`slots` 环境 `Context` 合并,现在通过显式的仅类型导入到达(`import type {} from '@deepseek-ai/dsh-client-ui-renderer/client'`,已有的 `dsh-client-locale/client`,以及经由 `dsh-client-ui-conversation/client` 间接得到的 `sessions`),而不再是靠一个恰好把三者都声明齐全的单一包。日后若某个 harness 包不再重新导出这些环境合并中的某一个,会在对应的 `ctx.<service>` 访问处直接表现为 `tsc` 报错 —— 与这次升级中 `Context.slots` 的回归表现完全一样。
