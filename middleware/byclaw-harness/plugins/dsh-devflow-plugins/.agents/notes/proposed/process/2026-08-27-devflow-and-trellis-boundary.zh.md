# Agent Note:devflow 与 Trellis 的边界在哪

Status: proposed

[English](2026-08-27-devflow-and-trellis-boundary.md) | 中文

> **这一条需要人来定。** 它是关于团队怎么工作的决定,不是代码行为;在维护者接受、修改或否决之前,状态保持 proposed。

## Problem

同一个工作区里有两套系统在给同一件事建模。

| Trellis(`.trellis/`) | devflow(本插件线) |
|---|---|
| Phase 1 Plan —— `prd.md` / `design.md` / `implement.md` | `draft` → `designing` → `ready` |
| Phase 2 Execute —— implement / check | `developing` → `reviewing` → `testing` |
| Phase 3 Finish —— spec 更新、提交 | `done`,随后 `archiveDone` |
| 父子任务树,一层,子任务可独立验证 | 父子卡,一层,子卡可独立验证 |
| `.trellis/tasks/<name>/` 加 jsonl 清单 | `.devflow/tasks/<seq>-<slug>/` 加 `journal.jsonl` |
| `task.py start` 以产物评审为实现的闸门 | 迁移波布上的门禁命令与审批 |

重合一直深到规则层:两者都把拆解限制在一层,都要求子项可独立验证,都让父项负责整合验收。这种收敛是"形状对了"的证据,不是浪费的证据。

浪费在别处。同时维护两套要花双份注意力,而且**两边的经验不互相积累** —— 在 Trellis 里学到的关于父子行为的教训,对 devflow 毫无帮助,反之亦然。更糟的是,今天的边界由习惯而非规则维持,于是一件工作落在哪套系统里,取决于是谁起的头。

**本仓库是最尖锐的例子。** devflow 是一套研发流程系统,而它自己的开发被记录在 Trellis 和 `.scratch/` 的 markdown 里,**没有一张 devflow 卡片**。那些只在使用中才会显形的缺陷 —— driver 走完一个阶段就停摆、门禁被默认超时杀死、从门禁内部调 `attachArtifact` 死锁 —— 根本没有浮现的机会,三者都是靠读代码发现的。

## Proposal

**选项 2:写下来的明确分工。** Trellis 拥有单个 agent 会话的内部;devflow 拥有跨越会话或跨越人的工作。

- **Trellis** 是一次会话的草稿纸与检查清单。它规划本次会话要做什么,持有规划产生的产物,并在这次会话的工作提交后关闭。它的单位是"某人现在正在做的一个任务"。
- **devflow** 是需求的公共记录。它为不在那次会话里的任何人回答"这件事到哪了",能挺过重启与交接,并承载部署所强制的门禁。它的单位是"一张比持有它的人活得更久的卡片"。

一件大到跨会话的工作,先开 devflow 卡;针对它的每次会话可以开一个 Trellis 任务再关掉,而卡片留下。

## Alternatives considered

另外两个选项,以及为什么它们不是推荐项:

- **选项 1 —— devflow 吸收 Trellis 的产物模型**(`designing` 在挂上三份产物之前到不了 `ready`;devflow 的门禁恰好能强制这一点)。造起来几乎免费,也很诱人。但它是一个比看上去更大的赌注:它让 devflow 成为唯一的系统,于是每一次会话 —— 包括一个五分钟的提问 —— 都要付卡片的开销。值得在选项 2 跑一段时间、边界被**观察**到而不是被**预测**之后再重新考虑。
- **选项 3 —— 退役其中一个。** 退役 devflow,是丢掉一条已发布、有测试的插件线。退役 Trellis,是丢掉本仓库当前赖以开发的工作流。"它们重合"不足以支撑其中任何一个。

**现状 —— 两套都留、边界靠习惯 —— 是三个选项里最差的那个**,因为它付出了维护两套系统的代价,却没有交付其中任何一套的清晰。

## Acceptance criteria

1. 把这条分工写进 `AGENTS.md` 与 `.trellis/workflow.md`,让规则活在各自系统的使用者会读到的地方。
2. 让本仓库的下一个需求采用 devflow —— 为工作开卡,起初不开 driver(卡片一动它就花模型预算),只用 `devflow_create`、`/devflow` 和看板。记录什么坏掉了。这正是本 note 的 Problem 段所描述的 dogfooding 缺口,也是这份提案里唯一一个能产出**证据**而非**共识**的部分。
3. 已有的 22 个 `.scratch/devflow/` issue 原地不动。迁移历史什么也换不来;规则只适用于新工作。

## Risks

一件起初很小、后来跨越会话的工作仍会让会话边界含糊;dogfooding 必须记录这些情形,而不是静默替它选择一套系统。在两套系统能互相链接记录之前,卡片状态与任务状态可能漂移。试用期间开启 driver 还会在每个已配置阶段花费模型预算,因此第一次采用时保持关闭。

如果提案被否决,选项 1 需要的新增设计工作最少。让边界无限期只靠习惯维持,会继续支付双份维护成本而不明确归属。

## Follow-up: 2026-08-27

产物契约的工作(`devflow-artifact-contract` 变更集)此后落地了选项 1 的产物模型——**以可选装备的形态,而不是本 note 请维护者裁决的那条规则。** 产物 kind 与 store 代写登记进了 seam,机械结构门禁与 LLM 准入门禁站上迁移 waterfall,driver 按 kind 喂入并索取交付物,[docs/devflow.zh.md](../../../../docs/devflow.zh.md#产物契约) 带有完整的部署样例和一条端到端组合证明。这一切都是按部署配置的:一个什么都不挂载的部署,卡片行为与从前完全一致,所以"每次会话都要付卡片开销"——上文选项 1 落选的理由——并没有发生。变化只在于:重新考虑选项 1 不再需要设计工作;采纳它如今是一个配置决定。本 note 提出的分工及其状态,仍由维护者定。
