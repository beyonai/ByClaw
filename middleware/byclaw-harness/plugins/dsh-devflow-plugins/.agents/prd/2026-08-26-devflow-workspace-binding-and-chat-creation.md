# PRD — devflow:工作区绑定、聊天建卡与 journal 沙箱加固

## Problem Statement

devflow 一期落地后,三个使用摩擦浮出水面:

1. **卡片不跟工作区走。** dsh 有明确的工作区概念(稳定 id + canonical 目录路径,会话按 header cwd 归属),但 devflow 的存储根是一个全局配置项,按 host 进程 cwd 解析。在工作区 A 的会话里打开看板,看到的可能是工作区 B(或启动目录)的卡;模型工具和 `/devflow` 命令同样只认这一个全局根。多项目并行时流程状态互相串台。
2. **建卡靠手写文件。** 创建一张卡要手工 `mkdir` + 写 `card.md` + 拼一行 journal JSON。和用户的真实工作流(在聊天里与模型讨论清楚需求)脱节:讨论完还得离开聊天去抄文件,格式抄错(rev、时间戳、actor)读取还会 fail-loud。
3. **写代码的 agent 能物理改写 journal。** 门禁配置在 profile 里 agent 碰不到,但 journal 文件本身在工作区内,拥有 workspace-write 的开发 agent 理论上可以绕开执行器(CAS、边合法性、门禁 waterfall)直接改历史。一期把这记为已知限制,现在要封掉。

## Solution

三件事,共用一个原则:**代码写在工作区里,`.devflow/` 就是该工作区的研发流程存储,随 git 走**。

1. **root 跟随调用方。** devflow 缝的每个操作获得显式的 root 维度(canonical 目录路径),"用哪个根"不再是全局配置而是按调用方解析:模型工具与 `/devflow` 命令从发起 agent 的会话 cwd 推导(`<cwd>/.devflow`);浏览器看板经 Remote 面传**工作区 id**,由 host 侧查工作区注册表解析成路径(浏览器绝不传裸路径);driver 扫描已注册工作区的根集合。配置里的 `root` 降级为"无法推导时的默认根",现有单根手动用法完全兼容。
2. **聊天建卡。** 缝新增 `create` 操作 + 模型工具 `devflow_create`:用户对模型说"把刚才讨论的方案建成研发卡",模型整理标题、需求正文与验收标准提交;provider 分配顺序 id、原子写入 journal 首条 `created`(唯一提交点)与 card.md 投影,并广播新事件让看板实时出现新卡。聊天讨论直接沉淀为任务书,手写文件路径继续有效。
3. **journal 沙箱只读。** 用既有的文件策略能力把 `.devflow/**` 从开发 agent 的可写集中剔除:代码随便写,流程状态只能经 devflow 工具走执行器(CAS、边合法性、reason 要求、门禁全部在那里)。强制执行发生在做决策的操作里,而不是靠"工具不提供"这种可绕开的表面约束。

## User Stories

1. 作为开发者,我想让看板只显示当前会话所属工作区的卡,以便多项目并行时流程状态互不串台。
2. 作为开发者,我想在切换会话时看板自动切换到对应工作区的卡,以便不需要任何手动过滤操作。
3. 作为开发者,我在未分组会话(没有注册工作区)里也想看到按会话 cwd 推导的卡,以便临时目录里的工作同样有流程可循。
4. 作为模型 agent,我想让 `devflow_list`/`devflow_take` 等工具自动作用于我所在会话的工作区,以便不需要用户告诉我根路径在哪。
5. 作为开发者,我想让 `/devflow` 的看板、移动、接管、归档都作用于当前会话的工作区,以便命令面与聊天面看到同一张板。
6. 作为开发者,我想在聊天里让模型把讨论结果建成一张任务卡,以便需求讨论直接沉淀为任务书而不用手抄文件。
7. 作为模型 agent,我想有一个 `devflow_create` 工具接收标题与 Markdown 正文,以便把用户口述的需求与验收标准落成合法的卡片文件。
8. 作为开发者,我想让新建卡的目录名自动分配顺序号加可读 slug,以便 id 稳定有序且不用自己查号。
9. 作为开发者,我想让两个 agent 并发建卡时序号分配不冲突,以便团队同时开卡不会互相覆盖。
10. 作为开发者,我想让建卡即刻出现在右上角看板里,以便确认模型真的建对了。
11. 作为开发者,我想让建卡记录进会话日志,以便回放会话时能看到这张卡是谁在哪次对话里建的。
12. 作为审计者,我想让新卡的 journal 首条就带创建者 actor 签名,以便审计链从第一秒开始完整。
13. 作为开发者,我仍想保留手写 card.md + journal 建卡的能力,以便脚本化批量建卡或离线操作。
14. 作为团队成员,我想让卡片和代码在同一个 git 仓库里流转,以便 clone 即得看板、PR 可以同时携带代码与卡片状态。
15. 作为安全边界的维护者,我想让拥有 workspace-write 的开发 agent 无法直接写 `.devflow/**`,以便 journal 历史不可被绕过执行器篡改。
16. 作为开发者,我想让 devflow 工具在沙箱只读策略下依然能正常流转卡片,以便加固不牺牲任何正常功能。
17. 作为 driver 运维者,我想让阶段驱动器按工作区根集合派发,以便自动化不会把 A 工作区的卡派给 B 工作区的上下文。
18. 作为门禁维护者,我想让门禁命令在卡片所属工作区目录里执行,以便 `pnpm run test` 测的是这张卡的代码。
19. 作为开发者,我想让归档、租约、投影重写全部按卡片所属根进行,以便多工作区下所有既有语义不变。
20. 作为浏览器用户,我不想让前端有任何能力传裸文件路径给 host,以便 Remote 面不成为任意路径读取的口子。
21. 作为开发者,我想在配置了全局默认根的老用法下一切照旧,以便升级不破坏现有部署。
22. 作为模型 agent,我想在建卡请求非法(标题空、slug 非法、目录已存在)时得到稳定错误码,以便向用户解释并重试。
23. 作为开发者,我想让看板在收到"新卡创建"事件时和"阶段变化"一样自动刷新,以便展示面永远是实时的。

## Implementation Decisions

- **root 是缝上的显式维度,不是卡片字段。** 卡片归属即其所在目录;`DevflowStore` 的操作携带 canonical root(进入既有的 request/spec 显式 defaulting 步骤),读侧 `DevCard` 增加只读 root,使 gates/driver 从事件携带的卡片就能跟对目录。每卡串行锁的 key 从卡 id 变为 root+id。配置项 `root` 保留为默认根(调用方无法推导时使用),现有部署零迁移。
- **workspace→root 的映射放在消费方,不进 Definition。** devflow 缝只认目录;模型工具与命令从发起 agent 的会话 cwd 推导;Remote 面新增 workspace id 参数,由 host 侧 BFF 查工作区注册表(canonical path)解析——浏览器永不发送文件路径,这是安全边界。工作区注册表是既有服务,devflow 不新增对它的 Definition 依赖。
- **缝新增 `create` 操作。** 请求为标题、Markdown 正文、可选 slug、actor;结果沿用既有的领域结果姿势(稳定错误码解析 `ok: false`,基础设施故障才 reject)。id 分配为"现有最大序号 + 1 + slug",目录以独占创建保证并发安全,撞号重试;journal 首条 `created`(带 actor)是唯一提交点,card.md 是投影——与既有写路径姿势完全一致。
- **新增 `devflow/card-created` 事件**(单播通知),进 Remote 转发白名单;创建不是 transition,不复用 stage-changed、不过门禁 waterfall(draft 卡无害,治理从第一次流转开始)。
- **`devflow_create` 工具**要求归属 agent 会话,提交后记会话日志事件(model-visible ⟺ logged);`/devflow` 不加 new 子命令(单行输入不适合长正文),手写文件路径继续有效。
- **看板会话联动。** 看板 slot 本就是会话作用域;客户端由当前会话解析其工作区 id 后调 Remote;未分组会话按会话 cwd 走 host 侧的同一条解析路径(以会话 id 换 cwd,仍不传裸路径)。
- **journal 沙箱只读**用既有文件策略能力实现:对开发 agent 的写权限集合剔除 `.devflow/**`;devflow 工具的变更全部发生在 host 侧 store(不经过 agent 的文件工具),因此执行器保持唯一写路径。策略作为部署配置交付(与门禁配置同处 profile),不硬编码在插件里。
- **存储决策(定稿):`.devflow/` 留在工作区目录内,随 git 走。** 卡片与归档建议提交;`claim.json` 为进程性临时态,建议 gitignore(文档化建议,不强制)。跨工作区聚合视图不做,`DevflowCardId` 唯一域为 per-root。

## Testing Decisions

- **只测外部行为**:provider 全部经 `DevflowStore` 公开面测(建卡后 list/read 可见、journal 可回放、并发建卡序号不冲突),不断言内部结构;错误路径断言稳定错误码而非异常文本细节。
- **工具走 real-Loader composition**(先例:devflow 工具包现有的组合测试):真实 Loader 挂真实文件 store,经工具执行器建卡并断言磁盘产物与会话日志事件。
- **Remote 面走 gateway 双端往返**(先例:gateway 客户端/主机测试与本轮的往返复现):workspace id 解析、非法 id 拒绝、card-created 转发。
- **看板走真实浏览器 e2e,双工作区场景从第一天就有**(先例:本轮建立的看板 e2e 台子):两个工作区各一张卡,两个会话切换,断言面板只显示所属工作区的卡、聊天建卡后新行实时出现。一期的教训(组件测试全绿、真实链路四个集成洞)证明这条测试缝必须与功能同 PR。
- **沙箱加固经执行器面验证拒绝**(先例:文件策略与沙箱现有测试):策略生效时 agent 的文件写工具对 `.devflow/**` 被拒,而 devflow 工具的同一流转成功——"拒绝要测在做决策的执行器上"。
- **组件层**沿用 jsdom 套件补面板增量,保持逐文件覆盖率门禁。

## Out of Scope

- 跨工作区聚合看板与 `(workspace, id)` 复合地址;
- 聊天改卡/删卡(create 之外的卡内容编辑仍是人的编辑器操作);
- 面板富视图(门禁执行状态、变更统计、分支名)与面板内审批行(沿用一期决策:审批走既有审批 composer);
- goal/Ralph 执行体、GitHub Issues/SQLite provider(一期已推迟,维持);
- 工作区删除/移动时的卡片迁移工具(目录随仓库走,git 即迁移)。

## Further Notes

- 切片建议:**008 聊天建卡**(缝 create + 工具 + 事件 + 看板刷新,独立先行)→ **009 root 按调用方解析**(provider 多根化 + 工具/命令 cwd 推导)→ **010 看板工作区过滤**(Remote workspace 解析 + 会话联动 + 双工作区 e2e)→ **011 journal 沙箱只读**(策略配置 + 执行器面拒绝测试)。008 与 009 无依赖可并行,010 依赖 009,011 独立。
