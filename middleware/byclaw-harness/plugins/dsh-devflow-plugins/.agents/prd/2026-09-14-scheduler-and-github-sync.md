# PRD：通用定时器与 GitHub 内容同步插件

状态：用户已通过 `$implement` 授权在独立 worktree 实现；远端发布位置仍待确定。本文保留原需求与可观察契约，当前实施和验收范围见 [验证记录](2026-09-14-scheduler-github-sync-validation.md)。

## Problem Statement

项目维护者需要持续发现 GitHub 上新增和变化的 Issue 与讨论，为后续问题评估、需求承接、摘要和知识整理提供可靠输入。人工定期查看成本高；把定时、同步、模型评估和自动开发写进一个插件，会使其他数据源与消费者难以复用，也难以判断失败发生在哪个环节。

现有会话级提醒依赖存活的根 agent，不能承担不依赖活跃聊天的仓库扫描。仅用内存事件通知消费者，还会在插件停用、进程重启或处理失败时丢失后续工作。

维护者需要两个可独立使用、可组合的插件：通用定时器负责何时触发；GitHub 同步插件负责获取和保存远端内容及变化。其他插件自行决定是否评估、建卡或开发。

## Solution

提供宿主级持久化定时器，以及可按仓库订阅的 GitHub 内容同步插件。宿主运行时，即使没有活跃聊天会话，也能按计划同步；宿主停止时不承诺执行，重启后按补触发策略恢复。

用户可从对话入口管理计划和订阅，手动同步，查看当前运行、进度、错误及结果，暂停后续扫描或取消当前运行。同步产生可查询的内容快照和持久化变更记录。消费者按各自游标处理变化，事件通知仅用于降低处理延迟。

首版支持固定间隔和带明确时区的 Cron；同步对象覆盖 Issue、Issue 评论，以及可选启用的 GitHub Discussions、评论和回复。保留对象类型与关联关系，不把 Discussions 强行转换成 Issue。

成功标准是：用户配置一个仓库后，定时同步能够在无活跃聊天时运行；独立消费者能够读取变化、确认处理并在重启后续读；用户能区分已触发、已接收、同步中、部分失败和已完成。本 PRD 不交付自动开发闭环。

## User Stories

1. As a 项目维护者, I want 从对话中创建定时计划, so that 我不必手工编写调度文件。
2. As a 项目维护者, I want 设置固定间隔, so that 系统能持续同步仓库。
3. As a 项目维护者, I want 设置 Cron 和明确时区, so that 扫描时间符合工作安排。
4. As a 项目维护者, I want 查看下一次触发时间, so that 我能确认计划配置正确。
5. As a 项目维护者, I want 暂停和恢复计划, so that 我能控制后续扫描。
6. As a 项目维护者, I want 手动触发计划, so that 我能立即验证或刷新内容。
7. As a 项目维护者, I want 宿主在没有活跃聊天时执行计划, so that 扫描不依赖人工保持会话。
8. As a 项目维护者, I want 重启后保留计划和触发记录, so that 服务中断不会清空配置。
9. As a 项目维护者, I want 明确错过多个周期后的补触发行为, so that 恢复服务时不会突然积压大量任务。
10. As a 项目维护者, I want 同一计划避免重叠执行, so that 长同步不会重复消耗资源。
11. As a 插件开发者, I want 注册通用触发处理器, so that 定时器能服务 GitHub 之外的任务。
12. As a 插件开发者, I want 获得稳定的触发标识, so that 重复投递可以安全去重。
13. As a 运维人员, I want 区分投递失败和下游运行失败, so that 我能定位故障归属。
14. As a 项目维护者, I want 配置仓库和凭证引用, so that 同步能访问获准读取的内容。
15. As a 项目维护者, I want 选择同步的内容类型, so that 我能控制同步范围。
16. As a 项目维护者, I want 同步 Issue 及评论, so that 下游能理解问题和补充信息。
17. As a 项目维护者, I want 按需同步 Discussions 及回复, so that 产品讨论和知识问答也能供下游使用。
18. As a 项目维护者, I want 首次同步覆盖所选范围, so that 下游能获得可靠的初始数据。
19. As a 项目维护者, I want 后续只处理变化并定期对账, so that 同步兼顾成本与完整性。
20. As a 项目维护者, I want 关闭、重新打开和编辑等变化被记录, so that 下游不会长期依赖过时内容。
21. As a 项目维护者, I want 同步结果排除被 Issues 接口返回的 PR 条目, so that 候选内容类型正确。
22. As a 项目维护者, I want 手动调用同步而无需启用定时器, so that 同步插件能够独立使用。
23. As a 项目维护者, I want 看到分页进度、数量、限流等待和最后成功时间, so that 我能判断运行是否健康。
24. As a 项目维护者, I want 取消当前同步并保留已提交结果, so that 我能停止资源消耗且不破坏已有数据。
25. As a 项目维护者, I want 暂停订阅与取消运行具有不同含义, so that 我能精确控制后台工作。
26. As a 插件开发者, I want 查询带来源、类型、版本和父子关系的内容, so that 我能建立可靠的后续处理。
27. As a 插件开发者, I want 独立读取和确认变更游标, so that 一个消费者不会影响其他消费者。
28. As a 插件开发者, I want 重启后读取尚未处理的变化, so that 内存通知丢失不会造成遗漏。
29. As a 插件开发者, I want 为新消费者选择从头回放或从当前位置开始, so that 不同用途能控制历史处理量。
30. As a 插件开发者, I want 消费失败后能重新读取同一批记录, so that 我能重试而不丢失输入。
31. As a 运维人员, I want 多个实例不能同时提交同一任务的冲突结果, so that 故障恢复与扩容不会破坏状态。
32. As a 项目维护者, I want 认证失败和来源不可访问被明确展示, so that 系统不会把权限变化误判为内容删除。
33. As a 项目维护者, I want 凭证不出现在日志和内容快照中, so that 排障与内容消费不会泄露凭证。
34. As a 项目维护者, I want 外部讨论仅被当作数据, so that 评论中的指令不会改变执行权限或触发开发。
35. As a 项目维护者, I want 同步插件不会自动评论、关闭 Issue 或创建开发任务, so that 后续动作由独立策略负责。
36. As a 插件开发者, I want 获得最小消费者示例和接入说明, so that 后续评估、摘要和 Devflow 接入无需修改同步插件。

## Implementation Decisions

- **交付边界**：交付两个逻辑插件及其公开服务、管理入口、持久化实现与必要展示。服务定义、提供者和消费者遵循现有插件组合规范；物理包数量服从仓库规范，不以“两个插件”限制必要的定义包拆分。
- **执行归属**：定时器管理计划和投递，不执行 Devflow 阶段；同步插件管理 GitHub 内容与同步运行，不进行模型评估。后续开发继续由 Harness agent 和现有 Devflow gates 负责。
- **依赖约束**：仅使用已发布的 Harness 接口，跨插件通过服务协作。当前固定依赖的兼容性必须在真实组合中验证；不得把本地 Harness 未发布接口当作可用依赖。
- **定时器接口**：提供计划创建、查询、更新、暂停、恢复、删除及手动触发；提供处理器注册与释放。计划包含处理器标识、经过校验的参数、时间规则、重试上限、超时及补触发策略。处理器缺失时显式等待或报错，不静默丢弃触发。
- **时间规则**：固定间隔按原定时间锚点计算；Cron 使用五字段表达式和 IANA 时区。夏令时不存在的当地时间跳过，重复当地时间只触发一次。时间参数不合法时拒绝保存，并提供可查询的下次触发时间。
- **离线恢复**：默认合并为最近一次到期触发，可配置跳过；首版不回放所有错过周期。宿主启动时重建待处理工作，宿主不运行期间不承诺准时执行。
- **并发规则**：同一计划默认不重叠，忙时合并为一个待触发请求；同一同步订阅也需串行化，以覆盖手动触发与不同计划同时命中。允许不同订阅在配置的全局限额内并发。
- **投递语义**：先持久化触发意图，再投递处理器。周期触发保持稳定标识，重试复用标识；独立手动触发产生新标识。至少一次投递依赖处理器持久化幂等处理，不承诺跨系统 exactly-once。
- **接收与完成**：处理器仅在接收记录持久化后返回已接收及下游运行引用。定时器不将已接收显示为同步完成；同步插件独立保存进度和完成结果。已接收后的运行重试归同步插件负责，避免双层重试制造新工作。
- **暂停与取消**：暂停和删除计划阻止未来投递，不隐式删除已接收运行；暂停订阅阻止新同步。取消当前运行传播取消信号并保存最终状态。取消后迟到的结果不得继续以原执行身份提交。
- **同步对象**：保留稳定来源 ID、仓库身份、对象类型、父子关联、远端 URL、可用的远端更新时间、本地版本、抓取时间及内容指纹。Issue 与 Discussion 分别建模；Issue 评论和 Discussion 回复保留上下文。PR 不是首版同步对象。
- **同步范围**：按仓库与内容类型订阅；首次覆盖所选范围的可读取内容，分页和资源预算限制每次运行量但不得静默截断。未完成初始同步时明确标记未完成。修改范围后重建对应基线，不能错误沿用不兼容游标。
- **增量与对账**：依据各 GitHub 资源实际支持的接口执行分页、增量或对账，不假设所有对象都有统一更新时间过滤器。使用重叠窗口和内容指纹去重，定期校验评论、回复及其他增量可能遗漏的变化。
- **不可用与删除**：只有明确的远端证据或完整且有权访问的对账才能认定删除；权限失败、404 歧义和分页中断记录为不可访问或未知。Discussions 未启用或无权限时明确记录该内容类型不可用，不影响已正确完成的其他内容类型，也不得宣称整体全部成功。
- **持久化提交**：内容快照与对应变更记录必须逻辑原子提交，可采用事务或可恢复日志；同步检查点只能推进到已持久化数据。部分提交结果可见，但运行保留部分完成或失败状态。重新获取同一内容不得生成无意义的新版本。
- **变更记录**：提供稳定记录 ID、有序游标、来源对象、变更类型及对应内容版本。消费者能读取该版本的快照，而非只拿到已经更新后的最新对象。内存事件在持久化提交后发送，仅用于唤醒消费者。
- **消费协议**：按消费者与订阅保存独立确认位置，支持分页读取、显式确认、失败重读和显式回放。只允许确认已交付的连续记录，不能跳过未处理项。消费者需以记录 ID 实现自身副作用幂等，处理成功但确认失败时可能重复收到记录。
- **保留策略**：首版不自动清理变更历史和相应版本，避免破坏离线消费与回放；暴露存储占用并允许配置容量上限。达到上限时暂停新增同步并报错，不静默丢历史。自动压缩和过期游标迁移不在首版范围。
- **多实例与恢复**：使用持久化互斥和执行代次防止冲突提交；持有权过期后旧实例不可提交。处理触发已保存未投递、接收成功回执丢失、分页提交中断、通知丢失和取消后迟到结果。
- **凭证与输入**：配置使用凭证引用；日志、快照及消费者输出不含凭证。外部内容以不可信数据提供，不执行其中的命令、不修改项目权限。同步只需要远端读取能力。
- **管理与可见性**：从现有对话命令或工具入口管理计划、订阅和运行，变更可追溯到真实调用者。提供运行详情与可恢复状态，显示触发时间、接收时间、进度、计数、重试、等待原因和错误。适用时复用已有任务输出机制，但不依赖活跃 agent 才能继续同步。
- **下游接入**：提供不含业务决策的最小消费者示例，用于证明独立消费和恢复。评估结论、Issue 到卡片映射、建卡与启动记录由未来下游插件维护。同步内容变化本身不授权开发。

## Testing Decisions

- **主要验收入口**：通过真实 Loader 加载定时器、GitHub 同步插件、真实持久化提供者及最小测试消费者，使用公开管理和查询接口驱动。仅替代外部 GitHub 服务和时间推进；不模拟内部插件协作以伪造组合成功。该验收边界待用户确认。
- **测试原则**：验证用户可见状态、持久化输出和消费者实际收到的内容，不断言内部函数调用顺序。纯时间算法可补充必要的定向测试，不能用单元覆盖率替代运行验收。
- **既有先例**：复用 Devflow Web 测试真实启动 Loader、文件存储与 HTTP 服务后观察结果的方式；参考 Harness Schedule 的持久化重启测试及插件释放测试，但不继承其会话存活限制。
- **正常闭环**：无活跃聊天时创建间隔计划，触发首次同步，读取内容与变化，消费者确认游标；再次同步未变化内容不产生重复变更；远端编辑后产生可读取的新版本。
- **时间与生命周期**：覆盖间隔锚点、Cron 时区、夏令时、时钟变化、离线补触发、暂停恢复、删除、处理器缺失与卸载后无新投递。用确定性时间推进，避免依赖长时间 sleep。
- **内容完整性**：覆盖多页 Issue、评论、Discussion 及回复，排除 PR，验证关闭与重新打开、编辑、明确删除、权限变化、部分类型不可用和范围变更。部分页失败不得推进到尚未提交位置。
- **GitHub 故障**：覆盖限流、认证失效、网络超时和服务错误，验证等待、重试上限、取消及明确错误，不把失败当作空结果或成功。
- **崩溃注入**：分别在触发持久化后、下游接收后回执前、快照与变更提交期间、检查点推进前、通知前和消费者处理后确认前中断并重启。恢复后无内容遗漏、无额外同步运行、无指向缺失快照的变更；允许符合契约的重复消费。
- **并发与取消**：两个实例竞争同一计划，同一订阅被定时和人工同时触发，旧持有者恢复，取消后旧请求返回；验证唯一承接、串行同步与过期结果拒绝。
- **消费者隔离**：两个消费者独立读取，一方失败或离线不影响另一方；恢复后读取未确认记录，显式回放可访问对应历史版本，通知丢失仍可通过记录续读。
- **安全与可见性**：恶意评论不得改变操作权限或执行命令；凭证不出现在输出；已接收、同步中、部分完成和成功状态准确，容量耗尽可见且无静默历史删除。
- **发布验收**：执行仓库要求的类型检查、lint、测试、构建及打包检查；使用固定已发布 Harness 依赖完成真实 profile 安装、启动和管理入口验收。构建成功与真实 profile 验收分别记录。
- **退出条件**：两个插件可独立加载、组合闭环通过、上述恢复与消费场景通过、管理入口可操作、接入说明齐全，才判定本 PRD 完成。不以创建了计划或收到 HTTP 成功响应代替同步和消费完成。

## Out of Scope

- 判断 Issue 的解决价值、代码可解性、优先级和开发成本。
- 模型评估、自动创建 Devflow 卡片、启动开发 agent、推进开发阶段及绕过 gates。
- 创建 PR、推送代码、评论或关闭 Issue、修改标签等 GitHub 写操作。
- GitHub PR 内容同步及其他托管平台适配。
- webhook 接入；同步入口保留独立调用能力，不在首版交付 webhook。
- 任意 shell 或用户脚本定时执行、通用 DAG、工作流引擎和跨机器执行集群。
- 宿主关闭期间准时执行，或外部邮件、短信和推送通知。
- 完整重做 Devflow 看板，以及自动清理历史和存储压缩。
- 自动配置仓库级技能体系或修改现有项目开发规范。

## Further Notes

- “定时器”是宿主级计划服务；“触发”是一次到期投递；“同步运行”是同步插件接收后执行的工作；“变更记录”是持久化数据；“消费者确认位置”表示该消费者已完成的连续处理范围。这些状态不能互相冒充。
- GitHub 同步可以被人工或其他可信插件直接调用，不能强依赖定时器。定时器不依赖 GitHub 或 Devflow 核心服务。
- 本文中固定间隔与 Cron、完整讨论类型、补触发默认值和保留策略是为形成可实施范围而明确的首版提案；发布前可在本草稿调整。
- 实施宜按通用定时器、独立同步、持久化消费与组合验收三个可验证交付推进；本 PRD 作为总需求，对应 S1–S9 拆分与后续 worktree 实施。
- 发布建议为当前仓库 GitHub Issues，标签为 ready-for-agent。该标签当前不存在；发布位置、标签创建和主要验收入口确认后再发布。ready-for-agent 表示需求可供实现；实际本地实施由后续 `$implement` 请求授权，验收状态以验证记录为准。
