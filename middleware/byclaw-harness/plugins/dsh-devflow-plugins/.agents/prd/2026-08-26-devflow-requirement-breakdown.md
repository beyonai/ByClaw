# PRD — devflow:大需求拆分与父子卡片

## Problem Statement

devflow 今天的卡片模型是完全扁平的:卡片就是 root 下的一个 `NNN-slug` 目录,id 由全局递增序号分配且永不复用,`DevCard` 上没有任何指向其他卡片的字段,四种 journal 条目(`created` / `transition` / `artifact` / `claim-expired`)也没有一种能表达卡片间的关系,而承载需求内容的 `card.md` 正文创建后不可改。

于是一个"大需求"进来时只有两条路,两条都会坏:

1. **塞进一张卡。** driver 的粒度是一卡一租约一 revision,大需求因此无法并行推进,而被派发的子代理拿到的 objective 是整份需求;阶段语义也对不上——大需求的"开发完成"不是它自己的状态,而是子项的函数。
2. **手动开 N 张互不相干的卡。** 这在今天可行(连续建卡时 id 天然相邻,每张 body 自带背景),但看板是扁平列表,20 张同源卡片就是噪音,没有任何位置回答"这个大需求做到 3/8 了";`archiveDone` 按每张卡最后一条 journal 条目的月份分桶,还会把同一个大需求的卡片拆散到不同月份目录里,事后无法整体找回。

缺的不是新状态机,而是**卡片之间的一条"组成"边**,以及围绕这条边的三件事:大需求何时算完成、大需求不该被当成一次可执行派发、大需求在看板上怎么呈现。

## Solution

父需求就是一张普通卡,子需求在创建时固定一条指向它的 `parent` 边挂上去。关系是数据,不是 id 结构,也不是第二套状态机。四件事:

1. **缝增加一个关系维度。** `create` 收可选 `parent`,写进 journal 的 `created` 条目(因此不可变、可回放),投影到 `card.md` frontmatter,读回到 `DevCard.parent`;`CardFilter` 支持按 `parent` 取一张父卡的全部子卡。
2. **完成语义靠既有的 `devflow/transition` 瀑布。** 子卡未全部 `done` 时,父卡 `-> done` 被一个策略监听器否决,理由点名还差哪几张。门禁卡在 `-> done` 而不是更早的边,因为父卡自己的 `reviewing` / `testing` 正是"整体联调与整体验收"该发生的地方。
3. **driver 跳过有子卡的卡。** 大需求永远不会被当成一次 stage 派发交给子代理;子卡照常被驱动。
4. **看板与详情做层级呈现。** 父行显示 `k/n` 子进度与受阻标记、可折叠展开子行,父卡详情列子卡清单并可钻取,子卡详情回链父卡——全部由客户端从已取回的卡片列表派生,不新增任何 Remote 面。

只允许一层:父卡不能再有父卡。父子是**组成**关系,不是依赖关系——`blocks` / `depends-on` 与自动排程沿用根 PRD 的 out of scope。

## User Stories

1. 作为开发者,我想在聊天里把一个大需求拆成一张父卡加若干子卡,以便每个子项能被独立认领、独立推进、并行开工。
2. 作为开发者,我想让父卡正文承载整体背景与整体验收标准,以便每张子卡不必各自复制一遍上下文。
3. 作为子代理,我想在子卡上看到父卡的 id 与标题并能读到父卡正文,以便我只拿到子需求时仍能理解全局意图。
4. 作为审计者,我想让父子关系在创建时固定并写进 journal,以便关系与卡片内容一样可回放、可审计,而不是一个能被随手改掉的 frontmatter 字段。
5. 作为开发者,我想让挂到不存在的父卡、挂到本身已有父卡的卡(二层)、挂到已完成或已归档的父卡,都被稳定拒绝并给出明确理由。
6. 作为开发者,我想让父卡在子卡未全部完成时无法进入 `done`,且理由点名还差哪几张卡,以便"大需求完成"永远意味着子项全部完成。
7. 作为开发者,我想让父卡仍然照常走完自己的 `reviewing` / `testing`,以便整体联调与整体验收有明确的落点,而不是子卡一做完就自动收尾。
8. 作为开发者,我不想让 driver 把父卡当成一次可执行的工作派给子代理,以免一个子代理去啃整份大需求。
9. 作为模型,我想按父卡列出它的全部子卡及其阶段,以便汇报进度或挑出下一张该做的卡。
10. 作为开发者,我想在看板父行上看到 `k/n` 的子进度,以便一眼知道这个大需求做到哪了。
11. 作为开发者,我想折叠或展开父行下的子卡,以便一个大需求不会把看板刷屏。
12. 作为开发者,我想在父行上看到"子卡中存在受阻或被打回"的标记,以便先去处理真正卡住的地方。
13. 作为开发者,我想在父卡详情里看到子卡清单并点进任意子卡,也想在子卡详情里点回父卡,以便上下钻取顺畅。
14. 作为开发者,我想让同一个大需求的父卡与子卡一起归档进同一个月份桶,以便事后能把这段历史整体找回。
15. 作为命令面用户,我想在 `/devflow` 与 `/devflow show` 里看到父子关系,以便不开 Web 也能读到拆分结构。
16. 作为存量用户,我想让不带父子关系的老卡片与老 journal 继续照常工作,顶层卡就是没有父卡的卡。

## Implementation Decisions

- **关系是数据,不是 id 结构。** 明确拒绝 `007.1-xxx` 式的层级 id:它会同时破坏全局 `nextSequence` 分配器、branded id 的不透明性,以及"id 即目录名且永不改变"的不变量,收益仅仅是目录列表好看。
- **父子边写进 `created` 条目,因而不可变。** `JournalCreated` 增加可选 `parent`,`decodeJournalEntry` 在耐久边界校验它,`foldJournal` 折出 `DevCard.parent`;`card.md` frontmatter 的 `parent:` 与 `title` 一样只是可读投影,权威永远是 journal。不提供改挂——`relinked` 条目类型没有当前消费者。
- **只允许一层。** 创建时若指定的父卡自身带 `parent`,拒绝 `nested-parent`;一层同时消灭了环路检测与递归 rollup 两处复杂度。
- **父卡与子卡必须同 root。** 父卡在调用方解析出的同一个 root 里查找,查不到即 `unknown-parent`;跨工作区的父子关系不存在。
- **三个新的创建拒绝码**:`unknown-parent`、`nested-parent`、`parent-settled`(父卡已 `done` 或已归档,不再接受新子需求),沿用既有约定——领域拒绝 `ok: false` 加稳定码,只有基础设施失败才 reject。
- **完成门禁只卡 `-> done` 这一条边**,由一个新的策略插件挂在既有 `devflow/transition` 瀑布上实现:不进 store、不加状态机、不动阶段联合类型。否决理由点名未完成子卡的 id 与其当前阶段。
- **策略插件独立成包。** 它的角色是"父卡完成门禁",与 `dsh-devflow-gates` 的"边上命令门禁"是两件不同的事,不塞进后者;与其余 devflow 插件一样由用户 profile 组合。未组合时父子关系照常可用,只是没有完成门禁——这是可接受的降级。
- **driver 跳过有子卡的卡。** 派发前按 `list({ parent: card.id }, card.root)` 判断,有子卡则记一条调试日志并跳过。这条规则不依赖门禁插件是否被组合,也不依赖部署把哪些阶段配成被驱动阶段。
- **上下文继承靠读,不靠复制。** `devflow_show` 在子卡上回父卡的 id 与标题、在父卡上回子卡摘要(id / 标题 / 阶段);子代理需要全局背景时自己 `devflow_show` 父卡。driver 的子提示词不变,不把父卡正文塞进每次派发。
- **不引入批量 `devflow_split` 工具。** N 次 `devflow_create({ parent })` 已经足够,批量原子性没有当前消费者,部分失败可以续建。
- **归档以"族"为单位。** `archiveDone` 不再单独归档"父卡尚未完成"的 done 子卡;父卡 done 时,父卡与其全部子卡一起归入父卡最后一条 journal 条目所在的月份桶。没有父子关系的卡行为完全不变。
- **看板与详情零新增 Remote 面。** `list` 已经返回整个 root 的 `DevCard[]`,`parent` 字段随之抵达前端;分组、`k/n`、受阻标记、子卡清单、父卡反链全部客户端派生,与上一份 PRD 的"派生指标不进缝"同一条路线。
- **胶囊计数口径不变**,仍是活跃卡总数,父卡照常计入;层级只影响列表呈现。
- **父卡与子卡都是普通卡**:都能被认领、被 `/devflow move`、被受阻打回、被登记产物。除了 `-> done` 的门禁与 driver 跳过,没有第二套规则。
- **大需求的完成判据只有一个**:全部子卡 `done`,加上父卡自己走完流水线。不引入独立的 epic 验收清单或可勾选项;父卡正文里的整体验收标准是给人和模型读的,不是机器判据(与"详情严格只读"一致)。
- **老数据照常。** 不带 `parent` 的 journal 与 frontmatter 继续解析,`DevCard.parent` 缺省即顶层卡;不需要任何迁移。

## Testing Decisions

- **缝**:带 `parent` 创建后的 journal 回放与 `DevCard.parent`、三个拒绝码各自的路径、`CardFilter.parent` 的取子集、多根下的父卡查找(同 id 不同 root 不串)、不含 `parent` 的老 journal 照常回放。
- **门禁插件**:按 `dsh-devflow-fs-guard` 的姿势做真实 Loader 组合测——子卡未全 done 时父卡 `-> done` 被否决且理由点名、全 done 后放行、无子卡的卡不受影响、fiber 处置后监听器摘除(HMR 安全)。
- **driver**:有子卡的卡进入被驱动阶段不派发,子卡照常派发,跳过不影响队列与并发上限。
- **归档**:父卡未 done 时其 done 子卡留在活跃集;父卡 done 后整族进入同一月份桶;无父子关系的归档行为不回归。
- **工具与命令**:`devflow_create({ parent })`、`devflow_show` 的父/子摘要、`devflow_list` 的 `parent` 字段与过滤;`/devflow` 与 `/devflow show` 的层级呈现。
- **组件层 jsdom**:父行 `k/n` 与受阻标记、折叠展开、父卡详情的子卡清单与钻取、子卡详情的父卡反链、孤儿子卡(父卡已归档)降级为平铺渲染。
- **真实浏览器 e2e**(沿用既有双工作区台子):播一个父卡加两张子卡,断言层级与 `k/n`;`/devflow move` 把最后一张子卡推到 `done` 后,父行进度实时更新;tripwire 无错误。
- 逐文件覆盖率、双语 README 与 JSDoc、cordis/tool/config catalog 门禁与 Agent Note 随各切片,遵循仓库既有门禁。

## Out of Scope

- 卡片间的依赖关系(`blocks` / `depends-on`)与自动排程——沿用根 PRD 的 out of scope,本 PRD 只做"组成"关系;
- 两层以上的层级、改挂父卡(`relinked`)、跨工作区的父子关系;
- 父卡的自动流转:子卡全部完成不会自动把父卡推进,门禁只否决,不代替人或模型做移动;
- 大需求的自动拆分(模型自行生成并批量创建子卡清单)——拆分仍是聊天里商定后逐张建卡;
- 甘特图、燃尽图与跨大需求的聚合统计视图;
- 归档卡的层级浏览(`list` 不含归档卡,入口不存在)。
