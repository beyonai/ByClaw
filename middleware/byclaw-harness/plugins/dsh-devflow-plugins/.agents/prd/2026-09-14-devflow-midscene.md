# PRD — Devflow Midscene 两阶段集成

## Problem Statement

开发者通过 Devflow 管理需求、实现、审查和验收，但一张卡片进入 testing 后，仍需手动操作浏览器、判断页面表现、整理截图和报告。命令退出、UI 动作完成、视觉断言通过和卡片允许完成缺少统一的证据关联，容易出现“工具返回成功，但用户路径没有验收”的结果。

已有社区插件能调用 Midscene 操作 Web 或 Android，但它针对早期 Harness，且没有将卡片、运行、结果、取消、产物和门禁串联起来。开发者不能可靠地知道当前操作属于哪张卡、取消是否生效、看到的报告是否对应当前代码，也无法在失败后完整回看。

本需求要让开发者从对话发起可重复的 Web 验收，看到真实进度和报告，并在需要探索页面时使用同一套证据与生命周期约定下的原生工具。

## Solution

分两阶段交付，两阶段均属于本 PRD 的承诺范围，阶段二必须在阶段一通过验收后开始。

### 阶段一：可见、可重复的 Web 自动化验收

用户在对话中要求验收某张卡片。Harness agent 读取验收标准，使用项目的环境启动手册，运行 Playwright + Midscene 用例。用户能看到当前用例、步骤摘要、输出和取消入口，完成后能打开独立 HTML 报告，并在卡片上读取测试摘要。Devflow 仍通过既有门禁决定阶段是否允许推进。

首个交付不是一次性演示：提供可复用的验收技能、用例示例、结果汇总与报告交付约定，并用 Devflow 自身的列表、详情和产物导航作为试点。实际页面缺少某个预期入口时应明确失败或修正试点用例，不能伪造通过结果。

### 阶段二：原生 Web 操作工具

用户继续从对话发起打开页面、点击、输入、查询、等待和断言。工具明确当前目标，提供结构化结果、进度与取消，沿用阶段一的运行身份和报告约定。完整验收由受版本管理的用例完成；一次探索式操作不会自动获得验收通过资格。

原生工具首版只承诺 Chromium Web。Android、iOS 和桌面后续分别立项，不能以 Web 验收替代设备验收。

## User Stories

1. As a 开发者, I want 从对话指定卡片并发起验收, so that 不用手动拼装启动和测试命令。
2. As a 开发者, I want agent 读取卡片验收标准并指出用例覆盖关系, so that 测试证明的是需求而不是任意演示。
3. As a 开发者, I want 首次准备环境后留下可重复执行的启动手册, so that 后续验收不必重新探索项目。
4. As a 验收人员, I want 确认被测 URL、构建与工作区, so that 不会验收另一个服务或旧构建。
5. As a 用例作者, I want 用 Playwright 管理导航、数据准备和确定性检查, so that 业务不变量不依赖视觉模型猜测。
6. As a 用例作者, I want 用 Midscene 表达视觉动作和可见结果, so that 能验收难以稳定定位的页面元素。
7. As a 用例作者, I want 将测试数据和登录状态隔离, so that 用例能重复运行而不互相污染。
8. As a 开发者, I want 使用固定 SDK 和已验证视觉模型配置, so that 结果可复现且不会因隐式升级改变行为。
9. As a 用户, I want 运行开始后看到用例、步骤和实时输出, so that 知道工作仍在进行及卡在哪里。
10. As a 用户, I want 从现有任务控制入口取消验收, so that 停止真实工作并释放其拥有的资源。
11. As a 用户, I want 区分通过、断言失败、基础设施错误、取消、超时和中断, so that 能决定修代码、修环境还是重跑。
12. As a 审查者, I want 从卡片测试摘要打开截图和 HTML 报告, so that 能回看动作及可见结果。
13. As a 审查者, I want 报告写明用例与断言数量及未执行项, so that 不会把部分完成或零用例当成通过。
14. As a 审查者, I want 报告关联源码、未提交内容、用例与运行环境, so that 能判断它是否仍适用于当前变更。
15. As a 开发者, I want 卡片变更后产物登记明确拒绝或重新核对, so that 旧结果不会静默覆盖新状态。
16. As a 维护者, I want 失败、取消、缺少凭证和超时无法通过验收门禁, so that done 有真实证据支持。
17. As a 维护者, I want 能按项目配置测试范围、超时和完成边策略, so that 不会对无 Web 界面的卡片强制运行浏览器。
18. As a 维护者, I want express 和 emergency 的验收策略明确可见, so that 跳过 testing 不会被误认为已经完成视觉验收。
19. As a 用户, I want 重新打开会话后仍能找到已经完成的报告, so that 结果不依赖进程内 job 记录。
20. As a 用户, I want 宿主重启后未完成运行显示为中断或未知, so that 不会误以为浏览器操作已经完成。
21. As a 用户, I want agent 在重跑有副作用的动作前检查现场, so that 不会重复提交或删除数据。
22. As a 项目负责人, I want 子卡片各自有验收证据而父卡片有集成验收, so that 单个子任务通过不会冒充整体通过。
23. As a 开发者, I want 阶段二通过原生工具打开和操作指定 Web 目标, so that 可以探索失败现场而不编写临时脚本。
24. As a 开发者, I want 原生工具返回可解析的查询、断言和运行标识, so that 后续调用不必从说明文字提取信息。
25. As a 用户, I want 工具说明当前页面和目标并拒绝不属于当前调用者的目标, so that 操作不会落到其他会话。
26. As a 用户, I want 两张卡片并发时页面、模型配置和报告隔离, so that 它们不会抢同一个活动页。
27. As a 用户, I want 连接已有测试浏览器时明确其所有权, so that 插件退出不会关闭由我启动的浏览器。
28. As a 用户, I want 工具结果在会话重放时保留目标、结果摘要和报告入口, so that 历史不是只有一个成功图标。
29. As a 维护者, I want 插件卸载后释放工具注册、监听与自有浏览器资源, so that 重载不会留下幽灵工具和任务。
30. As a 维护者, I want 模型凭证不出现在工具参数、日志和报告, so that 能安全管理测试配置。
31. As a 维护者, I want 查看模型用量与运行耗时并设置超时和步骤限制, so that 能控制测试成本；无法取得的统计应明确不可用。
32. As a 用例作者, I want 将探索结果整理成可审查的用例后再用于验收, so that 自由操作不会悄悄修改验收标准。
33. As a 发布维护者, I want 用真实 Loader、打包 profile 和浏览器证明兼容, so that 单元测试通过不会被误报为安装可用。
34. As a 开发者, I want 阶段二复用阶段一的报告格式与状态含义, so that 升级到原生工具不需要迁移已经积累的验收证据。

## Implementation Decisions

### 职责与版本

- Harness agent 是工作流执行者。Devflow store 管理卡片、revision 和 journal；各 gate 继续拥有阶段准入判断。Midscene 只负责页面交互、视觉判断和执行证据，不新增 Devflow runner 或第二套阶段状态机。
- 以本地 main 的 runbook 架构为基线。Harness 依赖保持精确发布版本 `0.1.5-rc.2`，Cordis `4.0.2`。Midscene 以调研确认的 `1.12.6` 为候选，进入实现时重新验证完整依赖与公开 API，统一锁定后不得浮动升级。任何必须升级 Harness 的发现应先调整方案，不能偷偷依赖未发布接口。
- 不接已退役的 Midscene MCP，不在首版引入 Beta 测试框架。以 Playwright + Midscene SDK 为稳定执行路径。
- 复用社区插件的服务/提供者/工具分层理念，按当前 Harness 契约适配。修正已确认的 aiAssert 返回值错误，并覆盖默认成功、断言失败和 SDK 执行错误，不能复制现有 mock 的错误预期。

### 阶段一交付与产物

- 交付验收技能、项目用例模板、受版本管理的结果汇总入口和试点用例。复用 testenv 的环境 runbook、Harness shell/jobs、Devflow artifact 与 command gate；不恢复旧的 testenv 证据执行器。
- 每次运行使用独立 runId、输出目录和浏览器 context。结果记录卡片/工作区、用例集与指纹、源码及工作区内容指纹、被测服务构建标识、SDK/模型、开始结束时间、用例/断言计数、结果分类和报告引用。字段须有实际消费者，不暴露上游内部 dump 作为稳定公共格式。
- 卡片登记使用现有 `test-report` 类型的 Markdown，包含 Coverage 和 Results 以及独立 HTML 报告的可访问引用。大报告和截图保存在受配置管理的测试输出位置；不把外部路径直接传作卡片内 artifact，不绕过 store 写保护。首版不承诺 HTML 已被卡片归档复制，也不承诺原生 iframe 预览。
- 报告缺失或迁移后路径不可达应明确显示不可用，不能成为成功证据；完成报告保留到显式清理。文件保留与活跃 job 生命周期分开管理。
- 卡片产物登记发生在阶段转移前，通过现有工具/服务、真实 actor 和最新 revision 执行。同一卡片 transition waterfall 内不得重入产物写入。
- 首版 command gate 对配置了 Web 验收的完成边进行真实重跑，依据本次执行退出状态及完整结果裁决，不信任可任意编辑的旧 `passed` 字段。为避免重复运行而引入的可信缓存不在首版范围；UI 明确区分先前检查与门禁重跑。门禁失败保留原始输出，供 agent 随后登记，不能在 waterfall 内回写卡片。
- 默认按项目显式配置 `testing → done` 验收；express/emergency 的其他完成边必须明确启用相同验收或记录该路径未要求验收。不得对未配置路径显示“Midscene 已验证”。

### 阶段二交付与工具生命周期

- 新增 Web Midscene provider 与原生工具消费者；只有实际复用需要时才拆独立服务包。可选 Devflow 适配层通过公开服务关联卡片，provider 不写卡片存储。
- 支持显式目标的打开/连接、操作、输入、查询、断言、等待、报告获取及关闭自有目标。工具名称和动作参数以当前 schema 约定为准，但必须暴露目标身份，不能用一个共享服务让 Android 工具实际操作 Web。
- 同一目标串行操作；不同目标按调用者和卡片隔离。所有权来自真实调用上下文，模型不能声明任意 owner。外部浏览器的连接、借用页面和自有 context 分别记录，只销毁本插件拥有的资源。
- 前台操作响应 `exec.signal`；后台操作通过现有 jobs 注册，使用独立 job 生命周期与取消控制。取消返回和任务完成须以实际操作停止、资源清理完毕为依据；不可中断 SDK 操作应在受控进程中执行，并有升级终止路径。
- 将 Midscene progress、report 和 usage 转为有限的项目结果字段。Web 展示复用现有工具卡和 job 入口，必要时注册原生客户端 slot；持久化必要结果元数据以支持重放，不能依靠 Host presenter 自动生成 Web 视图。
- 模型配置按实例或进程隔离，不在共享进程运行期间修改全局环境变量。超时、步骤数、输出大小和允许目标是部署配置；凭证通过已有配置注入。
- 阶段二的自由操作默认属于探索记录。只有选定受版本管理的完整用例并满足阶段一证据规则，才可参与验收判断。

### 中断与父子任务

- jobs-local 不保证跨进程恢复。持久化运行清单与已完成结果，重启后对没有可靠终态的记录标为 interrupted/unknown，保留可检查的部分报告。检查和显式重跑由 agent 发起，不新增后台调度器或自动动作回放。
- 父子卡片分别登记验收结果，父卡片另做集成验证。是否能完成仍由既有 parent gate 判断。

## Testing Decisions

### 主测试边界

采用真实 Harness 组合下的用户可见行为作为主要边界：对话/工具请求经执行入口产生运行、日志与报告，登记 Devflow 产物，再请求阶段转移并读取 journal 与结果。只替换外部模型和不可控外部系统；不能用 mock store、mock 工具注册表或 mock 状态机替代关键组合路径。

阶段一先通过真实 shell/jobs 执行用例与门禁，阶段二在同一组合中通过真实 Loader 注册和调用原生 Web 工具。真实 SDK 与本地 Chromium 的契约验证单独覆盖，不把付费模型依赖加入所有单元测试。

### 现有先例与检查范围

- 参考 artifact-contract 的真实 Loader 组合测试、devflow-web 的 HTTP/变更流测试、工具调用与 registry disposal 测试、Harness jobs 的输出/取消约定和已记录会话重放机制。
- 正向路径验证从卡片验收标准到报告与阶段 journal 的完整结果；负向路径验证断言失败、零用例、部分完成、报告缺失、模型不可用、浏览器断开、超时和取消不会获得通过。
- aiAssert 契约测试使用所选真实 SDK 的行为或受控模型端点，不通过 mock `undefined` 返回值自行定义成功含义。
- 验证源代码、脏工作区、测试用例、被测构建、卡片 revision 和归属改变后的结果处理。首版门禁必须真实重跑，旧文件不能跳过执行。
- 验证并发目标与模型隔离、跨会话访问拒绝、重复取消、前台 pre-abort、后台取消、清理失败以及 borrowed browser 不被关闭。
- 验证会话重放和宿主重启后的报告读取，未结束运行明确为中断/未知；不自动重新执行可能有副作用的操作。
- 报告入口在真实 Web 中可用；既有看板/列表导航保持可用。普通单元测试、组合测试、真实浏览器验证和真实视觉模型验收分别报告。

### 阶段完成条件

**M1：阶段一完成。** 用真实 Loader/profile 和 Chromium 从对话完成一个 Devflow 导航用例，产生可打开报告和 test-report；故意改变预期后断言失败且门禁拒绝；取消/超时停止实际工作；重启可读取旧报告但未完成运行不显示通过。所有结果记录实际构建与用例版本。至少包含一次真实视觉模型正向运行和一次预期失败，记录环境与用量。

**M2：阶段二完成。** 在 M1 的同一验证入口通过原生工具完成等价流程；两个隔离目标可独立运行、跨 owner 访问被拒绝；取消与卸载释放自有资源；外部 Chrome 保留；会话重放恢复结果摘要与报告入口；自由探索不会被门禁当成验收。

**发布前。** 受影响源码按项目要求通过类型、lint、逐文件覆盖率、组合测试、构建和 tarball 检查；真实安装组合与 Web 验收有独立记录。构建成功不等于 M1/M2 验收成功。首次实现验证使用隔离 profile，实际用户 profile 的部署属于后续交付操作。

## Out of Scope

- Android、iOS、HarmonyOS、桌面设备及真实设备管理。
- 新的 Devflow 状态机、后台 runner、自动调度器和跨重启继续执行浏览器动作。
- 直接依赖社区旧插件即宣称兼容；维护历史 MCP；引入 Beta 测试框架。
- 用视觉判断替换所有 API、数据库、权限和确定性断言。
- 自动接受模型生成的用例修改、自动放宽失败断言、自动扩大操作目标范围。
- 门禁结果缓存、可信证据签名平台、通用附件存储平台及新的报告门户。
- 重建 Devflow 看板/列表，或由报告页面直接推进卡片阶段。
- 本次规划阶段安装依赖、修改运行中的 profile、执行产品代码改动、发布 npm 或部署。

## Further Notes

- 两阶段是顺序交付，不是两条并行方案；M1 未满足前不开始阶段二实现。两个阶段共享一个工作分支，分别形成可审查的变更批次。
- 本 PRD 发布到本地 Markdown tracker，使用 `ready-for-agent` 表示需求可供后续 agent 执行；Trellis `planning` 表示本轮只完成规划，不等于已经授权启动实现。
- 技术证据已确认：旧插件默认 aiAssert 成功处理存在错误；Midscene MCP 已退役。报告链接、SDK 版本和基线差异在配套调研记录中保存。
- 当前主线存在本地与远端分叉；本需求基于本地 main 的 runbook 版本。后续准备合并时应单独处理基线整合，不在 Midscene 需求中恢复已删除的旧 testenv 功能。
- 实施前按当前仓库加载相关规范，新增非平凡功能时同步 Agent Note、README、类型契约与相应测试；本 PRD 的模块选择不授权改动 Harness 内部实现。
