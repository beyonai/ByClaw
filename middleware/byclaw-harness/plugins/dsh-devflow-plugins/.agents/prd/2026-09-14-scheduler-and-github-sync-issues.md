## 共同交付要求

每个切片同时交付公开服务行为、必要持久化、现有对话管理入口及可见状态、真实 Loader 组合测试和接入文档。适用的模型工具须带用户可读结果呈现。不得把界面、测试和恢复统一留到最后一个切片。

只使用项目固定的已发布 Harness 接口。遵循项目的服务定义、提供者与消费者规范；开发流程仍归现有 Devflow 和 Harness agent。每个切片执行适用的类型检查、lint、测试、构建与打包验证；涉及新插件组合时验证真实 profile 加载，分别记录构建结果与运行验收结果。

没有已证实必须单独进行的前置重构；如实施中发现，先以具体依赖和可验证收益提出。S1 用真实注册的测试处理器验证通用能力；S2 不依赖定时器；两个入口在 S3 组合。S7 的消费者为接入示例，不实现问题评估或开发策略。

## S1 — 无活跃聊天时执行固定间隔计划

用户故事：1、2、4–13。

### What to build

用户通过对话管理固定间隔计划，注册的处理器在宿主运行、没有活跃聊天时接收到触发。用户可以查询、修改、暂停、恢复、删除和手动触发计划，查看下一次触发、投递结果与下游运行引用。计划和触发跨重启保留。通过一个真实注册、持久化接收的示例处理器完成端到端验收。

### Acceptance criteria

- [ ] 公开服务和对话入口能完成计划全生命周期，校验时间及处理器参数，变更记录真实调用者；手动触发有独立标识。
- [ ] 固定间隔保持时间锚点，宿主不运行时不承诺执行；重启支持默认合并最近一次到期及可选跳过策略。
- [ ] 触发意图先持久化，重试复用标识；示例处理器持久化幂等接收后才返回运行引用，回执丢失可重投而不新建工作。
- [ ] 计划、投递与下游完成分别展示；处理器缺失、超时及重试耗尽具有可见状态。
- [ ] 同一计划运行未结束时合并后续到期请求，运行状态通过通用处理器协议查询或报告；该协议不包含 GitHub 业务字段。
- [ ] 暂停和删除阻止未来投递，不暗中删除已接收工作；处理器释放或插件卸载后停止新投递。
- [ ] 真实 Loader、真实持久化及确定性时间推进覆盖无活跃聊天、重启、接收回执丢失、重叠和卸载；验证固定依赖的 profile 加载。

## S2 — 手动同步仓库 Issue 与评论并查看结果

用户故事：14–16、18、21–26、32–35。

### What to build

用户创建仓库订阅并手动同步 Issue 与评论，无需加载定时器。同步结果保存稳定来源身份、关联关系及可读取版本，并产生持久化变更记录。用户可查看进度、内容、错误与初始同步是否完整，暂停订阅或取消运行。

### Acceptance criteria

- [ ] 仓库订阅、凭证引用、所选内容类型通过公开服务和对话入口配置；Issue 和评论分别分页获取，排除 PR。
- [ ] 保存来源 ID、仓库身份、对象类型、父子关联、URL、远端更新时间（如有）、抓取时间、指纹与本地版本。
- [ ] 快照与变更记录逻辑原子提交，记录能读取对应历史版本；首次同步未完成时明确显示，不能以单页成功冒充完整结果。
- [ ] 运行显示分页数量、进度、错误和最后成功时间；认证失败、限流、超时和重试耗尽不视作空数据成功。
- [ ] 同一订阅的人工请求串行处理，接收具备持久化请求标识与幂等行为；分页提交中断后重启可恢复，检查点不越过已提交数据。
- [ ] 暂停订阅阻止新运行；取消当前运行保留已提交内容，并拒绝取消后的迟到结果。
- [ ] 凭证不进入日志、快照或返回内容；外部正文不作为命令执行；没有 GitHub 写操作或 Devflow 建卡副作用。
- [ ] 真实组合测试只替代外部 GitHub，覆盖多页、失败、取消与重启；独立插件可在真实 profile 加载和操作。

### Blocked by

None - can start immediately

## S3 — 定时同步仓库并关联完整运行状态

用户故事：1、2、4–13、23–25、35。

### What to build

GitHub 同步插件注册通用处理器，用户为已有订阅创建固定间隔计划。无需活跃聊天即可完成从到期触发、持久化接收到同步结束的流程，用户能从计划找到同步运行并定位失败归属。

### Acceptance criteria

- [ ] 用户通过管理入口关联计划与订阅；计划参数只引用受校验的订阅标识，不复制凭证。
- [ ] 同步运行持久化接收后才返回运行引用，界面或对话结果准确区分已触发、已接收、同步中、部分失败、成功和取消。
- [ ] 回执丢失、触发重投和宿主重启不会创建额外同步运行；接收前投递重试归定时器，接收后运行重试归同步插件。
- [ ] 定时与人工同时触发同一订阅时串行处理，不同计划不能绕过订阅互斥；下游完成后计划可继续触发。
- [ ] 暂停计划、暂停订阅与取消运行各自行为可见；卸载同步处理器后计划明确等待或失败，重新加载可以恢复。
- [ ] 真实 Loader 组合在无活跃聊天条件下走通完整同步，注入接收回执丢失与通知丢失并恢复；真实 profile 验证管理入口和状态关联。

## S4 — 按 Cron 与时区执行通用计划

用户故事：3–5、8、9、11。

### What to build

用户能为通用处理器配置五字段 Cron 和 IANA 时区，在管理入口查看下次触发并修改时间规则。复用既有接收、补触发和运行生命周期。

### Acceptance criteria

- [ ] 创建与更新接受合法五字段 Cron 和 IANA 时区，非法值拒绝保存，查询返回明确的下次触发时间。
- [ ] 夏令时缺失的当地时间跳过，重复的当地时间只触发一次；运行不隐式依赖浏览器或宿主时区。
- [ ] 重启、时钟前后调整、修改计划和错过多个周期遵守稳定触发标识与既定补触发策略。
- [ ] 使用 S1 示例处理器通过真实 Loader 验证管理、到期接收及重启；无需依赖 GitHub 同步即可演示。

## S5 — 增量更新与对账保持 Issue 内容准确

用户故事：15、18–20、23、26、32。

### What to build

对已同步的仓库执行增量扫描与定期对账，记录 Issue 及评论的编辑、关闭、重新打开和有证据的删除。用户能查看新旧版本、变化类型及不完整或不可访问状态。

### Acceptance criteria

- [ ] 根据资源实际接口能力选择增量或对账，使用重叠窗口与指纹去重；未变化的内容不产生新版本或重复变更。
- [ ] Issue 和评论更新可被发现，变更记录准确关联对应版本；关闭与重新打开不会被过滤条件永久漏掉。
- [ ] 完整且有权限的对账或明确证据才能确认删除；认证失败、404 歧义与中断分页不得批量删除本地内容。
- [ ] 修改订阅范围后建立相应基线，进度明确，不误用旧游标或将范围移除视为远端删除。
- [ ] 分页提交中断、快照提交中断、检查点写入失败及通知丢失后恢复无遗漏；失败不冒充整体同步成功。
- [ ] 从手动入口完成初始同步、远端变化、增量或对账、历史查询的真实组合验收。

## S6 — 同步 GitHub Discussions 及完整回复上下文

用户故事：14、15、17–20、23、26、32–35。

### What to build

用户在仓库订阅中启用 Discussions，同步主题、评论和回复，并通过相同查询与运行入口查看内容、变更及进度。保留 Discussion 类型和回复层级，复用持久化及接入协议。

### Acceptance criteria

- [ ] 订阅可独立选择 Discussions；主题、评论、回复的分页完成度与关联关系正确，不将 Discussion 伪装成 Issue。
- [ ] 同步生成相同协议的版本和变更记录，支持后续更新和对账，不假设 Discussions 支持 Issue 的增量参数。
- [ ] 未启用、权限不足及部分回复失败明确展示，不影响已成功提交的 Issue 内容，也不报告整体全部成功。
- [ ] 取消、重启、重复抓取、限流、凭证脱敏与不可信内容处理满足既有行为；无需定时器可以手动验收。
- [ ] 真实组合覆盖多层分页、主题及回复编辑、不可访问与恢复，公开查询可还原讨论上下文。

## S7 — 下游插件独立消费、确认和回放变更

用户故事：26–30、36。

### What to build

提供公开消费协议和一个最小示例消费者。每个消费者按订阅独立读取、确认和回放持久化变更，处理进度可查询。实时通知仅唤醒消费者，离线和重启后仍可续读。

### Acceptance criteria

- [ ] 接口支持分页读取、独立确认位置、从头或当前位置注册、显式回放；记录具有稳定 ID、有序游标及可查询的对应快照。
- [ ] 只接受已交付连续前缀的确认，拒绝跳过未处理项；明确并验证确认失败可能导致重复消费。
- [ ] 示例消费者以记录 ID 幂等保存可观察结果，处理后确认前崩溃不产生重复副作用；未确认记录重启后可读。
- [ ] 两个消费者独立运行，一方失败或离线不阻塞另一方；丢失内存通知仍通过持久化记录恢复。
- [ ] 提供消费进度、失败与回放入口，接入文档说明注册、读取、确认和幂等责任；不加入模型评估或开发策略。
- [ ] 真实组合由手动同步产生变更，消费者完成读取、确认、重启续读及历史回放，不模拟内部服务协作。

## S8 — 多实例接管后拒绝旧运行的迟到提交

用户故事：8、10、12、13、24、25、31。

### What to build

两个宿主实例共享同一持久化域时，计划与同步运行具有唯一有效持有者。实例退出或失去持有权后可恢复接管，旧实例恢复及取消后的网络返回不得提交结果。用户能看到接管、等待和最终运行状态。

### Acceptance criteria

- [ ] 通过持久化互斥和执行代次防止两个实例对同一计划或订阅冲突提交；定义共享存储支持条件并对不支持的部署明确报错。
- [ ] 两个实例同时到期只形成一次有效承接；已持久化接收但回执丢失时，接管沿用原运行。
- [ ] 持有权失效后的实例无法推进触发状态、快照、变更或检查点；取消后的迟到响应同样拒绝。
- [ ] 不同订阅在配置的全局并发限额内运行，实例恢复不会超发；同一订阅始终串行。
- [ ] 在真实双实例组合中注入崩溃、失去持有权、旧实例恢复及取消后返回，查询结果证明无冲突提交与遗漏。

## S9 — 存储达到容量上限时暂停同步并保留可回放历史

用户故事：23、25–30、36；覆盖 PRD 的保留策略与组合发布验收。

### What to build

用户查看历史存储占用并配置容量上限。达到上限后暂停新增同步，明确提示原因；保留历史、查询和消费能力，提高上限并恢复后可以继续同步。该切片同时完成所有已交付能力在安装 profile 中的组合验收。

### Acceptance criteria

- [ ] 管理入口可查看占用、设置上限并查询容量等待状态；容量不足时不写入不完整快照与变更，也不推进同步检查点。
- [ ] 不自动删除历史或对应版本；容量暂停不阻止已有消费者查询、确认及回放。
- [ ] 提高上限并显式恢复后从已提交位置继续；计划不得把容量拒绝显示为同步成功。
- [ ] 通过定时同步产生多版本内容并触发容量限制，再恢复同步；两个消费者能够持续读取已有历史，包含 Issue 与 Discussion。
- [ ] 固定已发布依赖下安装真实 profile，验证固定间隔、Cron、人工同步、独立消费、多实例支持条件、暂停和恢复；汇总每个切片已有证据，不以该项代替前序切片自身测试。
- [ ] 用户文档说明容量、历史保留及恢复操作，分别记录构建、真实运行与外部 GitHub 验证的实际范围。
