# AGENTS.md

本文件约束本仓库所有插件的开发与维护。进入具体插件目录后，还须遵守该目录的 `AGENTS.md`；工具定义及平台兼容性检查同时适用本文件。

## 插件工具定义规范

适用于新增或修改模型可见的工具名称、`description`、参数说明、输入输出 schema、注册作用域和注入顺序。模型可见措辞属于行为的一部分，不能仅按普通注释修改。

### 描述内容与预算

- 工具描述只说明：何时调用、执行什么、关键前置条件、重要副作用、结果及使用限制。参数描述只说明该字段的含义、格式、缺省语义和必要约束。
- 使用简洁、中性的业务语言。面向中文业务的工具优先使用简洁中文；已有其他语言约定的插件须记录语言调整的原因。不得声称中文本身能保证平台接受请求。
- 不把事故复盘、推理过程、长篇操作教程、重复示例、角色指令或整段文档塞入工具定义。背景依据和详细流程放在插件文档中；调用时必须知道的约束仍保留在描述里，不能只留下文档链接。
- 新增或修改描述时，默认顶层描述不超过 250 个 JavaScript 字符（`description.length`），单个参数描述不超过 150 个字符。这是项目维护预算，**不是百炼或其他平台公布的上限，也不保证低于预算就不会被拒绝**。超出时先消除重复；仍需超出则记录必要性并提供对应平台回放证据，不机械截断，不省略关键限制。
- 禁止运行时统一截断、过滤词语或删除工具来掩盖平台错误。确需调整可用工具集，应作为独立行为变更说明并验证。

必须保留的语义包括：用户授权和确认要求、权限及作用域、持久化影响、覆盖或增量语义、缺省和空值行为、只读或写入、文件访问限制，以及成功结果不能代表什么。

例如，`prepare_group_task_publication` 必须明确“整体替换待发布内容、等待用户确认、不上传附件、不发送群消息、不完成任务、不能声称已经发布”；`devflow_record_iron_rule` 必须保留确认后的记录触发条件、重复规则合并和管理员规则保护；`devflow_read_spec` 必须保留过期文档先核对代码的要求。

### 参数 schema 与执行约束

- 类型、必填字段、枚举、长度、数组数量和额外字段策略由 schema 表达；权限、路径、跨字段依赖及业务状态还须在执行端校验。描述不能代替校验。
- 使用当前 DSH SDK 支持的定义方式：`defineTool` 的字段 DSL 可使用字段上的 `required: true`，原始 JSON Schema 使用对象级 `required: [...]`。不得将 DSL 未转换的定义直接当成平台 JSON Schema 发送；检查实际注册并发送的 schema。
- 输出 schema 和渲染结果须与实际执行返回值一致。不得为减少描述或绕过平台错误而放宽权限、必填项、枚举、`additionalProperties` 或文件约束。
- 仅优化措辞时，工具名称、非 description 的 schema 字段、执行代码、作用域、确认流程和工具顺序保持不变；若确需改变，单独说明原因并补充对应测试。
- 保持注入顺序确定。已有工具顺序兼容处理不能因描述精简而顺手删除；顺序问题须独立进行对照验证。

示例（原始 JSON Schema 的参数片段）：

```ts
// 不推荐：只告诉模型“务必传正确参数”，未声明可验证的字段约束。
const weakParameters = { type: 'object', description: '严格按要求传入参数。' }

// 推荐：字段说明简洁，格式及额外字段策略由 schema 表达。
const parameters = {
  type: 'object',
  properties: {
    text: {
      type: 'string',
      maxLength: 100000,
      description: '完整待发布正文；省略会清空旧正文，仅发附件时可省略。',
    },
  },
  additionalProperties: false,
}
```

以上仅展示参数片段；实际工具仍须校验正文和附件至少一项，并执行权限、路径和状态检查。

## 平台异常排查与验证

遇到 `400 data_inspection_failed` 或工具定义相关拒绝时，先确认失败发生在平台请求接收、流式返回、参数解析还是工具执行阶段。`data_inspection_failed` 本身不能证明描述过长、JSON Schema 错误或具体某个工具有问题；工具描述、消息历史及其他请求内容都应纳入排查。

1. 获取真实发送的请求，以原请求作为对照；保留模型、消息、其他模型参数、完整工具集和工具顺序。不要用只有一条“你好”的简化请求代替原场景的复现证据。
2. 每轮只改变一个维度，例如仅改指定工具及参数的 `description`。比较时递归去除 description，确认剩余报文相同；若研究顺序或工具移除，另外开展实验。
3. 交错发送原版与候选版，同一条件至少重复两次；结果不稳定时增加轮数。记录成功数、失败数、状态码、错误码、请求 ID、模型及渠道；不以单次成功归因或宣布修复。
4. 不将 `HTTP 200` 或首个 SSE 数据当成完整成功。分别验证请求被接受、流正常结束、模型能正确选择工具及生成参数、执行结果正确；未验证的层级明确说明。带副作用的工具调用使用隔离工作区或测试业务数据，并遵守真实授权和确认流程。
5. 请求回放和报告不得提交 API Key、认证头、完整生产对话或生产用户资料。凭证通过环境变量或受控本地文件读取；提交的测试使用脱敏夹具。

| 观察结果 | 可以确认 | 不能据此确认 |
|---|---|---|
| HTTP 400，`data_inspection_failed` | 平台拒绝了该请求 | 工具已执行；存在固定长度上限；唯一故障工具 |
| HTTP 200，收到初始 SSE | 请求被接受，流开始 | 回答正常结束；工具选择和执行正常 |
| 工具入参校验失败 | 该次入参不符合执行约束 | 平台内容检查失败 |
| 隔离场景工具执行通过 | 该场景执行及断言通过 | 所有模型和业务场景均可用 |

## 变更所需检查

- 从真实 Loader/工具注册入口检查模型最终看到的名称、描述和 schema，不能只测试字符串常量。
- 为被修改工具补充或维护描述预算和关键语义断言，以及非 description 参数约束检查。
- 执行相关成功、缺失/非法参数、权限或作用域拒绝、覆盖/清空语义及关键副作用测试；按插件实际能力选择适用场景。保留现有组合和会话恢复测试。
- 执行所属插件的类型检查、lint、构建或 verify 命令，并检查 `git diff --check`。报告实际执行范围；未运行的检查不得写成通过。
- 平台兼容性结论须附受控回放结果；若缺少真实渠道验证条件，说明“本地通过，平台未验证”。不能将模拟测试或覆盖率等同于平台接受率。
