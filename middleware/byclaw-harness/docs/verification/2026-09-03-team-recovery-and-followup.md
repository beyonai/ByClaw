# 团队超时恢复与后台追问验证

日期：2026-09-03。

## 结论与范围

插件已实现无进展巡检和同一团长的前台追问，未修改 deepseek-harness 源码。Integration 的构建与 23 项验证脚本通过，定向代码复查通过。用户随后允许修改 ByClaw，BE 已补通用准入及多轮消息分流；新增逻辑不判断运行时品牌或使用 DSH 专用字段。

修复后已完成真实页面复验，用户最终确认端到端验证成功并要求停止继续验证。下文保留修复前失败证据以及修复后实际观察，便于追踪根因。

## 插件修复

- 5 分钟改为无进展巡检间隔。流式输出、会话事件及实际运行状态变化续期；任务总时长不限于 5 分钟。
- 超时后保持原命令和输出通道，通过 DSH 持久化 inbox 通知实际团长检查成员、阻塞与交付；嵌套团队通知所属团长，团长不可达时通知当前响应 Agent。
- 待消费巡检去重，失败后下一间隔重试；进展变化、取消、收尾或关闭会使过期巡检失效。
- 团长结束一轮时，仍在输出的成员不会被当作整个团队已结束。
- 同一团长的追问独立排队，排空团长当前轮次后执行；追问有独立消息和 trace，成员继续输出到原任务。
- 追问轮次结束时同步交还输出路由。追问附件和资源只作用于团长，后台成员保持原上下文；团长恢复后台任务时重新声明原任务上下文。

## 后端根因与已补通用能力

`ByClaw/byclaw-be/.../chat/service/ScriptService.java` 的 `prepareParams()` 首先调用 `resolveRunningTraceState()`。后者只要 `runningInfo.running=true` 且新请求不带原 trace，就抛出上述异常，未判断 `rootActive` / `acceptingInput`。

`RunningOutputStreamRegistry.applySessionRuntime()` 在团队成员仍活跃时会保持 `running=true`，同时正确返回 `rootActive=false`、`acceptingInput=true`。因此插件已经发送了可接受输入状态，页面也允许点击发送，但服务端判断仍阻断请求。提前伪造任务结束或改写后端 Redis 私有标记不能正确解决这个协议矛盾。

后端已实现的具体行为：

1. 将“团队仍运行”与“主 Agent 正在处理本轮输入”分开。确认当前通用运行态明确允许输入时，为追问创建新的消息和 trace；原 trace 的续写/交互响应继续使用已有分支。
2. 保存原任务输出上下文，按 trace 分发和落库。前台追问终态不能停止原任务的 Stream 监听、覆盖其未落库输出或释放仍在运行的团队上下文。当前 `OutputStreamManager` 的上下文以 session 为单键，需要连同清理逻辑一起核查。
3. 回归覆盖并发输出归属、两种结束顺序、迟到清理、跨实例登记和失败处理、恢复发现及最终响应广播。

这些修改属于 ByClaw 后端，不需要修改 DSH 核心。
