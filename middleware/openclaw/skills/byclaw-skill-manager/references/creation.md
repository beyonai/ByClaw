# 创建 Skill 流程

用于新建、优化、重构或迁移技能。输入为用户需求、已有技能（如有）和当前会话上下文；产物为已确定开发位置下的完整技能目录。

开发目录承载本次任务的开发、编辑和验证，具体位置与持久化由当前运行环境决定；发布后的加载由平台元数据驱动，不能把开发目录当成所有运行时的安装目录。对象与转换见 [生命周期契约](lifecycle.md)。

## 1. 确定需求与开发目录

从用户需求、已有技能和当前上下文确定触发请求、输入、预期产物及验证方式。按 [环境指引](container-environment.md) 选择用户指定或运行时提供的可写开发目录；复用已明确的路径，不要求固定目录结构或 sessionId。

使用当前文件工具直接创建或编辑技能文件，不依赖其他技能、初始化器或特定 CLI。已有技能先读取再增量修改，不重复初始化。没有可用文件写入能力时，说明受阻步骤并继续整理可交付内容；不把文本草稿声称为已落盘文件。

### 每次新建前先盘点现有能力与查重

资源盘点前读取 [凭据与连接发现](credentials-and-connections.md) 中相关的资源发现指引；直接调用平台接口或使用随附 API 脚本前读取 [API 与脚本契约](api-contracts.md)。需要确认执行环境时读取 [个人沙箱环境](container-environment.md)，处理失败或结果不明时读取 [错误与恢复](error-codes.md)。已加载且仍有效的内容可复用；按需加载不意味着可以跳过创建前的资源盘点。

每次新建技能前，无论用户意图是否明确，都先检查当前运行时能力与平台资源目录：既查相似 SKILL，也查能直接完成业务动作的 TOOL、TOOLKIT、MCP 等相关资源。不能只查技能、只看已加载工具，或等用户点名资源类型后才补查。按业务目标、输入输出、操作对象与能力重合度比较，不仅匹配技能名称。已有同一任务、相同查询范围且仍有效的查找结果可复用；业务方向变化后补查。

用户只表达“想做一个技能”时，可先浏览当前可见技能，引导确定业务方向；优化目标不清时，围绕已有技能与期望变化提问。不要求用户先给出完整技术方案，也不将全量目录展示作为每次新建的必经步骤。

查询结合当前运行时技能清单与平台实际提供的技能目录，按接口分页和查询范围取得完整结果、去重，再优先展示与业务意图相关的技能：名称、用途、重合点、可复用部分及权限/加载状态。用户要求查看全部时提供当前可见范围的完整清单；结果较多时可按用途分组，不只展示推荐项却声称已列全。

“全部”只指当前身份在已查询范围内可见的技能。当前会话清单、某员工的完整文件列表、未绑定目录列表都不等于平台全量技能目录；查询边界和不可查询范围需说明。接口能力见 [API 契约](api-contracts.md)，不虚构全平台搜索端点，不因局部空结果断言没有同类技能。

根据实际候选提供可选择的方向：直接使用已有技能、优化某个已有技能，或为明确差异新建技能。有相近候选时展示重合点与差异，推荐复用或优化；用户了解候选后仍选择新建时，按明确差异创建，不擅自修改已有技能。完成技能与相关业务资源盘点、未发现可复用候选且需求明确时直接新建，无需额外确认。用户指定优化对象时先读取该技能，只有转为新建时才执行新建前查找。

某个查询来源不可用时，继续检查可用来源并说明覆盖缺口；全部来源均不可用时明确报告“现有能力盘点未完成”，可继续需求与资源整理，但在新建文件前让用户决定补齐查询条件或接受未完成查重继续创建。不能把无法查询报告为没有相似技能。

### 盘点的顺序与完成证据

1. 按用户目标提炼业务对象、动作、输入输出与作用域，再检索名称、编码和用途相关的候选。分别检查 SKILL 与相关工具资源；工具集还要读取其动作清单或必要详情，不能只按工具集名称判断是否适用。复用有效的已有查询结果，按实际分页读取，不将首屏或单次关键词空结果当作无资源。
2. 使用当前部署已有的资源查询能力。按 [资源发现 API 契约](api-contracts.md#平台资源发现与技能查重) 调用 `listResourceUseAuth`，通过 `resourceBizTypeList` 筛选类型；单独查询 SKILL 与 TOOL/TOOLKIT/MCP 有助于比较结果。使用前核实封装实际支持的参数与分页，不假定某个 CLI 已支持全部类型；技能包不依赖其他技能目录中的私有脚本。接口查询范围、资源详情和有效权限分别判断。
3. 将候选与用户期望的动作、数据来源和输出匹配。已有工具可直接满足时，先告知用户现成方案；已有能力需组合或规范输出时，推荐创建调用它们的技能；只有实际缺失的能力才自行实现。新技能可以复用平台资源，不要求复制工具实现。
4. 在进入实现前保留简短盘点结论：已查询的类型与范围、匹配候选及动作、可用/待授权/待验证状态，以及复用、优化或新建的理由。查询受限时说明缺口，不能宣称已完成全面查重。盘点查询与必要文件能力检查可先做，自行实现业务探测应在盘点之后。

### 按业务契约选择执行方式

在选工具或自行实现前，核对以下四点：**业务对象、身份与数据范围、权威数据来源、预期输出及完成证据**。候选名称相近、工具已加载或命令可运行，都不能代替这些匹配条件。读取候选动作的参数与响应，确认它覆盖用户实际目标，而不只是能提供相关信息。

已有能力匹配时优先复用；需要组合、补充或规范输出时只实现明确缺口。局部观测、缓存和单个工作区的数据只能证明其覆盖范围，不能当成用户全部资源或平台实时状态。若不同解释会改变数据来源、权限或实现方向，给出具体解释供用户确认；不要默默选择最方便调用的方式。跨领域反例见 [测试流程](testing.md)。

### 想法或资源不明确时匹配能力

按 [凭据与连接发现](credentials-and-connections.md#需求不明确时的资源匹配) 读取所需来源，主动将可见资源组合成少量可理解的业务方案，供用户确认或选择。先展示能完成什么、需要哪些输入、会产出什么及尚缺哪些权限/能力，不先堆砌凭据字段。

例如用户希望“自动整理工作进展”，可以在发现实际资源后推荐：用当前 Agent 模型总结用户提供的材料；读取已注册的项目 API 后生成报告；使用已连接的代码仓库提取变更后生成周报。仅推荐有发现证据的资源，尚未发现的能力标为待查，不虚构用户已连接相应服务。

每个候选说明复用或新建的理由、资源匹配、可用状态与副作用。用户确认业务方向和关键资源后，将其整理成创建/优化输入：目标、输入、输出、资源定位、认证解析方式、变更范围和验收样例。确认方案不等于已完成平台授权、连接器登录或业务写入；按实际操作范围继续。等待关键选择期间可继续只读检查与无关准备，不替用户决定影响业务方向的分支。需求、目标和资源已明确时直接继续，不重复征求确认。

## 业务依赖与生成技能的运行时契约

复用前述盘点结果，将选定资源的真实 ID、类型、操作/schema、有效权限与运行时调用路径记录为业务依赖。用户改变业务目标或所需操作时补查，不因已经完成盘点而跳过新增依赖核实。

读取 [凭据与连接发现](credentials-and-connections.md)，按实际业务依赖将三类来源及动态解析要求写入产物。新技能调用大模型时，默认复用当前执行 Agent 的模型信息；创建阶段据此验证，发布到其他员工后仍在调用时解析目标员工的 Agent 模型。

生成的 SKILL.md 和必要脚本/references 应明确：使用什么运行时能力取得当前 Agent 配置、如何解析资源认证或连接器凭据、何时刷新，以及缺失时如何处理。绑定的身份、模型协议、endpoint 与凭据必须匹配；不能把创建时读取到的秘密或默认模型地址写进产物。

按新技能实际依赖写入其必要的解析指引，保持产物自包含；不要要求目标运行时再次访问开发者会话目录或本管理技能的绝对路径。用户明确要求固定外部服务时，保存逻辑配置与秘密引用，实际凭据仍由目标用户运行时解析。

## 2. 组织并生成产物

按下方设计指引，直接在已确定的开发目录创建/更新入口与必要资源。只有实际需要时才建立 references、scripts 或 assets；保留用户现有修改。按业务动作在创建阶段解析所需模型、身份、资源元数据与连接，验证真实依赖是否可用；纯文件操作与真实业务联调的依赖分别判断。

## 3. 交接测试

完成后核对实际产物位置和文件集合，将技能目录、代表性请求、预期结果、依赖和已知限制交给 [测试流程](testing.md)。创建结束不自动意味着发布、授权或安装；按用户目标决定后续流程。

以下为直接编写技能文件时使用的产物与设计约定。

## 从真实任务确定边界

先提炼触发请求、输入、最终产物、外部副作用和成功证据。优先读取已有技能、实际 API、运行脚本和真实失败记录；不要仅凭通用知识生成平台流程。已有技能先查调用关系，保留有效约定和用户修改。

一个技能围绕一个连贯能力组织；多种路径共享相同对象和契约时可放在一个 skill 内。只有任务能独立触发、依赖或生命周期明显不同时才拆分，避免按每个 API 拆成技能。

以本技能为例，纯说明优化可以只读写文件；涉及业务实现或联调时，即使处于创建阶段也需要相应身份、连接与认证。“发布并授权给某人”还需要目标数字员工、目标用户和平台凭据。按依赖缺项决定哪些步骤可继续，不能把业务调用标为已验证。

## 面向通用 Agent 编写

技能内容以任务、输入、产物和能力需求为中心，在用户个人沙箱内执行。通用流程不依赖某一 harness 的专有工具名、默认目录或环境变量；必要的运行时适配放在 references 中，标明适用条件与发现方式。具体命令若依赖 Python、shell 或某个工具，应声明为该步骤的依赖，并给出能力缺失时仍可完成的范围。

从当前会话工具清单取得文件读写、命令执行、浏览器等能力，并结合平台资源目录发现 API、MCP 等业务能力；不要把某一 Agent 平台的专有调用写成通用 API。相对资源由当前加载器解析；依赖实际文件的脚本先取得沙箱文件路径。输入可来自用户指定资源，开发输出位于当前任务选定的可写目录，“离线”仅指不调用外部服务。

平台业务语义可以具体到 ByClaw API，但运行时适配只在实际需要时使用，不能让没有 OpenClaw CLI 或 DSH 配置的环境无法创建普通 Skill。加载、生效、刷新按目标运行时验证，不假定所有 harness 共用技能目录或热加载机制。

## 三层内容

- `name`、`description`：让 Agent 在加载正文前识别任务。名称与目录一致，使用小写字母、数字和单连字符，最长 64 字符；描述非空、最长 1024 字符，说明能力与触发情境。
- `SKILL.md`：共同约束、意图路由、关键分支、完成标准。详细参数和条件流程下沉，入口不复述引用全文。
- `references/`：按任务读取的领域契约、环境指引和例子；`scripts/` 放确定性操作；`assets/` 仅放产物会用到的模板或素材。不为凑结构建立空目录。

产物严格遵循通用 Agent Skills 规范：仅使用规范定义的字段及其允许的扩展机制，不新增 ByClaw 或 harness 专属的自定义字段。优化已有技能时，非标准字段应从交付产物移除或按规范迁移；平台管理状态由平台维护，不写入技能 frontmatter。

## 让指令改变实际决策

写清输入从哪里取得、分支如何选择、什么响应算完成。例如“查询目标员工是否已有技能绑定，再决定是否执行增量安装”，比“确保安装安全”更可执行。提供一个默认路径和必要例外，不堆积同等优先级的菜单。

通用的编程、Git、HTTP 教程通常无需重复；优先记录 ByClaw 的 ID 语义、同名覆盖、员工绑定、同步边界。可以给检查表，但只把真实前置条件写成硬约束，不把个人习惯写成平台要求。

引用使用 skill 内相对链接，从入口可直接到达。运行路径相对于已加载技能根目录，输入/输出路径作为参数；不要硬编码某位用户的 HOME、工作目录、员工 ID 或服务地址。容器事实获取见 [环境指引](container-environment.md)。

## 在实际开发目录交付技能

在已确定的开发位置建立或更新独立技能目录，目录名与技能名一致。入口、引用与脚本保持相对引用，以便整体打包；不依赖固定父目录名称。

从已安装技能或用户提供的源目录优化时，先读现有内容，将本次开发所需文件复制到选定开发目录并在其中修改。除非用户明确指定原地修改，否则不更改安装副本。已有同名开发产物先核对，保留用户更改；不为了重新生成而删除整个目录。

最终交付指出实际完整产物路径、验证结果与待处理项。不要把管理技能自身的 SKILL_ROOT 当成开发产物路径，也不要把会话文件生成宣称为平台发布完成。

## 脚本与依赖

重复的打包、验证或 API 处理适合脚本化；开放式需求判断保留给 Agent。声明解释器、第三方包、系统工具、凭据变量、联网目标与输出位置，区分必要和可选依赖。只检查变量是否已配置，不将凭据放进示例、ZIP 或日志。

脚本应有有界超时、可区分错误、无交互或明确交互模式，以及不依赖固定 cwd 的路径处理。只读检测不能夹带安装、登录或重启。没有幂等契约的写操作不能自动重试。离线测试使用临时目录和合成数据，不能把线上发布当成 smoke test。

不要把“执行成功”绑定到固定文案；验证输出文件或服务状态。对脚本的校验能力如实说明，例如本技能现有打包脚本只检查 SKILL.md 存在，不验证语义、链接或凭据。

## 迭代与验收

先保存真实请求和预期可观察结果，再试运行；覆盖正常触发、相近但不相关的请求、缺参、依赖缺失和部分失败。若有隔离环境，可让不了解设计意图的独立 Agent 按技能执行；未授权的外部副作用用 mock 替代。根据实际错误修正最小范围，不为单次问题增加通用禁令。

检查打包后的产物仍自包含，所有必要脚本和引用都存在。验证场景见 [测试流程](testing.md)。保存已知部署版本和未验证项，让后续更新可复查。
